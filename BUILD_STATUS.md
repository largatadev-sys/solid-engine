# BUILD_STATUS — Largata

**What this is:** the live map of what's built — the first thing a cold session reads. Source-of-truth index: design artifacts → `docs/design/` · story plans → `docs/plans/` (immutable point-in-time intent; never updated after the fact).

**Status and a spec link. Nothing else.** No SHAs, no branch names, no summary of what a story proved — the tickets carry the detail, git answers "where does it live" (`git log --grep <story-id>` · `git branch --contains`), and every fact duplicated here is a fact that rots. The tracker is the map; the plans and git are the territory. **On session start: read this, then verify against the code — code wins; flag mismatches.**

**Update this before the merge, not after.** A story's row reaches its final state in the last commit *on the feature branch*, so the squash-merge lands a truthful tracker and nothing follows it. Updating after the merge means committing straight to `dev`, which the git workflow doesn't allow.

Key: ⬜ not started · 🔄 in progress · ✅ done · ⚠ blocked · 🚫 wontfix *(specced, then declined — the spec stays as the record of why)*

An unknown kind throws. Every choice is keyed on the trip title plus a coordinate, so a rebuilt dataset is the same dataset — screenshots, walk assertions and bug reports all stay reproducible.

**The founder found four defects by reading the data that no measurement caught, and that is the lesson worth keeping.** Distinct-title percentages, band counts and median costs were all green while the fixture offered a boat trip in Indonesia for **85 rupiah** (half a US cent), told travellers to *"wear something you can swim in"* at **Petra**, served *"Long lunch"* at **08:45**, and repeated one location across every activity in a day. **Aggregate statistics cannot see nonsense; they only see distribution.** Reading a single trip end to end surfaced six absurdities in a minute. Fixed: `TYPICAL_COST` carries a per-currency figure for all 52 currencies calibrated against what the written-out fifty charge; one vocabulary pool per time band; terrain-specific notes moved behind the kind; each activity given a distinct sub-place inside its day. Uniqueness is **trip-scoped, not day-scoped** — a hub revisited on day 7 was repeating day 1's line, which needed the used-sets lifted from `buildDay` to `buildTrip` and the sub-place pools widened.

**The photo's caption drives the activity, and the extractor is deliberately low-recall.** Every activity's *description* is its own photo's Pexels alt text — the one string literally true of what you are looking at. Its *title* takes the caption's landmark only when there is a real one: a loose filter accepted 42% of 1,669 captions but half were unusable (*"Captivating aerial view of Sapporo"*, *"of a red Hanoi sign"*), so the strict filter takes ~18% and every acceptance in a sample of 40 was a real named place. **A broken title reads as a bug where a generic one only reads as unremarkable**, and the fallback is already good. `photoForSlot` is the single definition of which photo an activity gets, so title, description and image cannot disagree.

**Seeding stayed HTTP-only, and parallelising it was proven rather than assumed.** One worker per traveler took the 150-trip local run from ~50 minutes to **4m03s** with every count exact — safe because no seeded row references another itinerary, the one cross-traveler thread (t2's collaborator role) resolving inside each trip's own sequence. The deployed run went at width 4 in **13m55s** with two recovered retries. `--parallel=N` caps the width; sequential stays the default. Flags added: `--complete-only` (seed only trips whose photos are all fetched, because a coverless trip is dropped from the Recommended rail outright and reads as a broken feature rather than an unfinished download) and `--all-public` (a shared preview wants a product, not a lifecycle spread — **not** for the rung you test against, since publishing requires `completed` and the flag therefore flattens draft/upcoming/ongoing and the two private trips that prove the visibility fence).

**Three harness bugs found by running it, each of the shape this repo keeps re-learning.** `PER_PLACE` was a literal `3` in two files, so raising it in one downloaded photos the other never looked for — and the fetcher's skip-check tested `-1.jpg`, so every cached place reported `have` forever and a raised constant topped up nothing while printing success. The archive sweep read `GET /v1/itineraries` bare, which pages at 20, so it printed a clean *"cleaned N"* having seen a fraction of the list — harmless where a wipe exists, and how duplicates become permanent on the rung where archive is the only cleanup. And one withdrawn CDN image (a 422) aborted an entire fetch run for the sake of one file.

**The photo cache left the repo entirely.** ~330MB of third-party artifacts now live at `~/.largata/photo-cache` (`LARGATA_PHOTO_CACHE` overrides), resolved once in `photoPool` so five scripts cannot disagree. Gitignoring it was never the point; it had no business in the project tree. Consequence recorded: photo-derived titles and descriptions vary with the cache, so the dataset is not reproducible from git alone — the structure, places, costs and times are.

**A credential leaked into a transcript and the rotation is deliberately parked.** `backdate-seed` passed the connection string as `-e PGURL=<url>`, putting it in docker's argv and therefore in every `execFileSync` error message; a dropped connection duly printed it. **Fixed** — the value is inherited from the child environment now. Exposure verified narrow: all 33 session logs and `git log --all -S` clean for every credential, `mobile/.env` gitignored and untracked. **Rotation deferred on the founder's call** because Railway injects that password into the backend too, and rotating a literal takes the rung down; the epic map carries the line, the trigger, and the check to run first.

*Why it wasn't a story —* No product code: every file is under `mobile/scripts/`, dev harness that never ships. No new endpoint, no schema change, no design decision left open — the decisions it did make (regional authors, the duration ladder, the caption pipeline) were founder rulings taken live and are recorded in the commits. It earns a ledger line because the *findings* are what a future reader needs: that aggregate statistics cannot see nonsense, and that three separate harness bugs all took the shape of a check whose two outcomes are indistinguishable.

**Four horizontal strips were unreachable with a mouse — the founder found Discovery's rails dead on desktop, and the fix is one shared helper the app already owned.** `dragToScroll()` shipped at S4.21 for the diary/feed photo carousels; the Discover rails (S4.3), the trip workspace tab row and the published itinerary tab bar never got it. All four hide their scrollbar and a mouse has no horizontal gesture, so on desktop they scrolled by **nothing at all** — the S1.3 dead-click shape with a new cause, and invisible on every rung below a real browser: mobile app and mobile browser both work, because touch-dragging an overflow div is native browser behaviour. **The vertical page was deliberately left alone** (founder agreed the split): wheel and scrollbar are the desktop convention, no mainstream site drag-scrolls vertical content, and adding it over a page paved with pressable cards buys a click-vs-drag ambiguity for a gesture nobody expects.

**The helper needed parameterising, not copying, and its old release behaviour would have been wrong on all four.** It settled on `clientWidth` multiples and then *set* `scroll-snap-type: x mandatory` — correct for a viewport-width pager, but on a rail or a tab row it would impose paging that surface never had. Release is now a pitch **getter** read at pointerup (`viewportPitch` for the pagers, unchanged and untouched at their four call sites; the measured card pitch for the Recommended rail, matching its own `snapToInterval`; `freeScroll` for the two tab rows and the Trending rail), and the snap type is **captured at pointerdown and restored**, so the helper can no longer hand a strip a property it did not arrive with. A drag that actually moved now also swallows the click that follows it, because these four strips are made of `Pressable`s where the photo carousels were made of images — a drag released over a tab must not select it.

**Moved to `src/components/stripScroll.*` and renamed off "photoStrip", because it stopped being about photos.** It already crossed areas (`src/feed` imported it from `src/diary`); with eight consumers across four areas, leaving it in `diary/` is exactly the shape that made S3.4 nearly mint a second copy of `stillShowing`.

**Three findings from the diagnosis, all harness rather than product.** (1) **The probe reported the fix dead after it worked.** `probe-drag.js` reused its Chrome profile, which cached the pre-fix bundle; two independent probes with fresh profiles showed the handlers attached and the strip scrolling. The wipe that should have prevented it deleted **nothing** — `$USER` is unset in this Git Bash, so the documented `rm -rf "$TMPDIR/..."` remedy expands to a path that matches nothing and exits 0. Both halves are already Gotchas entries; they compounded, and the second one sat inside the remedy for the first. (2) **`drive-profile` failed on a stale profile and passed on a clean one** — the wipe before it had failed with *"Device or resource busy"* while Chrome was still shutting down, and the suppressed error made the run look trustworthy. **Confirm the directory is gone rather than trusting the exit code**, and sleep before wiping a profile whose browser just exited. (3) A first draft of the new walk assertion keyed the Recommended rail on **this run's own fixture title**, which the rail need not contain on a database holding 150 seeded trips — it reported a dead rail against a working one. Addressed by position, with the rail count asserted so the check keeps a failure mode.

**The guard against the next one SCANS rather than lists, which is the whole point.** A wiring test over a hardcoded list of the eight known strips would have caught this bug and then rotted — the next rail added is not on the list, and escapes exactly as these four did. `stripDragWiring.test.ts` walks `src/` and `app/` for `<ScrollView … horizontal>` and asserts each spreads the handlers, so the test grows with the tree. It independently rediscovered precisely the eight files this fix's audit found, which is the audit's own confirmation. Sabotage-checked on the property that matters: a throwaway rail with no drag fails the run **naming the new file**.

**`DiscoveryFiltersIT` compared one page against a total, so CI went red for a product that is correct — the second time this test has bitten.** `theCountAgreesWithTheListUnderIdenticalFilters` asserted `browseIds(filter).size() == countFor(filter)`, but `browseIds` read a **single page** while `/v1/discovery/count` returns **every match**. CI reported `expected: 53L but was: 20L`, and **20 is `DiscoveryService.DEFAULT_PAGE_SIZE`** — the tell that the list had simply stopped at its first page. The count was right: 53 really was the number of matching trips.

**It only fires under accumulation, which is why it looked intermittent.** The ITs share one singleton Postgres container, so published trips pile up across the run; the assertion's unfiltered case therefore compares 20 against however many trips every earlier class has planted. The class passes **18/18 in isolation** and passed again when run beside five sibling publishing classes — because Failsafe happened to run it *first*. It fails only once enough classes ahead of it have published, which moves with the suite's growth and its ordering, and is exactly the intermittency the founder saw twice.

**The loop that settled it was deterministic and took 33 seconds**, rather than the multi-minute `mvn verify` that reproduces it by luck: publish 21 trips under a unique destination and compare the single-page read to the count → `expected: 21L but was: 20L`, the identical shape to CI's failure with none of the order dependence.

**Fixed by making the helper yield what the list actually yields**: `browseIds` now follows `nextCursor` to exhaustion, treating a null cursor as the end and carrying a **repeat-cursor guard** that throws rather than spinning (S3.1's lesson — a page-following loop that trusts the server loops forever and dies on a heap OOM). That also repairs a quieter erosion the same helper was causing: every `doesNotContain` assertion in the file was being checked against page one only, so a trip wrongly included but pushed past position 20 by accumulated data would have **passed**. The invariant under test is unchanged and is now stated honestly — the count equals the number of items the list yields across all its pages.

**The regression test guards its own premise, because the obvious version rots silently.** Hardcoding 21 trips against a page size of 20 means that raising `DEFAULT_PAGE_SIZE` to 50 would leave the fixture inside a single page: no paging, no comparison, and the test passes **trivially while proving nothing** — a check losing its failure mode, which is the failure this repo has now catalogued four times. It therefore asserts first that the fixture *outruns* one page (`counted > firstPageSize`), so the premise fails loudly instead of the conclusion passing vacuously. **Sabotage-checked in both directions:** the fix reverted turns the new test red on the real defect, and shrinking the fixture to 5 trips fails the premise naming it — *"the fixture must outrun one page, or this test proves nothing about paging"*.

**Verification.** Full `mvn verify` as CI runs it: **725 integration tests, 0 failures**, plus **152 unit tests** green — the page-complete helper turned nothing else red, which was the real risk (an assertion that had been passing only because a match sat on page two). *(Counts read from the `Tests run:` summaries, never the exit code — the standing rule; the earlier absence of the surefire line in this session's log was a `tail -60` truncation, not a skipped phase, and was checked rather than assumed.)*

*Why it wasn't a story —* A defect in a **test**, not in the product: `/v1/discovery/count` and the browse endpoint were both behaving as S4.3 specified, and no production file changed. It rides the mouse-drag branch because the founder raised it there and both are one-sitting fixes to S4.3 surfaces; it is recorded separately because "the walk was wrong" and "the app was wrong" are different facts, and this one is the former.

**2026-08-15**

Mouse taps stopped reaching the workspace tab row — and every other horizontal strip — because `dragToScroll` took **pointer capture on pointerdown**. Pointer capture retargets the compatibility `click` to the capturing element, so the click landed on the ScrollView and the `Pressable` tab underneath never fired. Proven in headless Chrome with a discriminating control rather than argued: capturing gives `click-target=strip` and the button handler never runs, not capturing gives `click-target=a` and it does. Introduced by 7a85fc8, which added the drag to the Discover rails, the workspace tab row and the published tab bar; the founder reported the tabs because those are the ones pressed constantly, but the Discover rails and the carousels had it too.

**The fix: capture LAZILY**, on the first pointermove past `MIN_DRAG_PX`, never on the press. A stationary click never captures, so it reaches the control; a real drag captures on first movement and still tracks when the pointer leaves the strip — both properties 7a85fc8 wanted, without the collision. The click-swallow decision also moved from *scroll* travel to *pointer* travel, fixing a second latent bug: a drag at the scroll limit moves no pixels, so the old check let the click through and activated whatever the pointer was released over.

*Why nothing caught it —* two blind spots stacked, and both are worth remembering. The unit test named *"lets a plain click through untouched — a tab that is tapped must still select"* **passed throughout**, because its fake's `setPointerCapture` is a no-op stub: the stub erased the very mechanism that breaks it. And every web driver clicks with `element.click()` on the DOM node, which bypasses hit-testing and pointer capture entirely — a synthetic click **cannot** see this class of defect, on any surface. The new tests model capture instead of stubbing it, and were checked against the old code first: 4 red, then green with the fix. Same family as the `Alert.alert` and `<Image>`-headers traps — a web behaviour whose test double is more capable than the real thing.
