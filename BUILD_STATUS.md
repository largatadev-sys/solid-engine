# BUILD_STATUS — Largata

**What this is:** the live map of what's built — the first thing a cold session reads. Source-of-truth index: design artifacts → `docs/design/` · story plans → `docs/plans/` (immutable point-in-time intent; never updated after the fact).

**Status and a spec link. Nothing else.** No SHAs, no branch names, no summary of what a story proved — the tickets carry the detail, git answers "where does it live" (`git log --grep <story-id>` · `git branch --contains`), and every fact duplicated here is a fact that rots. The tracker is the map; the plans and git are the territory. **On session start: read this, then verify against the code — code wins; flag mismatches.**

**Update this before the merge, not after.** A story's row reaches its final state in the last commit *on the feature branch*, so the squash-merge lands a truthful tracker and nothing follows it. Updating after the merge means committing straight to `dev`, which the git workflow doesn't allow.

Key: ⬜ not started · 🔄 in progress · ✅ done · ⚠ blocked · 🚫 wontfix *(specced, then declined — the spec stays as the record of why)*

**2026-08-14**

**The founders take `#0`, and the handle minimum returns to 3 — S4.14's two undischarged obligations, closed together because the order between them mattered.** Both had been sitting since 2026-08-08. V25 shipped its founder grant as a deliberate `WHERE false` no-op (the UUIDs needed a query against a deployed rung and the founders' handle choices were unsettled), and `Handle.MIN_LENGTH` dropped 3 → 2 so founders could claim 2-character handles with no founder-conditional code — the epic-map line naming its trigger as *"before the first alpha tester signs up"*, **a trigger that had already fired and been missed.** V31 grants `(0, 0)` to the four founders; the minimum goes back to 3.

**The order is the whole story, and doing it the other way round would have been irreversible.** Raising the minimum first locks the founders out of their own 2-character handles permanently: after the raise a 2-char claim is `HANDLE_MALFORMED` for everyone, there is no founder-conditional path (the no-inline-tier-check rule forbids one), and the entitlement seam that would carry `can(traveler, short handle)` does not ship until register #14. So the grant and the raise are one change, and the raise waited on a fact only the founders could supply.

**The deployed rung answered every open question at once, and three of the four had already claimed.** A read-only query against the named database (`railway`, deployed dev — verified as dev rather than prod by its schema head at **V30**, since prod is still at Epic 1's) returned: `cj`, `aj` and `ea` held by three founders, `jeb` (three characters) held by the fourth, **founder ruling: jeb stays jeb**. Crucially those three are the *only* 2-character handles in the entire namespace — **no alpha tester had taken one**, so the raise reclaims nothing and costs nobody. Population at the time: 37 travelers, 30 with handles, **zero holding cohort 0**, which is what confirmed the grant had never run rather than run and been undone.

**V31 is keyed on `firebase_uid`, deviating from V25's written instruction to carry traveler UUIDs — founder decision, taken on the record.** Both identifiers were resolved, so this was a choice. A traveler UUID is minted **per database** and `dev` is reseeded at the developer's discretion; a firebase_uid is minted **per Firebase project**, so the literals stay true across every reseed and re-applying the grant is a copy-paste of the UPDATE rather than a fresh query against rows that no longer exist. V25's actual constraint — no emails, because emails are PII and PII never enters a committed artifact — is unchanged; a firebase_uid is the same category of opaque per-account identifier as the UUID V25 was happy to commit. **V25 itself is NOT amended and cannot be:** Flyway checksums the whole file *including comments*, and V25 has applied on deployed dev, so editing even a comment would fail validation on the next deploy of every rung that ran it. Its instruction therefore stands in the tree describing a route this change did not take — V31's header is the correction, and so is this line. *(The agent proposed amending V25 before catching this, and said so rather than silently dropping the promise.)*

**A limitation recorded rather than solved: no migration-based grant survives a reseed.** On a fresh database Flyway runs V1..V31 at boot, *before* any founder has signed in — the UPDATE matches nothing, the founders provision later as ordinary cohort-1 travelers, and the badge is silently absent. This is a property of doing a data grant in a versioned migration and would be equally true of traveler UUIDs; fixing it properly means a runtime founder concept consulted at provisioning, which is exactly the authority-serving-a-cosmetic-badge mechanism V25 refused. The answer is operational: after a dev reseed, re-run V31's UPDATE by hand. **`FounderVanityGrantIT` pins that case explicitly** (`aFounderUidThatMatchesNoRowIsANoOpRatherThanAFailure`) so the fresh-database and production behaviour is asserted rather than assumed — prod is a different Firebase project and these uids match zero rows there forever, so prod keeps needing its own grant at the prod-standup story.

**`#0`, not `#00` — no code was needed.** `VanityNumber.formatted()` already special-cases founders to the bare `"0"`, pinned by `aFounderRendersTheBareZero` and `VanityNumberAllocationIT`; the mobile meta-line renders `#${vanityNumber}`. The badge became `#0` the moment the rows landed. **ADR-008 is clean on it:** zero travelers held cohort 0, so `"0"` had never been served on the wire and nothing observable changed.

**The raise is two constants and it broke exactly one test, for the right reason.** `Handle.MIN_LENGTH` and `HANDLE_MIN_LENGTH` → 3; `HandleSuggestion` and `IdentityExceptions`' message string both derive from the constant and followed automatically. `aTakenShortHandleIsStillRefusedToEveryoneElse` had asserted **409 CONFLICT** for a stranger claiming a held 2-char handle — after the raise that request is refused **400 HANDLE_MALFORMED**, upstream of the taken-check, so the test was renamed to say which refusal it is now testing. **What does not change, and is why the raise is safe:** a handle's minimum is a *claim-time* rule. `byExactHandle` only calls `Handle.normalize`, never `Handle.of` (verified by reading every call site), so `cj`/`aj`/`ea` stay looked-up and invitable; `TravelerProfileService` treats a submitted handle equal to the stored one as a no-op; and the *client* gate exempts the stored handle before its length check, which was S4.14's recorded landmine and was already closed.

**Verification.** The migration IT was **sabotage-checked**, because a migration test that passes against a no-op is worse than none (S1.1's rule, and V25 left this obligation explicitly undischarged): altering **one character** of one founder uid failed 3 of 6 assertions with the right diagnosis (`expected: 0 but was: 1` on the cohort, `4 → 3` on the shared-zero count) rather than merely failing. Run with `test-compile` in the goal list — the S4.13 trap applies verbatim, since what changed is a `.sql` under `src/main/resources` and Failsafe alone would have tested the previous build's file. Note also that `failsafe:integration-test` **reported BUILD SUCCESS with 3 failures**, which is the counts-not-exit-code rule firing for real. `VanityBackfillIT` needed no change: it targets V25, so V31 never runs in it, and its `noTravelerIsGrantedFounderZeroYet` stays true of the world it steps through.

**Also fixed here, because the promotion gate found it: `smoke-api.js` carried a stale S1.9 assertion that S4.23 had silently invalidated.** It expected a member writing to an archived trip to get **409 `TRIP_ARCHIVED`**; S4.23 changed that to the mask — **404 `ITINERARY_NOT_FOUND`** — and its own `ArchiveWriteFenceIT` says so in a test named `anArchivedTripTellsAMemberItDoesNotExist_notThatItIsFrozen`. S4.23 added `smoke-archive-posture.js` for the new posture but left the old assertion behind, so the API walk has been **red on `dev` since 2026-08-13** for a product that is correct. Diagnosing it needed no rebuild: the branch's whole backend diff is one constant and one migration, while S4.23 touched `WriteFence` and `MembershipService` — and its ITs name the intended codes outright. **Repaired rather than reported**, because a permanently-red assertion is how a gate becomes something everyone learns to skip, which is the erosion this repo warns about in three other places. **The general shape worth keeping: when a story changes a status code, the walks that assert the old one are not found by any test run** — the ITs move with the change and the walk only fails later, on someone else's branch, looking like their fault.

*Why it wasn't a story —* Two epic-map backlog lines discharged on the owner's direct instruction, both minted by S4.14 and both one-liners in the code: a four-row data grant and two constants. No new surface, no new endpoint, no design decision left open. It earns a ledger line rather than a story because the *sequencing* — grant before raise — is the only thing a future reader needs, and that is what this records.
