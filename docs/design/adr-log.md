## Decisions

### ADR-001 — Offline posture: read-cache + queued writes now; offline-first as declared target
- **Status.** Accepted · 12/07/2026
- **Context.** Users are travelers — dead zones, airplane mode, foreign SIMs. Full offline-first means a local DB + sync engine + conflict resolution for collaborative data — a foundation-scale commitment.
- **Decision.** v1: itinerary, ledger, diary readable offline via a local cache; edits queue and sync on reconnect. Offline-first is the declared long-term target. Design obligation now: the mobile data layer sits behind a repository/local-cache abstraction from day one; no raw API calls in UI code.
- **Alternatives rejected.** Online-required — fails the core usage context. Offline-first now — months of sync/conflict engineering that validates nothing the alpha tests.
- **Consequences.** Read access survives connectivity loss cheaply; the abstraction is the graft point for the future sync engine. Queued writes accept server-side ordering.
- **Invalidating condition.** Post-validation data showing engagement loss in low-connectivity contexts, or conflict-rate pain → begin the offline-first migration on the prepared abstraction (a real migration; the abstraction makes it possible, not free).

### ADR-002 — Modular monolith on the aggregate boundaries; one PostgreSQL; object storage for media
- **Status.** Accepted · 12/07/2026
- **Context.** Many domain moving parts suggested microservices/multiple DBs. But: alpha 2–3k users (orders of magnitude inside one Postgres's headroom), one developer + agent, and the Workspace aggregate demands transactional consistency (INV-7/8) — splitting the ledger into a service turns a money ledger's invariants into a distributed-consistency problem.
- **Decision.** Modular monolith; modules = the domain aggregates; interaction by ID + service interface only; one PostgreSQL as the transactional home; S3-class object storage for media; the ledger as a bounded submodule with a designed promotion path.
- **Alternatives rejected.** Microservices — all cost, zero benefit at this scale; they solve team-scaling problems this team doesn't have. Multiple databases — breaks the transactional home for no load reason.
- **Consequences.** One deploy, one DB to operate, transactions where the money is. Any module extracts later along its existing interface — addition, not rewrite.
- **Invalidating condition.** A measured post-validation signal: sustained load approaching single-instance limits, or one module's deploy cadence diverging hard → extract that module. Never calendar-triggered.

### ADR-003 — Authorization: single chokepoint guard now; RLS as the post-validation second wall
- **Status.** Accepted · 12/07/2026
- **Context.** The Trip Workspace is the isolation boundary; a silent leak is the product's worst failure. Per-service checks fail by omission; row-level security is strong but the visibility logic (public/unlisted/published-state/diary-grants) is object-shaped and painful as row policies.
- **Decision.** One authorization guard resolves (user, workspace) → Membership before any workspace-scoped operation; service methods require the resolved Membership as a parameter — unbypassable by structure. RLS adopted later as defense-in-depth (purely additive beneath the guard).
- **Alternatives rejected.** Per-service checks — safety by vigilance. RLS-only now — cost and policy complexity without v1 benefit while the guard stands.
- **Consequences.** A forgotten check is a compile error, not a leak; one rule the agent can be held to mechanically.
- **Invalidating condition.** Any app-layer leak → RLS immediately. Otherwise the post-validation hardening phase adopts it on schedule.

### ADR-004 — Mobile: React Native + Expo
- **Status.** Accepted · 12/07/2026
- **Context.** Solo developer, first mobile app, both iOS and Android at launch (hard constraint), strongest recent skill React/Next.js.
- **Decision.** React Native + Expo (EAS builds, dev-build workflow); TypeScript throughout; the future web surface shares the React ecosystem.
- **Alternatives rejected.** Flutter — new language/ecosystem, zero transfer, no web sharing. Kotlin Multiplatform — shares logic, not UI: still two UIs. Two native codebases — infeasible solo.
- **Consequences.** One codebase, maximum skill transfer. Share-sheet capture requires a native extension → Expo dev builds, not plain Expo Go.
- **Invalidating condition.** A required native capability dev-builds cannot reach, or profiled framework-attributable performance pain in core flows.

### ADR-005 — Backend: Java + Spring Boot
- **Status.** Accepted · 12/07/2026
- **Context.** The developer's primary specialty; the domain needs a strong transactional story (INV-7/8) and a mature security layer for the guard.
- **Decision.** Spring Web · Spring Security (resource server + guard) · Spring Data/JPA + Flyway · @Transactional aggregate operations · @Async unfurler worker.
- **Alternatives rejected.** Node/TypeScript backend — one language appeal, but trades away the deepest expertise where correctness matters most. Anything new-to-learn — the learning budget is spent on mobile.
- **Consequences.** Fastest correct path on the backend; the new-skill risk is isolated to the client.
- **Invalidating condition.** Nothing foreseeable at this scale; revisit on team change.

### ADR-006 — Auth: Firebase Auth (managed identity); backend as OAuth2 resource server
- **Status.** Accepted · 12/07/2026
- **Context.** Google + Apple sign-in needed (Apple mandatory on iOS alongside any social login), email verification for invites, reset/refresh/revocation. Hand-rolling ≈ weeks of security-critical work that tests nothing.
- **Decision.** Firebase Auth owns credentials and sign-in; Spring validates its JWTs as a standard resource server; the domain keeps its own Traveler keyed by Firebase UID — the provider owns credentials, we own identity.
- **Alternatives rejected.** Hand-rolled JWT auth — undifferentiated security burden. Auth0/Cognito/Supabase — viable peers; Firebase wins on RN SDK maturity + free tier + smallest integration surface.
- **Consequences.** Sign-in is configuration; the UID-keyed indirection is the designed exit from the provider.
- **Invalidating condition.** Pricing/lock-in pain at scale, or a compliance need to own credentials first-party.

### ADR-007 — Unfurler: in-process async worker; build Tier 1+2; buy as fallback
- **Status.** Accepted · 12/07/2026
- **Context.** Items arrive as links; metadata must be fetched server-side. Tiers: 1 = Open Graph/Twitter-card/title; 2 = JSON-LD (schema.org); 3 = per-site parsers (fragile, deferred).
- **Decision.** An async worker inside the monolith; Tier 1+2 built in-house; results cached by URL; graceful degradation to bare link always; items enrich asynchronously. Commercial unfurl APIs recorded as the buy-fallback.
- **Alternatives rejected.** Separate unfurler service — deployment overhead without load justification. Buy-first — Tier 1+2 is small, and the spike may show it suffices.
- **Consequences.** Zero partnership dependencies for v1; the same item pipeline later accepts webview capture (v1.5) and provider APIs (future).
- **Invalidating condition.** The register #8 spike (or production) showing heavy bot-blocking / thin coverage on must-have sites → buy-fallback behind the same interface, or targeted Tier 3 parsers.

### ADR-008 — API versioning: path-versioned /v1, additive-only within a version
- **Status.** Accepted · 12/07/2026 · **noted 23/08/2026** (S4.29 — two in-place changes to fields that never left `dev`)
- **Context.** Mobile clients cannot be force-updated; store review + user update lag means multiple app versions call the API concurrently for weeks.
- **Decision.** /v1 path prefix; strict additive-only evolution within it (new fields/endpoints only; clients tolerate unknown fields); /v2 only for a genuinely breaking reshape — expected never during alpha/beta.
- **Alternatives rejected.** Header versioning — invisible, easy to fumble in a mobile client. No versioning — no escape hatch for a true break.
- **Consequences.** Old app versions keep working; API evolution discipline is enforced at review.
- **Note (23/08/2026 — S4.29).** Reachability is part of the rule: two S4.29 changes looked like breaches of shipped fields and were not, because neither field has left `dev`. Recorded at the source — see Artifact 05 §*Versioning — ADR-008*.
- **Invalidating condition.** A domain-level reshape inexpressible additively → /v2 with a sunset window measured against real version-adoption telemetry.

### ADR-009 — Subscriptions: entitlement chokepoint at the register #14 split decision *(amended from "Epic 1")*; store billing (RevenueCat-class) at Epic 7
- **Status.** Accepted · 12/07/2026 · **amended 28/07/2026** (S1.8 grilling — the seam's ship moment moves from Epic 1 to register #14's decision)
- **Context.** The business model is subscription-based (two tiers: Free / Subscriber). Launch is free; charging during alpha would contaminate validation, and TestFlight subscriptions are sandbox-only. Apple/Google require their in-app purchase systems for digital subscriptions (15–30% platform cut).
- **Decision.** Build the seam now, the feature later: one entitlement service — can(traveler, capability) — ships in Epic 1 returning full access; every potentially-gated feature asks it. Epic 7 (post-validation, pre-beta) integrates store billing via a RevenueCat-class wrapper (products, purchase/restore, receipt validation, webhooks → entitlement state). Standing rule: the split gates capabilities, never a user's existing data.
- **Amendment (28/07/2026 — S1.8 parked at its grilling; owner call).** The "ships in Epic 1" clause is superseded. E1 reached S1.8 with register #14 undecided, and the owner refused mechanism-before-policy: a full-access seam has zero real callers, the shape S1.1's spec already rejected ("a seam with zero callers proves nothing"), and its acceptance criteria cannot be made falsifiable. **The seam now ships at register #14's decision moment** (unchanged: before Epic 7) — born wired to the first genuinely-gated capabilities, so it never exists without real callers and real policy. Until then: no entitlement code exists; the no-inline-tier-checks rule stands; and **every story spec from S1.9 on records a one-line candidate-capability note** — the acts that pass the **potentially-gated test** (a *capability*, not access to existing data · *grows the traveler's footprint* — creates entities or consumes a meterable resource · *not governance* — role-authority acts are membership semantics, not tier features). The retrofit sweep this ADR originally feared is answered by that accumulated map, not by early code. First two candidates, recorded at the grilling: `itinerary.create` (traveler-scoped) and `invitation.send` (workspace-scoped — the `context?` parameter's caller). **Added at S4.28 (22/08/2026):** `invitation.link` — issuing a trip's shareable join link. It passes the test on all three counts: it is a capability rather than a read of existing data, it grows the footprint (a link is the door through which unbounded strangers arrive), and it is not governance — *approving* a request is owner authority and stays out of the map, while *minting and sharing* the link is the metered act. Note the pair is deliberate: `invitation.send` meters the trip asking one named person, `invitation.link` meters the trip opening a door to anyone.
- **Alternatives rejected.** Billing at launch — contaminates validation and is sandbox-only anyway. No seam until Epic 7 — retrofitting gating across fifty stories *(amendment: mitigated by the candidate-capability map; the seam still precedes Epic 7)*. Stripe-only in-app — store rejection for digital subscriptions. *Added at the amendment:* shipping the seam bare in E1 — process theater satisfying this ADR's letter while abandoning its point; wiring two structurally-chosen test-load call sites in E1 — recommended at the grilling, declined by the owner as mechanism before policy.
- **Consequences.** Monetization becomes a two-way door: Epic 7 is pure addition behind an existing switch. Pricing must absorb the platform cut. *(Amendment: the switch itself now arrives with the split decision rather than years before it.)*
- **Invalidating condition.** A founder decision to charge during alpha (pulls Epic 7 into launch scope — revisit validation criteria with it), or a multi-tier model (the entitlement service grows from boolean to capability-set — the seam absorbs it). *Added at the amendment:* a pre-#14 story needing a real gate → that story ships the seam early, wired to its capability.

### ADR-010 — Platform sequencing & mobile build pipeline: Android-first; local builds, no EAS
- **Status.** Accepted · 13/07/2026 · partially supersedes ADR-004's build-workflow clause
- **Context.** Apple Developer overhead (US$99/yr + macOS toolchain) is real cost before validation; the RN/Expo single codebase makes sequencing a distribution decision, not architecture.
- **Decision.** Android first at launch; iOS activates once Android validates. Launch builds run locally (Expo prebuild + Gradle, signed AAB), uploaded manually to the Play Console; Play internal testing is the pre-release track. **EAS is the declared later adoption** — triggers: the iOS activation (local iOS builds need macOS the developer doesn't have; EAS is the recorded answer, no Mac purchase), or Android release cadence making manual builds a real cost.
- **Alternatives rejected.** Both platforms at launch — pays Apple's cost pre-validation. EAS — a paid cloud dependency the Android toolchain doesn't need.
- **Consequences.** The alpha cohort is Android-only (recruiting constraint in iOS-heavy markets, recorded). Sign in with Apple defers to the iOS phase.
- **Deferred decision at the iOS trigger.** Local iOS builds require macOS + Xcode — activating iOS means acquiring a Mac or reintroducing a cloud build service for iOS only.
- **Invalidating condition.** Validation showing the Android-only cohort is unrepresentative, or a moment requiring iOS presence → pull the activation forward and resolve the build path then.

### ADR-011 — The phased authorization guard: chokepoint in `common/authz`, membership lookup behind a resolver seam
- **Status.** Accepted · 16/07/2026 (S0.3 grilling) · extends ADR-003
- **Context.** ADR-003 fixed the pattern (guard resolves membership; service methods require the resolved `Membership`), but the first domain endpoint (S0.3) arrives before the Workspace exists — and the guard's future data owner (workspace) and first consumer (itinerary) would otherwise form a reference cycle.
- **Decision.** Guard + `Membership` value type live in `common/authz` with the permanent signature `requireMember(traveler, itineraryId) → Membership`; the lookup hides behind a one-method `MembershipResolver`. S0.3 ships an owner-based resolver; S1.1 replaces it with the workspace module's row-backed resolver and backfills workspaces for pre-E1 itineraries. The seam that must never be retrofitted is the signature and call-site discipline, not the storage. (`Membership` is not unforgeable — the guard defends against *forgetting*, not deliberate fabrication.)
- **Alternatives rejected.** Seeding the workspace module early — an unspecced module and an immediate cycle. Pulling S1.1's tables into S0.3 — re-litigates ratified scope. Guard calling `ItineraryService` — the swap lands inside the Full-rigor chokepoint, and `common` points at a module.
- **Consequences.** A forgotten check stays a compile error from the first domain endpoint; the S1.1 swap happened behind the seam without touching call sites.
- **Invalidating condition.** Workspace↔Itinerary ceasing to be 1:1, or a second aggregate needing guard semantics the itinerary-keyed signature can't express → widen additively, superseding this.

### ADR-012 — PaaS: Railway (one project, three environments, Singapore); custom domains as the exit hatch
- **Status.** Accepted · 16/07/2026 (S0.4 grilling)
- **Context.** Artifact 04 fixed the shape (PaaS + managed Postgres, three environments) but not the vendor. Solo operator, pre-validation cost sensitivity, Docker deploy, users/founders in Asia; operator already runs a structurally similar app on Railway.
- **Decision.** Railway: one project, `dev`/`preprod`/`prod` in Singapore, per-environment backend (Dockerfile) + own Postgres 18 (explicit image tag), branch-tracked deploys gated on green CI, platform probe = `GET /v1/health`. Custom domains from day one (`api[-env].largata.com`) so every baked URL is vendor-independent — leaving Railway is a DNS re-point.
- **Alternatives rejected.** Render — stronger managed-Postgres story but zero operator familiarity; snapshots + a verified restore cover the actual pre-validation risk. Fly.io / Cloud Run + Cloud SQL — heavier setup, ~3× always-on DB cost for nothing the alpha needs.
- **Consequences.** Familiar operations compound daily; the custom-domain seam is ADR-008's constraint applied to infrastructure.
- **Invalidating condition.** Real production data outgrowing snapshot-grade recovery (beta scale, ledger live) → PITR bar at post-validation hardening; sustained reliability pain → migrate along the domain seam.

### ADR-013 — Plans are day-indexed: Day + Activity structure; dates stay itinerary metadata
- **Status.** Accepted · 23/07/2026 (S1.3 grilling, founder-confirmed)
- **Context.** The original Itinerary Item carried a calendar date/time, making "Day 3" a projection of dates. The 07/18 mock plans by ordinal days (duration at create, day titles, empty days); itinerary dates are optional since S0.3; forking wants relative days — date-grouping collapses for undated plans and has no home for a day title or an empty day.
- **Decision.** The Itinerary aggregate gains a **Day** child (contiguous ordinal, optional title); **Activities** belong to a Day with manual sort order as the authoritative ordering (optional time-of-day is display metadata, local, timezone-free). Dates remain optional itinerary metadata; Day N's calendar date is derived, never stored. No span↔day-count invariant in MVP (S1.7 revisits). Entity noun becomes **Activity** (was Itinerary Item); `type`/`source` defer as columns to their first reader (E6/E4).
- **Alternatives rejected.** Date-anchored items — break for undated itineraries, hold no day titles or empty days, copy meaningless dates on fork. Dropping dates — ADR-008 forbids it and register #10 wants them.
- **Consequences.** `/v1` speaks `days`/`activities` permanently within v1 — accepted knowingly, even for E6's future unfurled hotels/flights. Ordinal contiguity is the aggregate's consistency job.
- **Invalidating condition.** Real demand for calendar-anchored planning (cross-timezone flights, calendar sync) → an optional per-activity datetime added additively beside the day structure.

### ADR-014 — MVP concurrency: single-writer itinerary edit lock (supersedes S1.3's last-write-wins)
- **Status.** Accepted · 24/07/2026 (S1.4 grilling, founder-ruled) · **amended 31/07/2026** (trip-surfaces reconciliation — subject-typed leases; ships at S4.9) · partially supersedes ADR-001 (plan writes leave the offline queue); ADR-008 waived for the S1.3 write endpoints, knowingly
- **Context.** S1.3 shipped last-write-wins with attribution; AC 7 pinned the absence of any conflict surface. Founder ruling 2026-07-24 after challenge: silent overwrites are unacceptable for MVP; live editing is the declared future, this lock its stopgap.
- **Decision.** Whole-itinerary lease lock: one row (holder + expires_at), acquired on entering any plan-edit surface, TTL ~3 min auto-renewed while editing, released on save/cancel, expiry self-heals abandonment. No force-take (owner included). Server-enforced on every plan write (membership guard first, then lease); the client modal is a response to a failed acquire, never a broadcast (pull-based clients).
- **Amendment (31/07/2026 — trip-surfaces reconciliation, founder-ruled; ships at S4.9).** The lease becomes **subject-typed** — `header | day | activity` — same per-row semantics: the activity lease guards an activity's edits and deletion; the day lease guards the day's title and deletion (never its activities); the header lease guards the itinerary fields. Adds are unguarded (they commute); add/delete **day** is owner-only *interim* (revisit: validation gate; ADR-008 waiver renewed); delete-day 409s while a contained activity is leased by another member; **reorder is version-checked** (stale → 409, never silently overwritten); the lease gains an additive, pull-based read surface for the advisory "being edited by" indicator — never presence, and the modal stays the enforcement. Supersedes both the whole-itinerary scope and this ADR's per-item-locks rejection, answering the recorded "partial protection" objection structurally. Full text in `04-architecture.md`.
- **Alternatives rejected.** Keeping LWW — rejected by founder ruling on the merits. Per-item locks — more bookkeeping, partial protection. Live editing now — presence/sync infrastructure the alpha doesn't test.
- **Consequences.** Offline plan-editing disabled (read-only offline); shipped /v1 write endpoints gain a rejection case (additivity waived while clients are founders-only); S1.3's AC-7 IT deliberately replaced; editing serializes per itinerary.
- **Invalidating condition.** Validation-gate evidence that serialization hurts collaboration, or live editing arriving → the live-editing backlog line supersedes this wholesale.

### ADR-017 — Publish: a binary visibility flip with a live rule-scrubbed projection; the audience ladder
- **Status.** Accepted · 31/07/2026 (S4.1 grilling, founder-ruled) · resolves register #11 · re-rules S1.9's archive sight and S1.3's `notes` semantics (ADR-008 waivers renewed) · retires `completed` as a gate
- **Context.** Register #11 accumulated snapshot-vs-transition, publish-from-creation (proposed twice), est-vs-actual, and the 2026-07-29 safety constraint: a published itinerary must not reveal that its traveler is currently away from home — binding the whole projection.
- **Decision.** Publish flips a binary `private → published` visibility fact on the one itinerary, orthogonal to the dormant lifecycle; the public surface is a live projection scrubbed by rule (INV-2 amended), never a copy. No lifecycle gate; owner-only; symmetric unpublish (hidden-not-deleted; forks survive). The absence rule: no absolute dates, lifecycle state, or stamps ever cross — duration derives from day count. The audience ladder: archived = owner only · private = owner + collaborators · published = everyone; archive dominates publish, unarchive restores the prior audience. Unlisted deleted; `friends_only` reserved additively for the friend graph.
- **Alternatives rejected.** Snapshot-publish — kills the live-derived cost, mints a second identity, makes publish side-effectful. Two modes — double semantics, no consumer. A `completed` gate — resurrects removed UI, can't classify dateless trips. Date opt-in — a consent surface for a fact with no consumer.
- **Consequences.** Publish stays side-effect-free (S1.7's race exemption holds); post-publish edits are instantly public (reviews-vs-moving-target recorded for S4.5); members lose sight of archived trips; empty publishes accepted; the dormant lifecycle ships untouched.
- **Invalidating condition.** Trust abuse of live-updating published plans → freeze/versioning additively; the friend graph → `friends_only`; the web read-only surface → the same projection serves accountless reach.
- **Amendment — the mask extends to writes** *(13/08/2026, S4.23 grilling, founder-ruled)*. The audience ladder's archived rung binds every door, not only reads: a non-owner member's **write** to an archived trip answers the same not-found mask as their read, and on that trip the mask answers **before** any finer permission refusal — a mask with a louder door beside it is no mask. The owner's writes keep the honest archived refusal (the trip legitimately exists for them); self-leave stays open (S1.9's rule); acts closed by archive-time voiding (offer/invite acceptance) keep their existing answers. Supersedes the write fence's pre-ADR-017 member posture ("an archived trip tells a member it is frozen"), which encoded the sight rules this ADR ended. ADR-008 waiver renewed on the standing founders-own-clients ground.

### ADR-018 — Publication status is one three-valued fact, and publishing freezes the plan *(supersedes ADR-017's decisions 1, 2, 5 and 12)*
- **Status.** Accepted · 01/08/2026 (founder, on sight of the shipped S4.1 build; confirmed and clarified 03/08/2026) · **built** — supersedes ADR-017 decisions 1, 2, 5 and 12. ADR-008 waived on the record for the wire break, the third time in this story, on the standing ground that the installed clients are the founders. own.
- **Context.** S4.1 shipped ADR-017's model — binary `private ⇄ published`, a live projection, post-publish edits flowing straight to the public page. Looking at the running app, the founder re-drew it: *"public and private are both published, public being the default. draft will be the status when you are still working on the itinerary… you cannot edit a published itinerary."*
- **Decision.** One three-valued publication status replaces the binary visibility fact: **`draft`** (traveler + collaborators, **editable**) · **`private`** (published, traveler + collaborators, **frozen**) · **`public`** (published, every onboarded traveler, **frozen**, and the default on publish). Transitions: `draft --publish--> public|private`, `public ⇄ private` while published, and **`unpublish` returns the itinerary to `draft`**, which is the only way back to editing. The freeze covers **the plan only** — title, destinations, description, Standouts, best time, days, activities — while membership acts (invite, remove, ownership transfer, archive) keep working, mirroring the archive fence's existing "acts on the plan freeze, acts on the relationship do not".
- **What it reverses.** ADR-017 decision 1 (*"post-publish plan edits flow to the public page; no versioning, no freeze"*) — publishing is now a freeze. Decision 2's vocabulary — **`private` changes meaning**, from *not published* to *published, restricted*, and `published` as a wire value is replaced by `public`. Decision 5 — unpublish no longer returns to a private-but-unpublished state; it returns to draft. Decision 12's ladder re-derives on three values plus archived.
- **Consequences, including the ones to weigh before building.** *(a)* Fixing a typo on a public itinerary takes the page **down** — a stranger holding the link gets not-found, and stars/comments/reviews hide with it (decision 5's hidden-not-deleted) — until it is republished. *(b)* Conversely, ADR-017's recorded reviews-vs-moving-target worry for S4.5 **dissolves**: a review can only ever land on a plan that cannot change under it. *(c)* The derived Est. Total can no longer drift while published. *(d)* `friends_only` (reserved for the friend graph) now overlaps conceptually with the new `private` — the friend graph story must say what the third tier adds. *(e)* The Trips chips' accepted Draft/Private overlap **disappears**: three mutually exclusive values need no overlap rule. *(f)* This is a **wire break, not an additive change** — `private` changes meaning and `published` is replaced — so it needs the same ADR-008 waiver S4.1 has already renewed twice, defensible only while the installed clients are the founders' own.
- **Naming, resolved 01/08/2026.** Publication status ships as a **new field `status`** (`draft | private | public`); the dormant lifecycle keeps `state` and stays invisible, so the two "draft"s never meet. `visibility` retires with the wire break. *(Was recorded as the open question blocking a build.)*
- **Invalidating condition.** A traveler who needs to correct a live itinerary without taking it down → the draft-changes/publish-update flow ADR-017 rejected as versioning, reconsidered with a real reader.

### ADR-022 — The Trip Workspace model: one home surface, one exclusive Draft Workspace, and the lifecycle presented as a soft lock
- **Status.** Accepted · 08/08/2026 (S4.17 grilling, founder-ruled) · supersedes ADR-014's 31/07 subject-typed amendment for plan editing (restores the original whole-itinerary scope, reshaped as a session) · a presentation layer over ADR-019/020 (both untouched) · resolves the epic map's parked "three surfaces over one plan" question · **decision (3)'s saving semantics superseded by ADR-023 (10/08/2026)** — edits now buffer and Save Changes commits; the two surfaces and the exclusive session stand · **decision (2)'s soft lock superseded by ADR-027 (15/08/2026)** — Edit Itinerary now edits in place in every unpublished state, and the editor renames to Itinerary Workspace
- **Context.** Three surfaces grew over one plan — the workspace overview (`[id]/index`), the planner (`days/index`), and the read-only day view (`days/[dayId]`) — and the parked question asked which should win. The founder brought the workspace mock set (2026-08-08, two frames of the draft editor, a finalize sheet, a finalized viewer, add/edit activity, plus parked poll frames): a single home screen per trip and a single editing screen behind Edit Itinerary. Separately: live collaborative sync does not exist, so the subject-typed leases permit simultaneous editing that neither party can see happening.
- **Decision.** (1) **Two surfaces replace three.** The **Trip Workspace** (viewer) is every own unpublished trip's opening screen in every lifecycle state — read-only presentation, the lifecycle ladder as its CTA rail (Finalize in the editor · Start Trip · Complete Trip · Publish routing into the existing publish flow), a quiet one-step "Step back", and the shared tab row. The **Draft Workspace** (editor, behind **Edit Itinerary**) owns all plan editing via the day-by-day accordion. Published trips keep their published view; archived shows the viewer with the unarchive banner. (2) **The lifecycle presents as a soft lock.** Ready and beyond render read-only; Edit Itinerary on a Ready trip fires `reopen` and enters the editor in one act. The hard freeze remains `published`'s alone — the domain rule of ADR-019/020 is untouched; this is presentation. (3) **The Editing Session.** Edit Itinerary acquires an exclusive whole-itinerary hold (an additive lease subject); other members see "being edited by X" with Edit Itinerary disabled; **Save Changes** ends the session and returns to the viewer — it persists nothing, since every edit already saved per action; back-exit and the TTL self-heal abandonment.
- **Alternatives rejected.** Keeping the subject-typed leases for the workspace — built and server-enforced, but without live sync two members editing different parts is blind co-editing; the founder ruled the exclusive session honest ("live editing for collaborators is not implemented here"). Cutting Save Changes — rejected; the founder kept it as the session's explicit end. Stubbing Complete/Publish on the new viewer — rejected: both are shipped acts, and the surfaces that carried them are being retired, so stubbing would regress live features.
- **Consequences.** The planner, day-view and old-overview routes retire (their references migrate: S4.15's greyed CTA, publish-success's back link, the preview's published-state button). The workspace is single-writer while a session is held — an abandoned session blocks everyone until the TTL clears it, accepted knowingly. The activity form culls Description / Creator Tips / Photos / Move-to-day (wire fields stay additive; the orphaned-capability consequences live on the epic-map backlog). Drag-to-reorder un-parks (the arrows graduate; the version-checked PUT was built for this). Ongoing/completed badges and Step back ship as named deviations — those states have no mock frames.
- **Invalidating condition.** Live editing arriving (ADR-014's own condition) → sessions dissolve into presence and the exclusive hold goes; or validation-gate evidence that exclusivity blocks real collaboration → the subject-typed leases return from the shelf.

### ADR-023 — Plan edits buffer in the Editing Session; Save Changes commits via one version-checked bulk save *(supersedes ADR-022 decision 3's saving semantics; the surfaces and the session stand)*
- **Status.** Accepted · 10/08/2026 (S4.18 grilling, founder-ruled) · reverses ADR-022's *"Save Changes persists nothing"* on the founder's defect report from the running S4.17 build; ADR-014's lost-update settlement re-answered at the wider window buffering opens
- **Context.** ADR-022 kept per-action persistence and made Save Changes the session's end — a button whose label promises gating it does not do. The founder reordered activities, pressed back without saving, and found the change already persisted: leaving without pressing Save reads as discarding when it is not. Two fixes were weighed openly — relabel to `Done` (cheap, honest, keeps per-action crash-safety) or buffer for real — and the founder chose buffering. Also at decision time: the app holds no local persistence of any kind, and activity-photo upload is already dead UI (the S4.17 cull), so neither a crash-surviving draft nor a photo-staging exception had existing machinery to lean on.
- **Decision.** (1) **Edits stage; the server sees nothing until Save Changes.** The seven plan ops (append/rename/delete day, create/edit/delete activity, reorder) mutate a local draft of the plan — a value, not an op log — initialized when the session opens. The activity form stages into the same draft across its navigation. (2) **One transactional bulk save.** `PUT /v1/itineraries/{id}/plan` replaces the plan document wholesale, reconciled by id, holder-only, all-or-nothing; Save Changes = commit + release + return to the viewer. Back-exit confirms, then discards. (3) **The save is version-checked, never last-write-wins by default.** A `planVersion` bumped by every plan-document write — the bulk save and the still-live per-action endpoints old clients use — rides the request; a stale base refuses with a named code, and the refusal offers two explicit choices: discard-and-reload, or an overwrite that re-submits against the current version (explicit, attributed, race-safe — one endpoint semantic, no force flag). (4) **Crash loss is accepted.** Process death costs the buffer; the mitigation (a persisted draft) is parked with a trigger rather than built. (5) **History is derived by diff.** The server diffs committed vs staged plan at save and emits the same typed entries per-action capture wrote, attributed to the saver; staged-then-undone churn never becomes history.
- **Alternatives rejected.** Relabeling to `Done` — honest about the wrong thing: the founder wants the promise kept, not corrected. Last-write-wins — reopens the wound ADR-014 closed, in a wider window. A client-shipped op log for history — the server should derive history from state it can verify, not from a client's narration. Local draft persistence — the app's first storage layer plus a reconciliation model, smuggled into a labeling fix. Staging photos — the pending-media state machine ADR-021 already rejected, for a surface that currently has no UI.
- **Consequences.** Other members read the last-*saved* plan for the whole session — a longer stale window, accepted knowingly (the advisory "being edited by" already covers it). A crash loses a session's work where per-action saving lost nothing — accepted, parked mitigation. The per-drop stale-reorder retry machinery retires; its version check graduates to the whole plan. The per-action endpoints stay live under ADR-008 and bump `planVersion`, so old and new clients coexist honestly. S4.10 inherits diff-derived history — capture cannot be backfilled, so this granularity decision is permanent for entries written from here on.
- **Invalidating condition.** Live editing arriving (the condition ADR-014 and ADR-022 already share) → the buffer dissolves with the session into presence + sync. Real reports of crash-lost work → the persisted-draft line un-parks. Travelers repeatedly hitting the stale-save refusal → the exclusivity/TTL balance gets revisited before any merge UI does.

### ADR-024 — The Diary is a per-traveler postcard stream derived from activities *(the shared-album model retires; INV-2a and INV-5 amended)*
- **Status.** Accepted · 11/08/2026 (S3.1/S3.4 grilling, founder-ruled) · reverses the 00-brief's "Diary is a first-class object — the shared-album model" and canon's contributor-grant mechanics · register #13 re-pointed, not resolved
- **Context.** Canon defined Diary as a shared album: one author-owner, contributors joining by the owner's consent (INV-2a), entries accreting, published as a unit. The founder's 08/11 mock and his own definition described a different object — *"a personal post, like a postcard, derived from an activity of an itinerary; the owner of the diary is the traveler"* — with no contributor concept anywhere in it. The two could not both be the domain model, and the story that builds diaries (S3.1, re-cut from an S4.2 ask at this grilling) needed the answer first.
- **Decision.** (1) **Diary** = one traveler's collection for one trip; **Diary Entry** = one activity-derived post (a postcard: 1–5 photos + optional caption). (2) **Contributor grants are deleted** — INV-2a narrows to *a diary has exactly one author; only the author writes*. INV-5 becomes: every entry belongs to one traveler's diary for one itinerary and derives from at most one activity, whose title/day/time it **snapshots at post time** (provenance nullable — plan edits never rewrite a postcard). (3) "One itinerary → many diaries" survives as **one per traveler**. (4) **No diary table** — the Diary is a projection over entries (the Gallery/Highlight precedent); diary-level state arrives additively at its first reader (S4.2's publish). (6) The shared-album *need* is partly re-homed: the **Photo Dump** (S3.4) is the member-shared pool; a dump photo selected into an entry is **copied**, so dump deletion never reaches a diary — and the consent question that stores up (another member's photo living on in my diary) is a recorded must-answer for S4.2 before any diary is visible beyond its author.
- **Alternatives rejected.** Keeping the shared album — nothing in the founder's product needs co-authored diaries (the group's shared thing is the dump; the diary is the *personal* perspective, and "independent lived perspectives on the same plan" gets stronger with one per traveler). A global profile stream with trip tags — makes Highlights a filter query and trip-grouping an afterthought; the per-trip collection keeps S4.2 a coherent projection. Live-linking entries to activities — an edit made for unrelated reasons silently destroys a traveler's memory (the append-only-ledger reasoning, applied to memories). Minting the diary table now — a row with no reader, the mechanism-before-reader shape this repo refuses by default.

S3.1 re-scopes to the capture story; S4.2 stays parked behind diary-publish and inherits the consent must-answer plus register #13. E3's line re-reads accordingly; the day-execution machine the mock drew around the capture links is backlogged separately. Media: a diary-entry photo kind with an author-only audience; entries own their bytes.
- **Invalidating condition.** A real demand for co-authored trip records → revisit as a *new* surface over the dump + entries, not by resurrecting grants. S4.2 finding diary-level publish needs state → the diary table arrives there, additively, as designed.

### ADR-025 — Postcards share individually to a public home feed *(per-entry opt-in; dump-implies-consent; independent of trip publish; the absence rule re-grounded on consent — INV-2a amended, register #13 re-pointed again)*
- **Status.** Accepted · 12/08/2026 (S4.22 grilling, founder-ruled; decision 2 reversed by the founder at spec review the same day, on the record) · discharges S3.1 decision 6's dump-photo consent must-answer for the *public* widening · supersedes the parked S4.2 shape ("published diaries on published itineraries") as the publicness primitive — S4.2 keeps Highlights, re-pointed onto this mechanism.
- **Context.** The Home tab has been a dead stub since S4.13, and diary entries have no visibility state at all — author-only structurally (ADR-024), with every widening reserved for the story that owns it. Canon's parked trajectory for diary publicness was diary-level publish gated on the published trip (S4.2 / register #13) — but publish requires `completed` (ADR-019/020), so a feed built on that shape could never show a trip being lived, and the founder's home-feed mock is unambiguous that it must ("Day 3 · 2h ago"). Separately, S3.1 recorded a must-answer before any diary is visible beyond its author: a postcard can contain photos *other members* dumped into the trip's shared pool.
- **Decision.** (1) **The share is per-entry**: a diary entry gains a `shared` state plus its instant — the author's sole act (INV-2a), default private, symmetric (unshare hides on next fetch, never tombstones; delete removes). (2) **Dump-implies-consent**: contributing a photo to the trip's Photo Dump consents to co-travelers using it in their postcards, shared ones included — the dump exists so members build their diaries from it, and the entry's copy belongs to the entry's author outright. The share reads nothing about a photo's origin: no provenance, no refusal, no consent machinery. The dump surface itself stays member-only. *(First ruled the opposite — own-photos-only — at the grilling; the founder reversed at spec review with the t1/t2 public-share case stated explicitly, both costs on the table: tightening later retro-blocks shipped postcards, and a contributor's control ends at the copy, leaving report/moderation as their only recourse.)* (3) **Independent of trip publish and lifecycle**: sharing is legal wherever the entry is (entries already require `ongoing`/`completed`); the trip's three axes are read, never moved. The card exposes the author, trip name, snapshot day label + activity title, caption, photos, and time-since-shared — never roster, absolute dates, lifecycle, or plan content; the link to the published itinerary activates only once it exists. (4) **Audience = any signed-in traveler**, by the S4.1 guard-bypass scrubbed-projection pattern; the diary-entry media audience widens to any authenticated traveler *for shared entries only*. Unauthenticated web stays backlogged. (5) **The feed is a global firehose ordered by shared-time** (retro-shares surface at the top); the friend graph, when it ships, narrows `public` per its standing backlog line. (6) **The absence rule is re-grounded, not excepted**: INV-2 forbids the *plan's projection* from revealing absence because that exposure is involuntary; a shared postcard is the author's own deliberate broadcast, and it identifies no one but its consenting author — no public surface carries the roster. Recency is therefore legal on the shared postcard and stays forbidden on the published itinerary.
- **Alternatives rejected.** Diary-level publish on published trips (the parked S4.2 shape) as the primitive — coarser consent than the act warrants, and structurally post-trip-only: a feed whose newest item is a finished trip has no pulse. Own-photos-only — the grilling's first answer, reversed at spec review: it makes the dump's core loop (build your diary from the pool) second-class the moment a diary is shared, and it demands origin provenance the copy path never kept (verified at spec time: the copy stamps the author, and legacy rows are indeterminate). Per-photo contributor consent — machinery before any evidence of need. A follow-scoped feed — assumes a graph that is deliberately post-validation; at current scale the firehose *is* the product. Requiring the trip published for the link's sake — inverts the dependency: the line un-tints until publish and self-heals.
- **Consequences.** The Home stub becomes the feed and Home becomes the landing route (Trips one tab over; Discover stays greyed for S4.3). S4.2 re-points: per-entry sharing is the primitive, diary-level publish becomes optional sugar over it, Highlights consumes shared entries; its inherited consent must-answer is discharged by decision 2's implied consent. Two backlog lines mint: the unpublished-trip teaser projection (a scrubbed landing for feed links before publish) and moderation/report — this is the app's first strangers-see-strangers surface *and* the dump contributor's only recourse after the copy, so the line is pulled forward on first incident. The Photo Dump surface owes one info line at its next touch (dumped photos may appear in co-travelers' shared postcards), keeping the implied consent honest at the point of contribution. Engagement chrome (likes/comments/save/search/bell) ships as S4.21-pattern stubs behind the one kill-switch; their real backends are separate stories. The feed's follow-flavoured empty-state copy deviates from the mock until the graph exists.
- **Invalidating condition.** The friend graph shipping → the feed narrows with `public` (backlog §106) and the terminal-card copy reverts toward the mock. A contributor complaint about a dumped photo's public life or any moderation incident → the report line pulls immediately; revisiting the consent model itself takes a new ADR and a migration story, because tightening retro-blocks postcards already shared — the cost decision 2 accepted. S4.3's discovery feed arriving → the browse role may re-home there; the postcard feed stays the recency surface.
- **AMENDED 13/08/2026, at S4.22's close, before the merge — decision 1 is reversed: there is no per-entry opt-in. Posting a diary entry publishes it.** *(Founder: "all diaries entries, if public are automatically in the homefeed. they default to public. revert that share button to what it was before, it was supposed to be a share diary entry you can send to someone… i dont know if there is already mechanism for private and public diaries but as far as i know it is not yet implemented, only for trips.")* **What changes:** `shared_at` is stamped at birth by the entity's constructor, so no caller can post an entry that is not public; the share/unshare endpoints, the request's `shareToFeed` field, the composer toggle and the preview's globe control are all **deleted**, cut deliberately *before* the merge because ADR-008 freezes /v1 the moment this ships and an endpoint re-added later could never be removed. `PostcardPreview`'s Share reverts to the send-this-to-someone stub it was on `dev` — which is what the founder's "revert that share button" names. **V30 backfills every pre-existing row from `created_at`**, not `now()`: a row left NULL would be permanently invisible with no UI able to surface it, and stamping the migration's clock would file last month's trip at the top of the feed claiming a moment that never happened. That backfill is irreversible and was taken on the standing ground that the installed base is the founders' own. **What survives unchanged:** decision 2 (dump-implies-consent) — the pinned IT still guards it; decisions 3, 4 and 5 entirely; and **decision 6's re-grounding of the absence rule, whose load-bearing clause holds with one word swapped** — the deliberate act is now *posting* rather than *sharing*, and a postcard still identifies no one but its author, so recency stays legal here and forbidden on the published itinerary. **What is parked rather than deleted:** the column keeps its nullability, because the friend graph — or any later per-entry control — re-enters through it. **The cost, stated:** a traveler's only retraction is now delete. There is no "post but keep this one back", and the composer says so plainly before the first postcard rather than after.
- **AMENDED AGAIN 13/08/2026 — archiving a trip takes its postcards off the feed with it, which restores the bulk retraction the reversal removed.** *(Founder ruling, on being shown that 117 shared postcards on archived trips were still public.)* **What was wrong:** the feed was half archive-aware — `navigableTripOf` already withheld the *link* for an archived trip while the *card itself* stayed on Home, so the product had two answers to one question. That is an inconsistency rather than a principle, and it was found only because a seeder's re-runs archived their previous trips and the postcards accumulated in plain sight. **What changes:** the projection excludes any entry whose trip is archived, so the card leaves the feed and the trip's public diary answers **404** — one filter in `PostcardFeedService.project`, so the feed and the per-trip diary cannot disagree. The lookup is **batched** (`WorkspaceService.archivedAmong`) rather than asked per entry, and the query stays on the workspace module's own service, never a join into its tables (ADR-002). **Why this and not the other direction:** decision 1's reversal deleted unshare, leaving delete — per-entry and permanent — as the only way out. Archive is the gesture a traveler already reaches for to put a whole trip away, it is **reversible** (unarchive returns the postcards, pinned by a test), and the link half already behaved this way. **The counter-argument, on the record:** archive is a *workspace* concern and a postcard is the author's deliberate broadcast, so one could equally have made the link stop being archive-aware. That reading was heard and declined — a bulk, reversible retraction is worth more to a traveler than the purity of the module boundary, especially with no trip-delete endpoint anywhere in the API. **Consequence to know:** a feed page may now return fewer cards than its limit, because the filter runs after the page is read. Pagination is unaffected — the cursor is taken from the last row *read*, not the last card *kept*.
- **AMENDED 04/09/2026 (S4.39's grilling — ADR-034): "every entry is public the moment it is posted" now reads "public to the audience the author's Profile Visibility admits".** The entry still has no state, toggle or unshare, and `shared_at` is untouched; the fact lives on the author — every signed-in traveler for a public profile, the author and their approved followers for a private one. Decision 2 (dump-implies-consent) is untouched. Diary-level publish (S4.2's sugar) is retired rather than re-pointed.

### ADR-019 — Lifecycle, discovery and visibility are three independent axes *(supersedes ADR-018's single-column shape; reinstates the `completed` gate ADR-017 retired)*
- **Status.** Accepted · 03/08/2026 (founder, two days after ADR-018, on the same running build) · ADR-008 waived on the record for the wire break, the fourth time in this story, on the standing ground that the installed clients are the founders' own.
- **Context.** ADR-018 fused two questions into one mutually-exclusive value: *is it in the feed?* and *who may read it?* The founder re-drew the model as three separate facts — *"an itinerary has 3 states, draft, active, complete… 2 states for the discovery feed, published and unpublished… 2 states with regards to the social feed. public and private."* Under that reading `status` cannot hold them: an itinerary is simultaneously somewhere in its life, in or out of the feed, and open or restricted.
- **Decision.** Three orthogonal axes on the one itinerary. **Lifecycle** `state` — `draft → active → complete`, traveler-driven (no date derivation), forward with a **one-step undo**; this is V12's dormant enum reactivated, not a new concept. **Discovery** `published` — boolean; governs the feed **and the freeze**. **Visibility** `visibility` — `public | private`; governs who may read, independent of the feed. Publishing **requires `complete`** and defaults to `public`; unpublish thaws and frees the lifecycle. While published the lifecycle is **pinned** — to move it, unpublish first.
- **What it reverses.** *ADR-018's shape, not its reasoning*: the naming argument (two unrelated "draft"s must not share a column) is **upheld and is why this works** — `state` keeps lifecycle, the other two axes take their own columns, and `status` retires after two days. **ADR-017 decision 1's lifecycle position reverses**: the epic map recorded *"publish gates on nothing; `completed` is retired as a gate"* — it is reinstated, and the "can't classify dateless trips" objection dissolves because the transition is a button, not a date. ADR-018's `private`/`public` stop being *publication* values and become *visibility* values, orthogonal to the feed.
- **Why the gate is the load-bearing choice.** It prunes 6 combinations to 5 and removes the frozen-draft: a plan can only freeze once the trip is over. That re-grounds the freeze — ADR-018 justified it as *"nobody reads a trip that changes under them"*; here it is *"a completed trip is a record of what happened"*, which is a rule a traveler can infer from one line of UI rather than being taught.
- **Consequences, including the ones to weigh.** *(a)* **Published + private is legal**: an entry in the feed that only the owner and collaborators may open — the feed must filter per-viewer, and a traveler who publishes privately gets a frozen plan with no public page. Accepted knowingly as the price of orthogonality. *(b)* **Publishing is now two steps** — mark complete, then publish — where ADR-017/018 allowed it from creation; the preview CTA must explain the precondition rather than merely hiding. *(c)* The lifecycle UI removed at the E1 promotion gate (epic map: *"the mobile surface comes out"*) **comes back**, which is why the endpoints were kept dormant rather than deleted — that call now pays. *(d)* `friends_only` re-collides: with visibility already split out, the friend graph narrows `public` rather than adding a tier. *(e)* Every existing row needs a lifecycle value; none has ever been completed, so all land on `draft` — meaning **every currently-published itinerary migrates to a state that could not have published it**, tolerated as a one-off since the installed base is the founders'.
- **Invalidating condition.** Travelers publishing plans *before* travelling (a use the gate forbids) → the gate loosens to `active`, or retires again with the freeze re-anchored. Dates becoming mandatory → lifecycle derivation reconsidered, its objection having been about dateless trips.
- **Amendment (26/08/2026, S4.37's grilling — founder-ruled).** Consequence *(d)* anticipated that the friend graph would narrow `public`; the follow story resolved it the other way. **Follow ships as a pure social edge**: an asymmetric, open, approval-free relation that grants no access and narrows no visibility — `public` keeps meaning every onboarded traveler. The ground: every surface built on ADR-019 since (Discover, the Home feed, public profiles, People search) is a public-square product, and narrowing `public` to a barely-populated graph would hollow out the exact surfaces the follow story exists to energize. Whether any graph ever narrows `public` — which under an asymmetric edge would first need "friends" *defined*, presumably as mutual follows — is **re-parked on the epic map with its own trigger** (a real privacy ask, or friends-only demand at the validation gate). The axes, the gate and the freeze are untouched.
- **Re-amended (04/09/2026, S4.39's grilling — ADR-034).** The third axis is retired: an itinerary carries lifecycle `state` and `published` only, and a published itinerary is readable by every signed-in traveler. Consequence *(d)* is settled a second time, the other way round for private profiles: **follow is an authority when — and only when — the followed profile is private**, through an approved Follow Request; public profiles keep the 26/08 reading. The gate on `completed` and the freeze are untouched. Consequence *(a)*'s "published + private" no longer exists; rows in that state were unpublished by S4.39's migration, not exposed.

### ADR-020 — The lifecycle is four states: `draft → upcoming → ongoing → completed` *(amends ADR-019's ladder; upholds its axes, gate and freeze)*
- **Status.** Accepted · 04/08/2026 (founder, at the create-itinerary-flow grilling against the final Figma frames) · ADR-008 waived on the record for the `active → ongoing` wire rename, the fifth time in this story family, on the standing ground that the installed clients are the founders' own.
- **Context.** ADR-019's three-state ladder fused two facts into `active`: *planning is finished* and *the trip is being lived*. The creation flow's final frames needed a terminal act, and the only honest one — "I am done planning" — had no state to land on: `draft` denies it, `active` overclaims it, and `completed` asserts a trip that never happened (the exact falsehood V20's migration refused to write). The founder re-drew the ladder with the missing rung: *"draft (planning) → upcoming (planning finished) → ongoing (currently doing the trip) → completed (trip completed)."*
- **Decision.** Four lifecycle states on the one `state` axis: **`draft`** (planning) → **`upcoming`** (planning finished, trip not started — the creation flow's terminal CTA, **"Finish Planning"**, lands here) → **`ongoing`** (the trip is being lived; renames ADR-019's `active`) → **`completed`** (the trip happened). **Every transition is the traveler's tap** — dates never flip state; a date-holding trip may *nudge*, never act. **One-step undo runs down the whole ladder** (`completed → ongoing`, `ongoing → upcoming`, `upcoming → draft` — the last is "reopen planning"); two-step jumps stay refused. **The publish gate stays at `completed`** and **the freeze stays solely on `published`** — no lifecycle state ever locks the plan: `upcoming` stays editable (or "Finish Planning" becomes a trap travelers learn to avoid) and unpublished `completed` stays editable (completion is when the record gets corrected; the freeze's ground is *readers*, and readers arrive at publish). Birth is not a transition: creation bears `draft`; a `completed`-at-birth door ("Add a Past Trip") is parked, unbuilt, pending its argument.
- **Alternatives rejected.** Naming the terminal CTA "Complete Itinerary" — puts one word on two facts (done-planning vs trip-happened), the exact collision ADR-018's upheld naming argument forbids. Date-derived transitions — dateless trips stall forever (the objection that killed derivation twice), and an auto-flipped `completed` turns the publish gate's grounding assertion into an automation. Freezing at `upcoming` or `completed` — locks plans with no readers and re-mints the frozen-not-yet-happened plan ADR-019 removed.
- **Consequences.** *(a)* `upcoming` is a new wire value and `active → ongoing` is a rename — one waiver covers both. *(b)* Existing rows: `draft`/`completed` keep their values; any `active` row becomes `ongoing` (none exist beyond seeds). *(c)* The Trips surface renders the lifecycle as four sections (Ongoing · Upcoming · Draft · Completed, empty hidden), superseding S4.11's chips; S4.11 decision 7's published/private row badges are **deferred, not deleted** (epic-map backlog). *(d)* The publish-success chrome re-homes from creation's end to the publish act, where its every line is true. *(e)* `WriteFence` ships unchanged.
- **Invalidating condition.** Travelers not tapping — trips rotting at `upcoming`/`ongoing` while the feed starves → revisit the nudge's strength before revisiting derivation. The parked past-trip door winning its argument → birth-state parameter (`draft | completed`), which this ADR already shaped for.

### ADR-021 — Media: Railway Buckets (Asia-conditional, R2 fallback); backend-URL serving through the audience ladder; strip-and-re-encode at ingest
- **Status.** Accepted · 06/08/2026 (S3.3 grilling, founder-ruled) · wires ADR-002's day-one "S3-class object storage" decision
- **Context.** S3.3 activates four promised surfaces (avatar, cover, activity photos, gallery). The cover/avatar wire fields are URL strings shipped writer-less (ADR-008). Facts at decision time: Railway launched native Buckets (Sept 2025 — S3-compatible subset, presigned support, free bucket egress, price-matches R2, **no public buckets, region list unpublished, never labeled GA**); Railway bills a *service's* own egress at $0.05/GB both directions; B2 has no APAC region; S3 Singapore egress is ~8× the field; `largata.com` DNS already sits on Cloudflare; MinIO community edition is EOL'd in 2026.
- **Decision.** *(1) Store:* one bucket per environment on **Railway Buckets, conditional on an Asia region being offered at creation — else Cloudflare R2 with the `apac` hint**, a recorded fallback executed without a new decision. *(2) Serving:* stored media URLs are **always backend URLs** (`/v1/media/{id}`, `/thumb`); the endpoint enforces the audience at read time (avatar → any authenticated traveler; itinerary media → the itinerary's audience ladder, archived = owner-only, masked as 404; no token → 401). Proxy streaming first; a presigned-redirect flip is the recorded optimization — one endpoint change, invisible to stored URLs. **No provider hostname is ever stored** — the ADR-012 exit-hatch discipline applied to media. *(3) Ingest:* multipart through the backend, upload+attach one act, authority checked at the surface (header lease / activity lease / self); every upload is re-encoded — metadata stripped (INV-11), orientation normalized, bytes proven an image — into two variants (display ≤2048px, thumb ≤400px), the original discarded; caps server-enforced (cover 1 · avatar 1 · 5 per activity · 10 MB/file).
- **Alternatives rejected.** B2 — no APAC, every read crosses an ocean. S3 — egress-priced serving for a photo product. Presigned client-direct upload — the INV-11 strip must sit in the write path, and it buys bucket CORS + a pending-media state machine to save fractions of a cent. Public buckets/CDN — Railway lacks them; R2's require a custom domain and split hostnames; a guard-enforcing proxy is one endpoint at alpha scale. Storing provider/presigned URLs — an expiring URL in a TEXT column is a lie, and a provider hostname in every row welds the exit shut. Keeping originals — the only copy that ever held EXIF, with no reader.
- **Consequences.** The backend is the bucket's only client — no CORS, no second vendor account (if Railway), one dashboard. Proxy serving pays $0.05/GB service egress — cents at alpha, and the flip-to is priced in. Provider swap = config + data copy, by construction. The local emulator is interchangeable (MinIO pinned or Garage — S3-compat is the only contract). Media writes inherit the freeze/fence/lease regime because media is plan data.
- **Invalidating condition.** Measured egress cost or photo latency → the presigned-redirect flip. No Asia region in Railway's dropdown at provisioning → R2 immediately. A real full-res consumer → keep-original reconsidered. The web read-only surface → the same media endpoint serves accountless reads under INV-3's rules.

### ADR-028 — The trip's own facts: ONE destination, ONE Trip Currency, merge-patch on the update endpoint, owner-only details editing *(the second ADR-008 waiver; carries three /v1 semantics changes at once)*
- **Status.** Accepted · 18/08/2026 (S4.25 grilling, founder-ruled) · **an explicit ADR-008 waiver** — the additive-only rule is set aside deliberately and on the record, not evaded. Standing ground: every installed client is a founder's own, so the "old app versions live for weeks" premise that justifies additivity is, today, false in fact.
- **Context.** A trip's basic facts were half-writable and scattered. **Dates had no writer since S4.19 retired the pickers** — every trip created after that showed a blank date eyebrow and read "Dates to be decided" forever, with no way to decide them. **Currency was a per-activity fact nobody set deliberately**: almost always the form's prefill, yet `EstimatedCost.derivedFrom` returns *nothing at all* when the currencies disagree, so one odd activity silently collapsed the published cost total. **The wire carried a destinations LIST for a product that ruled one destination per trip** (founder, 2026-08-09) — and the shipped edit form already truncated legacy lists to their first entry on save, so the plural column was being quietly destroyed by the UI while the API still promised it. The Details tab duplicated the edit form's job while burying "where and when is this trip" behind a sixth tab.
- **Decision.** *(1) Trip Currency joins the Itinerary* — nullable in the column, **defaulting to `PHP` at creation, server-side** (founder: "default to PH peso for now" — deliberately NOT seeded from the traveler's preferred currency, which keeps its one recorded meaning as the E5 expense default). Replace-only on the wire: absent = keep, explicit null refused. *(2) Destination narrows to a scalar* — one migration adds it, backfills **keep-first** from the legacy list, and **drops the list column**; every response shape that carried the list serves the scalar, and discovery search, trending and typeahead stop unnesting. *(3) The update endpoint adopts merge-patch semantics* — **absent = keep, explicit null = clear** for description, best time of year, start date, end date and standouts; title and destination remain required and refuse null. This replaces full-replace-with-exceptions and becomes **the standing convention for every future clearable field** (API conventions doc). *(4) Trip-details editing narrows to owner-only** (founder, 2026-08-18, reversing this same grilling's earlier any-member answer on the record: "edit details / publish are owner only; collaborators can just add to activities"). Plan writes — days, activities — stay member-wide, unchanged. *(5) Changing the trip's currency bulk-relabels every priced activity transactionally* — numbers untouched, labels swapped, **no FX ever**; the client confirms first when priced activities exist. The activity wire keeps its per-activity currency for additivity, and every activity save stamps the trip's currency into it.
- **Alternatives rejected.** *Adding a scalar beside the list* (the strictly-additive move V3's own comment prescribed) — leaves two sources of truth for one fact, and the wart V3 predicted could never be removed is exactly what a waiver removes. *Joining the legacy entries into one destination string* — declined on the record, 2026-08-18: it mints "Palawan · Philippines", a destination nobody typed, which every destination filter then misses. *Seeding the trip currency from the traveler's preferred currency* — superseded by the PHP ruling; preferred currency keeps one meaning. *Inferring a mixed-currency trip's currency* — no honest answer exists, so it takes the default and the activity rows keep their own stored currency. *Keeping full-replace* — it makes a second writer of trip details unsafe, which is the whole point of this story.
- **Consequences.** **Keep-first is destructive and owner-approved**: the dropped entries are not recoverable. It is safe in practice for a reason specific to this data — the overwhelming population of multi-entry rows is seeder fixtures, whose derived region was appended *last*, so keep-first retains the authored place and drops the machine's noise (the seeder's region-append is deleted by this story, so the shape cannot recur). **Jackson 3 cannot express merge-patch with `Optional`** — it maps *both* an absent key and an explicit null onto `Optional.empty`, so the wire needed `Patchable<T>`, whose deserializer overrides `getAbsentValue` to keep the two apart. **The mixed-currency total stops vanishing**: a trip now has one currency, so the single-currency collapse in `EstimatedCost` can no longer be tripped by one odd activity. Dates are named a **workspace-private invariant** — no public or published surface ever carries them; duration is the public fact (already true, now pinned by name rather than by accident). E5 inherits a trip that already knows its currency, with no FX anywhere.
- **Amended 2026-08-19, before the merge — three of this ADR's SURFACES are parked; none of its wire or model decisions are.** On a live feedback pass the founder hid the **settings cog** (`COG_IS_LIVE = false`, "the pencil function when editing will do for now"), the **facts line** under the workspace title, and the **date fields** in the details editor (`DATE_FIELDS_ARE_LIVE = false`), and parked the two date walks as `test.fixme`. Decisions 1–6 and 10–12 are unaffected and shipped: the scalar destination, the Trip Currency and its PHP default, merge-patch, owner-only details editing, the bulk relabel, the deleted Details tab, and the currency vocabulary all stand. What is switched off is decision 7 (facts line), decision 8 (cog) and the date half of decision 9. **The parking is a flag, not a revert** — the components stay imported and rendered behind a runtime `false`, so `tsc` and Jest still cover them and unparking is one boolean each. **One consequence worth naming, because it is the reason merge-patch was worth building:** with the date fields hidden the client OMITS `startDate`/`endDate` rather than sending null, since null means *clear* under decision 4b — a hidden field must not be able to destroy the value behind it. The details editor itself remains reachable by the title pencil inside the Itinerary Workspace.
- **Invalidating condition.** A real third-party or non-founder client on `/v1` → no further waivers; additivity binds again in fact and not just in rule. Travelers pricing one trip in genuinely several currencies → the parked per-activity override capability (recorded as S4.25's candidate capability), which is a capability and not a retreat from the trip-level currency. A traveler who wants two destinations on one trip → reopen the 2026-08-09 ruling, not this ADR.

- **Alternatives rejected.** Removing `finish-planning` or `reopen` from the wire — ADR-008 forbids removal, and dormancy/unsurfacing cost nothing: after the remap no client ever sees a draft, so no Finalize button renders. Keeping `draft` as a storable-but-never-emitted state — inert mechanism one layer down. Keeping Step back as a buried undo (cog) — permanent chrome for a rare mis-tap the drawers now prevent at the source. "Active" as the tab label — re-mints the axis collision and puts a second name on one state (ADR-018's naming argument, fourth application).
- **Consequences.** *(a)* The wire, under one waiver: trips born `upcoming`; `draft` never emitted; `finish-planning` permanently 409; `reopen` floors at `upcoming`; `category=draft` accepted-and-empty forever (`TripCategory` keeps the constant so `parse` doesn't 400 it). *(b)* One remap migration `draft → upcoming` (V36, the V21 precedent, stepping IT) — **owner-gated: approved in principle, the file is proposed before it runs anywhere.** *(c)* Blast radius measured 2026-08-20: ~6 backend + ~7 mobile files (`FinalizeSheet` dies whole; the transition drawer is born; `tripSections` becomes the tabs module) + docs; the real cost is mechanical churn — 29 backend IT files, 9 Jest files, 12 Playwright specs. *(d)* ADR-020's shaping for the parked past-trip door re-shapes: a birth-state parameter would now be `upcoming | completed`. *(e)* The "no mock frames" epic-map line loses its Ready and Step back deviations with the affordances themselves; the tabs surface gets its own baseline (the S4.26 canvas, prompt-first — `design-brief.md`).
- **Invalidating condition.** A real reader for the done-planning declaration arriving (validation-gate evidence: travelers wanting a visible "not ready yet" distinct from `upcoming`) → the fact returns as presentation first, a wire state only with its own ADR. Travelers mis-confirming through the drawers and asking for their trip back → the undo returns as a cog item before `reopen` grows UI chrome. ADR-020's rotting-trips condition carries forward unchanged onto the surviving rungs.

### ADR-030 — WebSockets enter the stack as generic topic infrastructure *(partially reverses the pull-based-only posture of ADR-014's family; extends ADR-008's additivity to socket payloads; push notifications remain a separate, unmade decision)*
- **Status.** Accepted · 20/08/2026 (founder — the transport ruling at the S4.10 chat grilling, grill-with-docs, three rounds; infrastructure-first sequencing ruled in the same session: WS-1 builds before its first consumer)
- **Context.** Every read surface to date is deliberately pull-based ("no sockets, no push, no broadcast" — the lease indicator, polls, invitations). In-trip chat (S4.10) is the first surface where live delivery is the expected UX, and its plausible successors (poll activity, presence, live editing's eventual sync) all want the same pipe. The alternative — polling the chat read while the tab is focused — was recommended and considered; the founder ruled sockets, built once, generically.
- **Decision.** One WebSocket layer inside the existing backend and app — no new deployable infrastructure. **(1) Auth:** a single-use ~30s ticket (`POST /v1/ws-ticket`), redeemed-and-burned at the `/ws` upgrade — never a bearer token in a URL (P3); browser WS cannot send headers, and a burned ticket in an access log is worthless. **(2) Subscriptions are authorization acts:** topic names (`itinerary:{id}:{channel}`) are parsed, the Membership resolves through the guard, non-members get the masked refusal, and membership hard-delete evicts the member's subscriptions AFTER_COMMIT — the S1.5 lease-release posture on the socket. **(3) Fan-out rides domain events**, `@TransactionalEventListener(AFTER_COMMIT)`, IDs only (ADR-002): a broadcast can never precede its commit; delivery is **at-most-once by design** because **(4) the database is the source of truth and the socket is a latency optimization** — every consumer must be able to re-read its state over REST after a reconnect (the catch-up convention); UUIDv7 event ids give finer grain when a consumer wants it. **(5) The envelope** `{topic, type, eventId, at, payload}` **evolves additively only** (ADR-008 extended — installed apps hold sockets against new servers for weeks) and **clients silently ignore unknown event types** — the rule that lets the server grow topics without stranding old apps. **(6) Hygiene:** server ping 30s / close after 2 missed; bounded send queues — slow consumers are closed, never buffered unboundedly. **(7) Origin posture mirrors CORS:** dev-profile allowlist bean, absent Origin admitted (native), prod refuses browser origins, invariant-tested. **(8) In-process fan-out behind an interface** — the broker seam is named and deliberately unbuilt.
- **Alternatives rejected.** Polling (`refetchInterval` while focused) — adequate for chat at alpha scale and architecturally consistent, but rebuilt-per-surface and a dead end for presence; the founder chose the pipe once. STOMP/SockJS — subscription routing for one channel shape doesn't earn a protocol layer. Bearer-in-query auth — P3. Sticky first-frame auth — kept as the recorded fallback if the edge mangles query strings (the WS-1 spike decides on evidence). A broker now — infrastructure for a scale that doesn't exist; the interface is the graft point.
- **Consequences.** The first stateful component in the stack: the harness gains socket assertions that must name their failure mode (connected-and-dead looks connected), the emulator and preview rungs gain `ws://` derivations of the one API base URL, and Railway's edge behavior becomes load-bearing (proven by WS-1's spike before anything is built on it). Chat (S4.10) ships as one table + two REST endpoints + one topic row. **What this ADR does not decide:** push notifications (a closed app still hears nothing — a separate decision with its own moment); presence/typing/live editing (ADR-014/022's invalidating condition does **not** fire because a transport shipped); horizontal scale-out (the broker seam's own ADR, on its day).
- **Invalidating condition.** The backend scaling past one instance → the in-process fan-out is replaced behind its interface (broker ADR). Live editing genuinely arriving (ADR-014/022's condition) → presence and sync design on top of this layer, not beside it. The spike or the device rung contradicting the hygiene defaults → the numbers move, the structure doesn't.
- **Amendment (24/08/2026 — S4.35's grilling, four rounds, founder-ruled; three additions, none of which reverses anything above).** **(A) A second topic subject: `traveler:{id}`.** Decision 2's grammar assumed every topic names a trip. That subject cannot serve a surface listing *every* trip a traveler belongs to — it costs one subscription and one guard resolution per trip on screen — and it structurally **cannot carry an event about a trip the subscriber is not yet a member of**, because the guard would refuse the subscription; which is exactly the event that makes an approved trip appear. So a two-segment subject joins it, authorized by **identity** (*is this you?*) rather than by membership, with the same masked refusal for anyone else's. **The contents are resolved once, at subscribe**: the server runs the guard, reads that traveler's memberships in a single query, and registers the session under each of their trip topics in `SessionRegistry` — so broadcasts stay per-trip and small and **no query runs per event**. `MembershipEvictionListener` already removes registrations on departure; its mirror adds them on admission, before the granting event is broadcast. **(B) An event whose audience is narrower than its topic carries no payload.** Most trip events are visible to every member; some are not (the join-request queue is owner-only). Filtering per subscriber at fan-out was rejected — it costs a serialization per session — and a dedicated owner-scoped channel was rejected because ownership transfer would have to move the registration, silently, or break. A **contentless signal** cannot leak, non-subscribing surfaces receive it and do nothing because the query is not mounted, and REST remains the sole authority on what a viewer may read. **(C) Fan-out becomes asynchronous, and this is a defect fix rather than a scale change.** Decision 6's bounded queue exists, but `Session.send` drains it **on the caller's thread** — the writing traveler's HTTP request thread, via `AfterCommit` — with a blocking socket write; and `Heartbeats.pingEverySession()` walks every session serially on Boot's **single-threaded** default scheduler with no pool configured. A client that stopped reading (a phone in a tunnel sends no FIN and stays open for minutes) therefore stalls another traveler's POST, and stalls the ping loop that exists to detect exactly that client. Draining moves to a bounded executor and the scheduler gets a real pool. **Amended in flight (25/08/2026, at S4.35's implementation, owner-ruled): the scheduler pool SHIPPED; the bounded executor is PARKED, and the reasoning above is only half-confirmed.** Measured against the shipped code before writing any fix: broadcasting 8KB frames to a socket that had genuinely stopped reading dropped the session at **~2.1MB in flight** via the existing `SEND_QUEUE_LIMIT` overflow close, with the **worst single broadcast at 57ms** — the bounded queue absorbs the stall before a socket write ever blocks the caller — and `pingEverySession()` timed twenty times under continuous flood came back at **worst 0ms**, so the `synchronized(socket)` contention is real in the source but not observable. What IS confirmed is structural rather than measured: no `TaskScheduler` bean and no `spring.task` config existed, so Boot's single-threaded default carried the heartbeat and the ticket sweeper together and one stalled task delayed the other. That half shipped (`spring.task.scheduling.pool.size`, guarded by `SchedulerPoolIT`, sabotage-verified). **The honest bound on the measurements:** they ran on Windows loopback with TCP autotuning, where the receive window grows aggressively; Railway's edge, a mobile network and a genuinely wedged handset are all different, and Tomcat's default 20s blocking send timeout means a real stall would surface as a 20-second hang rather than a permanent one. So the source reading above stands as source reading — what is disproven is only that *this rung* can produce a slow consumer. **Trigger for the parked half: the first write-latency spike correlating with a connected session, or the move off a single replica** — the same event as the broker trigger below. The harness the decision needs is committed (`SlowConsumerIsolationIT` + `DeafWsSocket`) and **passes against the unfixed dispatcher**, saying so in its own assertion text so it cannot be mistaken for evidence. **What this amendment does NOT decide, stated because a future reader will be tempted:** broadcasting an Editing Session's start and end **is not live co-editing sync** — ADR-022 chose an exclusive session *because* that sync does not exist, and that condition has not changed; the boundaries are pushed rather than polled, and the plan inside them is still read at its last saved state. Async fan-out also does **not** unlock a public-feed topic: it moves the cost off the writer's request thread, it does not make an unbounded audience cheap. **Invalidating condition, added:** any topic whose subscriber count grows with total travelers rather than with a trip's membership → the fan-out itself is redesigned (batching, per-connection outbox, or fan-out-on-read) before that topic ships. The single-instance condition above is **made structural**: the service is pinned to one replica, and the broker trigger is the instance count changing — not a connection number, because no instrument exists that would measure one honestly against the real edge.

### ADR-031 — CI answers for the suites; the machine answers for the eye *(extends ADR-026's harness posture to where suites RUN, not what they assert; changes no coverage; supersedes CLAUDE.md's "whole stack, once, before proposing a promotion")*

- **Status.** Accepted · 21/08/2026 (founder — grilled at H2, grill-with-docs, five rounds, 22 questions) · discharges the founder's per-ticket full-suite complaint
- **Context.** `implement` runs per ticket and its line 11 demanded *"the full test suite once at the end"*, so a six-ticket story paid six full passes — and the verify-and-modify loop after it had no skill at all, so agents defaulted to running everything. A full local pass measured **~30 minutes**. Meanwhile `.github/workflows/ci.yml` had been running `mvn -B verify` (214 unit + 882 ITs), the typecheck, the Jest suite and a clean-checkout compose on **every push, every branch**, in **2m46s** — five times faster than the same suite locally on a runner with *no more cores*, because the gap is Docker Desktop's WSL2 boundary and the Windows-only workarounds it forces, not CPU. Cost: ~6 billed minutes per push against a 2,000-minute allowance. Nothing could read it: an agent memory asserted `gh` was deliberately absent, so `dev` sat red for **13 consecutive pushes** on one order-dependent fixture collision before anyone looked.
- **Decision.** Three tiers, by what a suite *needs to exist* and whether it can go red without the code being wrong. **Cheap** (no prerequisites, near-zero startup, a red is always yours — Jest, `tsc`, backend unit) and **medium** (starts its own containers, can lie environmentally — the backend ITs) run **in CI on every push**, path-filtered behind an always-runs aggregator; per-push rather than per-gate because it localises a break to the commit that caused it. **Expensive** (needs a system someone stood up, can lie loudly — Playwright) runs at the **merge gate**: a `pull_request` to `dev`, required, with its own compose stack and the preview container built in-job. Local work is Tier 1 only — incremental `tsc`, `jest --changedSince`, and looking at the change. `dev` gets required PR + required check, administrators included. **`preprod` and `main` get required checks and NO required PR**, because GitHub's PR merge has no true fast-forward and requiring one would mint a different SHA, destroying the `git rev-parse main preprod` property the pipeline exists for.
- **Alternatives rejected.** *Scoping the backend locally by module* — H2's own first draft, and the centrepiece until CI's 2m46s was measured; it takes ~14 minutes to ~5, not to ~1, because most of a scoped run is startup. Survives only as a one-line debugging convenience. *An end-of-day full local sweep* (the founder's opening proposal) — right in spirit, but once CI owns the suites there is nothing left in it but the device walk. *Nightly Playwright* — an unattended red at 3am that nobody triages is precisely the lying-suite problem. *Trusting CI by discipline rather than protection* — thirteen red pushes is the evidence against. *Admin bypass on `dev`* — recreates the gap being closed.
- **Consequences.** Nothing automated runs on the founder's machine; their time goes to the device walk, motion fidelity and the defect classes no suite reaches (the avatar blind spot was found by chatting with a real person). A red becomes unmissable at the moment it matters because the merge button refuses — **email is explicitly not a signal here, the founder does not read it**. Direct commits to `dev` end, enforcing CLAUDE.md:39 rather than inventing a rule. Feedback moves from foreground blocking to a wait at the merge, which is already a pause point since promotions are propose-first. A workflow file can now read the pool credentials, so **workflow edits become sensitive**. The `@Tag("migration")` exclusions and the per-module scope table are cut, their justification having moved.
- **Invalidating condition.** CI going unread again — the named failure mode, and why readability blocks H2 rather than trailing it. A second workstation or contributor whose pushes contend for the pool. The Playwright job's minutes becoming a line item, which is also the re-worded trigger on the parked P8 duplication line. CI ever pointing at deployed dev instead of its own stack, which inverts the no-contention argument entirely.

### ADR-032 — The invite link + join request model *(extends S1.2's invitation model with the second consent direction; takes the ADR-008 waiver family's ground for the publish-freeze semantics changes; the anonymous teaser is the deliberate exception to the everything-authenticated posture)*

> **Amended 2026-08-23 — the token's entropy floor drops from ≥128 bits to ≥64 bits (43 characters → 11), founder-ruled.** The 77-character link was reported as too long to share. The original 32-byte token was **double** the ≥128 the ADR itself required, so the first cut to 16 bytes was free; this second cut is the one that needed a ruling. **What a guess actually wins is the anonymous teaser — title, destination, dates, cover — plus the right to *ask*, which an owner must still approve.** Not entry. At 64 bits that is one expected breach per ~5,800 years against 100,000 live links and a sustained 1,000 guesses/second, which is the same entropy Google gives an unlisted YouTube video — a strictly higher-value target. **48 bits (8 characters, the founder's first ask) was declined on the arithmetic**: ~11 breaches a year under the same assumptions, and the rate limiter that would have rescued it turned out to be a false friend — see the parked line in the epic map. **What still holds from the original:** no expiry, no regeneration, reset parked behind a spam-report trigger. **What would invalidate this:** any change that makes a guess win *entry* rather than a teaser — guest accounts, auto-approval, or a link tier that skips owner consent — restores the ≥128 floor, because the consequence, not the number, is what sets it.

- **Status.** Accepted · 22/08/2026 (founder — grilled at S4.28, grill-with-docs, four rounds + a design-prompt cycle; design baseline = the Travelers Spec s2 canvas, contracts C1–C7/M1–M7 normative)
- **Context.** Invitations reached only people the inviter could name — an email address (S1.2) or an exact @handle (S4.9) — and only the owner could issue them, from a door buried in the plan editor. Nothing could bring in someone not yet on Largata except dictating their email, and the founder's ask was a Discord-style shareable link — with the explicit constraint that holding the link must **not** mean entry, because links get forwarded.
- **Decision.** **(1) Two consent directions, named in the domain model:** an **Invitation** is the trip asking the traveler (the traveler consents by accepting — no owner action); a **Join Request** is the traveler asking the trip (the owner consents by approving). **(2) Approval creates membership immediately** — the request was the requester's consent, so there is no third handshake; a request can only exist for a signed-in, onboarded, email-verified account, so approval never admits a half-built identity. Decline is silent and retryable; membership arriving by either path supersedes the other's pending rows. **(3) One live link per trip**: an opaque unguessable token (≥128-bit), minted lazily, reused forever — no expiry, no regeneration (reset parked with a spam-report trigger); the link is dead while the trip is archived or published, computed at read time. **(4) The token-gated teaser answers anonymously** — title, destination, dates, traveler count, cover; never roster or plan — the first anonymous product endpoint, deliberate: the landing is the conversion moment for exactly the not-yet-onboarded person the feature targets. Two capability-scoped cover reads exist because the audience fence correctly refuses both audiences (the token and the invitation are themselves the authorization). **(5) Policy: any member invites by handle, revokes pending invitations, and shares the link** — the additive widening S1.2's grilling recorded in advance; **removal stays owner-only** (the mock's any-member-removal was rejected: an approve-then-purge griefing surface); the Requests queue and ownership offers stay owner-only. **(6) Publish freezes the people, not just the plan:** invitation issuance/revocation/acceptance, removal, join-request creation/approval, and all ownership-offer operations refuse on a published trip — "publishing is already a completed trip"; pending rows go inert and hidden, resurfacing on unpublish; **leave always works**; completed-but-unpublished keeps everything open (post-trip adds are the photo-dump use case). **(7) Link joiners onboard in full** — the pending token persists through sign-up/onboarding and app restarts and returns them to the landing; no trimmed path (rejected, not parked), no guest accounts (parked: they are an entitlement tier, which is ADR-009's parked seam, and handle forfeiture needs the scheduler this codebase deliberately lacks).
- **Alternatives rejected.** *Approval minting an inbox postcard the requester must still accept* — a third tap on a person who already asked, and a join that silently never completes if the card goes unnoticed. *Any-member removal (the s1 mock)* — subtractive authority with a griefing surface confirms can't fence. *Link expiry / regeneration now* — approval already gates membership, so a leaked link is queue noise, not entry; Discord-style rotation is real machinery for a problem with no evidence yet. *A blind sign-in wall instead of the teaser* — wastes the one moment the feature exists for. *Guest accounts* — see (7). *Network fuzzy search in the add sheet* — no search infra exists and the founder ruled it waits for the network itself; v1 is exact-handle plus the link.
- **Consequences.** Three shipped-/v1 semantics changes ride this ADR's waiver (the founders-only-clients ground of S4.23/S4.25): members' invite calls stop 403ing, membership/offer mutations start refusing on published trips, and invitation accept refuses on published trips. The app gains its first pre-auth screen and the auth gate learns to admit one segment unauthenticated. The share URL is composed server-side per environment, shaped so Android App Links can adopt the same URLs later. The analytics this story emits (teaser views, requests, outcomes) are what make the guest-accounts trigger measurable. The members screen and the editor's invite door are deleted; the Travelers tab becomes the single membership surface, ownership transfer included.
- **Invalidating condition.** Link-request spam actually reported → the parked reset-link line pulls. Invite-link conversion visibly dying at the sign-up wall → the guest-accounts line pulls (as its own grilled story, plugging into the landing's signed-out state — the mechanics here don't move). Public profiles landing → the suggestions/multi-select v2 annex activates in the add sheet. A real notification system arriving → approval/decline get their notification moments; nothing structural changes.

### ADR-033 — Crawler-facing card serving: render live at scrape time; version the handed-out URL, never the link *(the backend's first `text/html` surface, deliberately confined to the join surface; upholds ADR-032's eternal token; amends the parked design's "cached per trip")*

- **Status.** Accepted · 23/08/2026 (founder — grilled at S4.29, grill-with-docs, two rounds + a Java2D fidelity prototype reviewed before the spec)
- **Context.** A shared `/join/<token>` unfurled with S4.28's generic brand card: the web surface is a static SPA export, a crawler never runs JavaScript, and the backend had no HTML-producing endpoint anywhere — so per-trip Open Graph tags had no way to exist. The founder asked for the per-trip card the day after seeing the generic one unfurl. The hard constraint came from ADR-032: the invite URL *is* the eternal token, so the standard cache-busting move — change the URL when content changes — would break every link already sitting in a chat thread.
- **Decision.** **(1) Crawler detection at Caddy, on the web origin:** a curated user-agent matcher on `/join/*` rewrites to a backend HTML preview route; every other UA keeps the static SPA. The route sits under ADR-032's existing `/v1/join/**` anonymous matcher — no security-chain change — and its body is a branded page with a plain link, never an auto-redirect (a misclassified browser would loop). **(2) The card renders in-process, live, on every crawler request:** Java2D against bundled OFL fonts, composing the existing teaser and media interfaces — no external renderer, no second runtime, no pre-generation, and **no server-side cache**, because a cache reintroduces exactly the staleness the versioning exists to kill; the committed generic card is the failure fallback only. The image is its own route on the API origin, path-served to every UA (image fetchers don't reliably identify as crawlers). **(3) Freshness by versioning what is handed out:** a counter on the trip bumps when any card input changes (title, destination, dates, cover) and the share URL — and the `og:image` URL inside it — always carry `?v=N`. **The server never reads `v`**; it is purely a platform-cache key, which is what guarantees a fresh scrape of *any* version renders current data. `/join/<token>` bare resolves forever. Past shares keep the card they were shared with — a deliberate scope cut (no Graph re-scrapes, no app tokens, no version bookkeeping). **(4) Dead links (published/archived) answer 200 with a "no longer active" card; unknown tokens answer 404 with nothing** — grace for links that lived in real threads, silence for enumeration.
- **Alternatives rejected.** *Rotating the token to refresh the preview* — breaks every posted link; a functional break traded for a cosmetic one (the founder's first instinct, corrected on the record). *An edge/OG-renderer service or a Node renderer (Satori/Puppeteer-class)* — new infrastructure or a second runtime beside a Java backend, for one card the prototype drew in ~180 lines of Java2D. *Pre-generated cards stored in media* — invalidation machinery plus exactly the staleness class the live render deletes. *Server-side render cache* — same staleness class, for traffic measured in fetches-per-share. *Refreshing past shares via Facebook's Graph re-scrape* — real work (app token, per-platform matrix, version bookkeeping) for semantics the founder ruled acceptable without it: a preview shows the trip as it was when shared.
- **Consequences.** The backend gains an HTML media type on exactly one surface; the API origin serves a public, versioned image; the single Caddyfile (preview and deployed rungs alike) carries a crawler-routing concern reviewable in git. Card fidelity is verified by eye against the design frames and by real unfurls — golden-image tests are flake by construction across JVMs. The client is untouched: URLs are composed server-side and the token parser already ignores query strings.
- **Invalidating condition.** Measured render load → the cache line returns as an input-keyed LRU (never a trip-keyed cache with invalidation). A server-rendered web surface landing (the S4.8 must-answers / E6 neighbourhood) → this mechanism folds into it rather than surviving beside it. A major platform's fetcher ceasing to identify itself by UA → the detection posture is re-examined.

### ADR-034 — Visibility is a property of the Profile, not the Itinerary *(supersedes ADR-019's third axis; re-amends its consequence (d); amends ADR-025 / INV-2a; the follow edge becomes an authority for private profiles only)*

- **Status.** Accepted · 04/09/2026 (founder — grilled at S4.39, grill-with-docs, four rounds, 26 questions; backend story specced, the UI queued as S4.40)
- **Context.** Everything a traveler authors as a person was public to every signed-in traveler the moment it existed (ADR-025 as amended), follow granted nothing by design (ADR-019's 26/08 amendment), and nobody could refuse a follower. The founder's driver: travelers need a reason to open the app between trips, and a traveler who would post past trips to people they approved had no circle to post to. Meanwhile the itinerary carried its own public/private switch answering a different question — who may open a *published* plan — a second meaning of "private" that had already cost two ADRs (018, 019).
- **Decision.** **(1) Profile Visibility** — `public | private` on the Traveler, default public, the traveler's own edit. It governs what the traveler **authors as a person**: postcards wherever they appear (Home, the profile's diary tab, the per-trip diary, the photo bytes) and the profile's follower and following lists. It never governs a Trip Workspace (members only, always — INV-1) or an Itinerary. A private profile still exposes its header, its four counts, its published itineraries and its presence in search. **(2) The itinerary's visibility axis retires.** `published` is its one exposure switch, and a published itinerary is readable by every signed-in traveler; "published + private" ceases to exist. The gate on `completed` and the freeze on publish are untouched. **(3) Follow is an authority for private profiles, and only for them.** Following a private profile creates a **Follow Request** (`pending → approved | declined | cancelled`, one pending per pair, re-request a new row, decline silent); approval creates the edge. Public profiles keep S4.37's open follow. **(4) Remove-follower** exists on every profile; blocking stays parked. **(5) Transitions follow Instagram:** going private keeps existing followers; going public approves every pending request. **(6) Refusals are honest:** a gated list answers `403 PROFILE_PRIVATE` — existence is not secret, the profile is searchable — while bytes answer `404`; the profile read carries `visibility` and a viewer relation so a client can pre-empt. **(7) Co-travelers get nothing extra**, and dump-implies-consent (ADR-025 decision 2) is untouched: privacy governs what you author, not what you handed to the trip.
- **What it reverses.** ADR-019's third axis (the other two, the gate and the freeze stand) and its 26/08 amendment's "follow narrows nothing" — narrowed now to *"follow narrows nothing on a public profile"*. ADR-025 / INV-2a's "every entry is public the moment it is posted" — the entry still has no state; the fact moved to its author. ADR-017's reserved `friends_only` value closes for good: the narrowing question that waited for "friends" to be defined is answered by "approved follower of a private profile", which needs no mutuality.
- **Alternatives rejected.** *Profile privacy setting the default visibility of a publish* — kept the itinerary axis alive for one edge case; the founder chose one meaning of "private" over two. *Followers-only published itineraries* — a third itinerary audience; the same second meaning by another door. *Void pending requests at the flip to public* — recommended, declined once Instagram's behaviour was read: auto-approve is what the requester asked for. *Keep pending requests on a now-public profile* — needs a `superseded` state and an owner curating a queue for an open door. *A cooldown on re-request after decline* — nobody asked; the vector is on the rate-limiting line.
- **Consequences.** ADR-008 holds without a waiver: every wire change is additive, the default is public so every existing row answers identically, the retired itinerary field survives as a constant `public` and a private `audience` is refused by name; the shipped client cannot reach a private profile until S4.40 ships the toggle. Rows published as private were **unpublished** by the migration, not exposed (owner's ruling on a stop rule). A postcard's audience now depends on its author, so every postcard read — feed, lists, bytes — consults the follow edge when the author is private; the read rule is stated once in the S4.39 spec. INV-2 gains "to every signed-in traveler"; INV-2a gains "to the audience the author's profile admits". S4.37's lists stop being unconditionally public. Highlights (S4.2), when built, filters per viewer, and diary-level publish does not return as sugar. Blocking, notifications and any socket frame for requests stay parked with their triggers.
- **Invalidating condition.** A real ask for a followers-only *itinerary* → the third itinerary audience is argued as its own ADR, not by resurrecting the axis. Evidence that a private circle produces no postcards because there is nothing to post → the past-trip door (closed `wontfix` at S4.15) is the line to reopen, not this one. A privacy complaint that removal cannot answer → blocking pulls off the defensive line.
### ADR-035 — The content world becomes four first-class objects, built dark *(amends ADR-017/019's projection language for the new world; supersedes ADR-024's projection-and-containment for the new world; the old world keeps all three until the rewire deletes it; extends ADR-002 with a time-boxed waiver)*

- **Context.** Everything trip-related sat in one module, so the objects travelers think in — Trip, Itinerary, Diary, Postcard — had no identity of their own: a published page could not outlive its trip, a departed member could never withdraw public postcards, "delete" could only be archive-deep (S4.38), and the confirmed trip-less future was structurally impossible. The founder's direction: build the correct object model now, pure backend, without touching the running app. Grilled 2026-08-27 → 2026-08-30; built as CM-1; the wire reference is `docs/design/08-object-contracts.md`.
- **Decision, as one piece.** **(1) Four peer modules** — `trip`, `diary`, `postcard`, `publication` — matching the house convention of small top-level modules (an umbrella `content` module was weighed and declined by the founder). `publication` is a working name: `com.largata.itinerary` is the frozen old world, and the rename to `itinerary` is a free internal refactor once the old files delete; the entity and every traveler-facing word say **Itinerary**. **(2) Publish mints the itinerary object** from the frozen plan — ADR-019's freeze is what makes the mint equal to the live projection — carrying its creator-trip reference with **no foreign key**, so survival is structure, not mechanism. Unpublish retires but keeps the id (`UNIQUE(trip_id)`); republish refreshes the same object; the recorded owner hard-deletes it even orphaned. **(3) The diary is a stored entity** (title-only v1): standalone, or auto-minted on the first trip-derived post; a postcard lives in **at most one diary or loose**; **deleting a diary deletes its postcards** in one act — and the postcard→diary FK is NO ACTION, deliberately, so no code path can skip that containment or its photo cleanup. **(4) Postcard authority is authorship alone**: object-addressed read/recaption/delete; **delete crosses the archive freeze and consults no trip state** (withdrawal is a right — this is what dissolves the stranded-postcards hazard), while recaption respects the freeze (editing is not withdrawal). Trip-derived creation reads the activity through the trip module's interface at post time and snapshots it — never event-replicated. **(5) Real trip destruction** (`DELETE /v1/trips/{id}`, owner-only, any lifecycle state): one transaction destroys the workspace world and its stored media; the content objects, old-world entries, forked copies and fork provenance stand — made true by V52 dropping the old entries table's itinerary CASCADE and activity SET NULL. **(6) The B-fork's four safety rules** govern the dark window: the new world ships dark (no product reader or writer touches it); **every backfill runs at cutover, none at CM-1** (the old world keeps writing through the dark window, so an early backfill is stale on arrival); destruction ships unexercised (the old feed would mis-hide a destroyed trip's surviving old-world postcards until the readers move); trip data never forks (the new tables are for content objects only — the trip's published flag is written onto the existing record, one truth). **(7) The strangler waiver on ADR-002**: the new `trip` module maps and mutates tables the frozen old modules own, as their *next owner* — delegating to code scheduled for deletion was rejected. **Amended 08/09/2026 (CM-4): the waiver names its tables, so its surface cannot widen unnoticed.** It named none, and CM-3 widened it by a table (`edit_lease`) and back again with no signal either way — because every boundary guard in this repo reads Java imports and every one of them is blind to a table named inside a string literal. The waiver covers `TripService`'s raw SQL over exactly these **twelve** tables, measured from the statements rather than remembered: `itinerary`, `day`, `activity`, `workspace`, `chat_message`, and destruction's seven workspace children — `poll`, `invitation`, `join_request`, `join_link`, `ownership_offer`, `ownership_transfer`, `membership`. A thirteenth table appearing here is a change to the waiver and is argued as one. **The general source-text SQL guard that would enforce this mechanically is TW-1's**, deliberately: the three modules CM-4 touches contain no raw SQL, so it would guard nothing that story changes while carrying false-positive cost immediately, and the table→module map it needs is what TW-1's schema-per-module decision supplies. The waiver's **dissolution condition** is the rewire deleting the old world's files, at which point the boundary-guard test (which today fails the build on any new-world import of an old-world package) retires with the world it guards. **Amended 08/09/2026 (TW-1): the facade is gone and the waiver narrows from twelve tables to five.** `TripService` was deleted — every read it fronted is now over its own slice's repositories — so seven of the twelve are no longer waived at all but simply **trip's own**: `itinerary`, `day`, `activity`, `workspace`, `membership`, `ownership_offer`, `ownership_transfer`. What the waiver still covers is `TripDestructionService`'s raw SQL over the **five foreign** tables its one transaction deletes from: `poll`, `invitation`, `join_request`, `join_link`, `chat_message`. Each carries `NOT NULL REFERENCES workspace`, so an event-driven destruction is impossible before those keys drop, and the one-transaction contract is pinned by test; **trigger for dissolving this remainder: the foreign-key-drop story**, with the schema move. **The general source-text guard this ADR deferred to TW-1 now exists** — `TripRawSqlWaiverTest` asserts that raw SQL lives nowhere under `trip/` but the destruction service, that its foreign tables are exactly those five, and that the scan is not passing vacuously; a sixth foreign table is a red build.
- **Consequences.** Three new tables (`itinerary_object`, `diary`, `postcard`), two constraint drops on `diary_entry`, one additive keeper-module constant (`PhotoSubject.POSTCARD`), zero UI, zero client change, zero events — archive state and activity facts are synchronous interface reads; `TripDeleted` and WS eviction arrive with the rewire. The shipped app cannot tell CM-1 happened: the existing suites pass without a single edited test. Until cutover, content written through the new grammar is invisible to the feed and profiles — dark by design, not a bug.
- **Invalidating condition.** The rewire story completes the strangler: client cutover, freeze → backfill → switch, readers moved, destruction's screens and events, the old endpoints' ADR-008 fate — and the waiver, the working name, and the boundary guard all dissolve with the old world's deletion. A second deployable consumer, diverging module load, or a second team remain the named triggers that would reopen the broker/service-extraction non-goals.

### ADR-036 — The Diary is a trip that was taken: Diary → Diary Day → Postcard *(amends ADR-035's title-only diary; supersedes ADR-024's projection for the old world too, by turning its endpoints into adapters; upholds ADR-034's read fence and ADR-008's additivity)*

- **Status.** Accepted · 05/09/2026 (founder — grilled at CM-2, grill-with-docs, two rounds, 21 questions; four design-pass rulings and five testing seams confirmed 06/09 at `/to-tickets`)
- **Context.** CM-1 built the diary as a title and a bag of postcards, which was enough to prove the model dark but not enough to tell a trip. The founder's driver was a traveler with no upcoming trip and a phone full of past ones: *"this next story is about posting a diary and postcards individually without the itinerary or trip"*. Pressed on the shape, the ruling was explicit — **"you can add a day and you can add a postcard per day, same as how a trip adds day and activity"** — and the reason for the whole decoupling was that **"everything lives in the itinerary"**: a memory could only be told by first inventing a trip to hang it on.
- **Decision, as one piece.** **(1) The Diary carries what a Trip carries** — title, destination, the dates it spanned, a cover — and its postcards hang off **Diary Days**, mirroring Trip → Day → Activity one level down. **(2) A Diary Day's ordinal is derived from its date relative to the diary's start**, never sequential: filling Mar 15, 16 and 19 of a Mar 15–19 diary reads **Day 1, Day 2, Day 5**, because the traveler is numbering the days of their trip and not the cards they happened to write. One day per date; a date outside the range widens the range; editing the diary's dates never creates or deletes a day; days never reorder. **(3) Unfilled days are candidates, not rows** — the create response lists one per date and stores none, and a day becomes a row the moment it takes a place or a postcard. **(4) Two births stand.** *Standalone*, from a memory setup that **creates no trip row** — memory-as-Trip was weighed and rejected on the record. *Derived*, one per author per trip, minted at that author's first postcard there, **snapshotting the trip's title, destination and dates** and the author's to edit afterwards; a later edit to the trip does not rewrite it, and it takes **no copy of the trip's cover** for the same reason it takes no reference to it. **(5) A postcard gains a day reference**: loose, or on exactly one day, many per day. It may sit on a **trip day with no activity behind it** — the activity is provenance, not a requirement — and a loose one can be **filed onto a day once**; moving a homed postcard between days or diaries is refused by name in CM-2. A postcard with no place of its own renders its day's. **(6) Delete cascades downward and never upward**: a diary takes its days, postcards, photo rows, stored objects and cover; a day takes its postcards; a postcard leaves its day standing. Every confirm shows a count the server already put on screen. **(7) There is no draft state.** A diary is public to whoever the author's Profile Visibility admits from the moment it exists, and every later day or postcard is an edit — so the memory setup is **two acts**, not one: *Next: Add Your Days* creates the diary and returns its candidate days, each filled day saves as its own act, *Post* submits what is unsaved, and *Back* discards by deleting the diary. **(8) The old entry endpoints become adapters** over the new tables — same paths, same shapes, new storage — and their deletion is parked on an epic-map line whose trigger is the client's last old-path call going away.
- **What it amends.** ADR-035's diary — "a stored entity (title-only v1)" — is the shape CM-1 built and this re-cut replaces; its containment rule, its NO ACTION foreign key and its authorship-alone authority all stand and now govern one more level. ADR-024's projection is superseded for the old world as well as the new, not by deleting its endpoints but by making them adapters, so ADR-008 holds with no waiver: not one path, shape or status code moved.
- **Alternatives rejected.** *A composite create — the whole memory in one request* — would carry twenty photos in one act, and an empty diary is a legitimate object; set aside on the record. *A draft state, so a half-filled memory is private until posted* — a second lifecycle for a thing whose audience is already answered by ADR-034, and every screen would have to ask which state it was in. *Memory-as-Trip, minting a real trip row for a past journey* — the founder's flat "no it should not create any trip"; it would put a workspace, an edit lease and a member list behind a thing that has none. *A sequential ordinal, renumbering neighbours when a day is skipped* — makes Day 3 mean "the third card I wrote", which is not what a traveler means by Day 3. *Deleting the old entry endpoints now* — the founder's "don't delete just yet, park a deletion info; just rewire the existing to the new one"; ADR-008 means shipped clients call them for weeks yet. *A staged-upload endpoint so photos upload as they are picked* — the founder ruled photos travel with the postcard's own multipart act, so the mock's per-tile progress ring is a drawing, not a contract.
- **Consequences.** Two migrations: V53 adds the diary's three fields, the `diary_day` table and the postcard's day reference, backfilling CM-1's dateless diaries to `created_at::date` because a CM-1 row records nothing truer; V54 moves every old entry into `postcard` **with its id preserved**, so photo keys and shared links keep resolving, minting a derived diary per (author, trip) and a day per distinct trip day — resolved from the activity where it survives and from the entry's own "Day N" label where it does not. One new photo subject (`DIARY_COVER`) with its own audience. The readers all move at once — Home, the profile's diary tab, the author's lists, the media audiences — because a reader left on the old table would go blind the moment the adapters landed. **The proof that the wire did not move is the old world's own suites: 635 of 636 passed unedited**, and the three edits were storage-level helpers naming `diary_entry` directly, never wire assertions. `OldEntryTableIsReadOnlyTest` pins that no code path writes the old table any more.
- **Invalidating condition.** A traveler telling a trip that genuinely has no dates → the required range is re-argued, and `candidateDates` needs another shape. Evidence that filing wants to be a move rather than a one-way act → the once-only rule reopens, with the day's postcard count and the diary's as the things that must stay honest. The deferred feed and workspace-day screens landing → the diary card on Home and the "Post to diary" affordance arrive with them, against acts that already exist. The client's last old-path call going away → the adapters, the old entity, its repository, its photo audience and `PhotoSubject.DIARY_ENTRY` all delete together, on the epic-map line this story minted.

- **Amended 2026-09-05, at landing.** The itinerary object carries **no audience**: S4.39 (ADR-034) moved public/private to the Profile before this branch merged, so the axis was dropped rather than re-homed, publish takes no body, and every new-world read is fenced by `AuthoredContentAudience`. The trip-derived postcard snapshot carries PL-2's pin. The Diary's shape is re-cut at CM-2 (grilled 2026-09-05) into a collection with the four memory fields and a Day level; this ADR's "entity with optional containment" stands for what CM-1 built, and CM-2's ADR amends it.

### ADR-037 — A trip is the trip itself: the workspace gets its own grammar, and the old one sunsets with the old package *(reverses the 2026-08-30 declination of a parallel trip-path grammar recorded on the epic map's restructure line and in `08-object-contracts.md`; amends ADR-013's "the noun is historical and never moves"; takes a knowing, dated exception to ADR-008's never-remove for one root; upholds ADR-008's additivity for every path while both roots are served)*

- **Status.** Accepted · 07/09/2026 (founder — grilled at TW-1, grill-with-docs, three rounds, 28 questions; record `docs/plans/TW-1-trip-workspace-module/grilling.md`).
- **Context.** The trip was the one object with no address of its own: postcards, diaries and publications answer at their own roots, the trip answered at `/v1/itineraries`, a noun frozen before the vocabulary settled (ADR-013), and the 2026-08-30 ruling had declined a parallel grammar as duplicate endpoints for a vocabulary benefit. Pulling TW-1, the founder ruled the other way and gave the reason as the model, not the wire: *"a trip is the trip itself. you can publish an itinerary based from the trip. you won't transform the trip, you create an itinerary based from the trip."* Once a trip is never published and an itinerary is a thing created from it, the workspace's address is the trip's, and the module that holds the published object is the itinerary module.
- **Decision, as one piece.** **(1) The vocabulary.** A Trip is the trip itself — the journey-object with its plan, editing session, cover, photo dump, lifecycle, members and owner — and is never transformed by publishing. An Itinerary is created from a trip by publishing; forking an Itinerary creates a new Trip. The word Trip is the vocabulary of UI, code and the new wire; only the old wire and the `itinerary` table keep the historical noun until the old package is decommissioned. **(2) The grammar.** Every workspace route gains a `/v1/trips` twin declared on the same controller, so the two grammars are one Java method: 49 twins of the old root's 62 mappings, suffixes verbatim. *(counts corrected at the CM-3 build, 2026-09-07, measured from the running handler mapping; the excluded set is unchanged and is the one grilled here.)* The 13 exclusions, each for a recorded reason: the 8 old diary-entry routes (content, already parked for deletion), `publish` and `unpublish` (not trip acts), `audience` and `finish-planning` (retired), `fork` (an act on an Itinerary). CM-1's dark ten-field read on `GET /v1/trips/{id}` retires for the full record. **(3) Publish belongs to the itinerary module.** The trip has no publish act on the new grammar; the itinerary module owns `POST /v1/trips/{id}/publish` as CM-1 built it; the old flag-only flip stays on the old root, and the trip's `published` column with the `markPublished` write is a bridge for the old readers until CM-5 moves them onto the object. **(4) The refusal code** stays `ITINERARY_NOT_FOUND` on both roots until the old one sunsets, and the client learns `TRIP_NOT_FOUND` beside it now. **(5) The old root is served unchanged until CM-5 decommissions the old package, then sunsets whole** — a knowing exception to ADR-008's never-remove, taken while nothing is in a store, on the reachability reading ADR-008 already carries. **(6) Four stories in ship order:** CM-3 the grammar and client cutover · CM-4 the content-module boundaries · TW-1 the trip module · CM-5 the itinerary module. Each its own id, branch and PR.
- **Alternatives rejected.** *Paths unchanged, a client-side rename only* — TW-1's design and the 2026-08-30 ruling; set aside because the founder's ruling is that the wire says what the thing is. *A mixed grammar, repointing only where `/v1/trips` already existed* — one repository speaking two grammars. *A copied implementation running beside the old* — two JPA mappings on one row and every fix landed twice. *Corrected suffixes on the new root* (`editing-session` for `edit-lock`) — a third vocabulary that weakens the equivalence proof; the four misnomers go to the vocabulary-housekeeping line. *Trip owns publish and the itinerary module reacts* — rejected by the model itself: a trip is never published.
- **Consequences.** Every future workspace route is declared under both roots until CM-5, and the twin test is the bridge's guard. The client's 45 old-grammar e2e files and 7 scripts migrate. `TripResponse` and `TripReadContractIT` retire. The glossary gains Publish and Preview and amends Trip and Itinerary in the founder's words; `08-object-contracts.md`'s wire table is amended; the old-diary-endpoints deletion line is aligned to CM-5.
- **Invalidating condition.** An app in a store calling `/v1/itineraries/**` before CM-5 → the sunset waits for its update lag, per ADR-008's own context. A second workspace-rooted grammar proposed for any reason → this ADR's same-handler rule is the test it must pass.
- **Amended 07/09/2026 at the CM-3 build (founder ruling, taken as a publish/visibility stop rule): unpublishing tolerates a trip with no itinerary object.** Decision (3) moved the client onto the itinerary module's `POST /v1/trips/{id}/unpublish`, which required a live object and answered `404 PUBLICATION_NOT_FOUND` without one — but a trip published by the *old* act has only the bridge flag and no object, so the new app could not unpublish anything published before this story or by any shipped app version (measured on the local stack: 295 published trips, 5 live objects). Unpublish now retires the object when there is one and clears the flag either way, answering `204`; publish was already mint-or-refresh, so republishing heals an old trip. **What this says about the arc:** the twin and equivalence proofs compare two *addresses* of one handler and are blind by construction to a difference between two *acts* — the old flag-flip and the new mint are different acts wearing one verb, and only a walk could see it. CM-5, which moves the readers onto the object, inherits the question of what a published trip with no object should mean once the flag is gone.
- **Amended 07/09/2026 at the CM-3 build (code review): publishing refuses while another member holds the editing session.** The old route has always called `requireSessionFreeForLifecycle` before publishing; the itinerary module's route — built dark at CM-1 with no client — never did, so decision (3)'s move of the client onto it would have silently dropped the invariant and let an owner freeze a plan somebody else was mid-edit on. It now refuses with the same `409 EDIT_LOCKED` and the same holder-naming message, with the owner's own session still allowed. **The seam this exposes, and it generalises past this story:** the twin and equivalence proofs compare two *addresses* of one handler, so anything that is two *implementations* of one verb — publish is exactly that — is invisible to them by construction. **When a story repoints a client at a different implementation of the same act, diff the two implementations, not just the two paths.** The mechanism is `TripEditingSession`, a two-line interface in `common.authz` implemented in the itinerary module over `EditLeaseService` — the `TripWritability` shape, chosen because a new-world module may not import the old world and reading `edit_lease` in raw SQL from the trip facade would have widened ADR-035's waiver by a table (ADR-002).
- **Amended again 07/09/2026, before CM-3 merged (founder decision): decision (3)'s CLIENT half defers to CM-5; the server half ships now.** CM-3 pointed the app at the itinerary module's publish and unpublish, and both defects the story found lived there — the missing editing-session guard and the strict unpublish. With `preprod` and `prod` deferred (epic-map line 227), **`dev` is the only running environment and `founders.largata.com` is wired to it**, so a story whose sole traveler-visible change is the publish act carries its whole risk on the one live surface, with no rung behind it and a repair window as long as the arc. The client therefore stays on `POST /v1/itineraries/{id}/publish|unpublish` — the act the shipped app already calls — which makes CM-3 a pure grammar change nothing a traveler touches can perceive. **The itinerary module's routes keep both fixes and stay dark**, so CM-5 inherits a guarded, tolerant publish rather than the one CM-3 found. The principle worth keeping: *when the only environment is the live one, prefer shipping the change nobody can reach over shipping the change you have tested* — the walk proved the acts correct, and deferring them was still the cheaper posture.

### ADR-038 — Module conventions for the modular monolith: slices when layers outgrow, an allowlist guard per module, AFTER_COMMIT events, refusals published *(amends ADR-002's "by ID + service interface" into api-only with no entity crossing; records schema-per-module as a rule not yet applied; settled once for every module at TW-1's grilling, applied first by CM-4 and TW-1)*

- **Status.** Accepted · 07/09/2026 (founder — grilled at TW-1, grill-with-docs, round 2; record `docs/plans/TW-1-trip-workspace-module/grilling.md`).
- **Context.** TW-1's design named five rules for the module boundary and the content-module boundaries line amended its folding rule; both left the guard form, the layout threshold and the event mechanism open, each "to be chosen once for every module". The founder ruled they be settled at TW-1's grilling rather than at the boundaries story's, so that the largest module was on the table when the conventions were chosen.
- **Decision, as one piece.** **(1) Cross-module calls through `api` only**: interfaces and view records; no JPA entity ever crosses; an `api` names only its own types and `common`'s; `exception/` is published surface. **Amended 08/09/2026 (CM-4, founder ruling): this is a standing rule, general and forward-binding — every module talks to every other module through an `api` call or an event, always, and for every module added from here.** It was written as a convention each story applies; it is now a property each story must already satisfy, asserted by the meta-test in (3) rather than by a reader auditing. **The rollout is staged and named, because the tree is not there yet:** five modules are under the rule today (`diary`, `postcard`, `publication`, `trip`, `place`); four are deliberately outside it and must never be asked for a guard (`common` and `identity` as shared kernel, `media` as shared infrastructure, `ws` as transport — this ADR's own classification); seven are **owed with a named trigger** (`chat`, `poll`, `invitation`, `join`, `health`, `report`, `verification`, all at **TW-1's merge**, because they reach into the old world today and a guard written now would need an immediate by-name exemption — destroying the very property the rule exists to establish); and `itinerary`, `workspace` and `membership` are on neither list, being the god module TW-1 and CM-5 dismantle. A module invented tomorrow is classified deliberately or fails on its first build. **(2) Layout**: organize by layer while every layer folder stays scannable (around ten files); fold into feature slices with the layer as filename suffix when one outgrows that — postcard is layers, trip is slices, the same criterion at two sizes. **(3) The guard**: a per-module ArchUnit allowlist whose front door is `api..` and `exception..`, with sabotage checks that the module is seen and the predicates select something, plus one meta-test asserting every module has a guard. **Named at CM-4 (08/09/2026), because the story shipped two techniques and P9 asks that a pattern be named: how a module IMPLEMENTS its `api` is chosen by whether entities would otherwise cross, and nothing else.** A service whose cross-module methods already return `api` records or primitives **implements the interface directly** (`TripService implements TripApi`, `ItineraryObjectService implements PublicationApi`) — an adapter there would be a Middle Man, delegation adding nothing. A service whose methods return **entities its own module needs internally** gets a **package-private adapter in `adapter/`** (`DiaryFrontDoor implements DiaryApi`), which does two things direct implementation cannot: it narrows the return type at the boundary — `Diary` becomes a `UUID`, `DiaryDay` becomes a `DiaryDayView` — without forcing the module's internal callers onto the narrowed shape, and it keeps the implementing class package-private, so the concrete service is unreachable by construction rather than only by the guard. **The tell for which to reach for: does a caller inside the module need the entity the cross-module method returns?** If yes, adapter; if no, implement directly. **(4) Events**: Spring `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`; a reaction never runs in the publisher's transaction; a failed reaction is logged at WARN with ids and not retried; an outbox only where a consumer's loss would corrupt data, with the trigger named per consumer; BEFORE_COMMIT only where a pair must be atomic, and then the cross-module write is recorded. **(5) No single transaction writes across a module line**, with **five** recorded exceptions that stand until their triggers: admission (the invitation's status flip and the membership row, pinned by test), destruction's five foreign-table deletes (until the FK drops), publication's flag bridge (until CM-5), **the diary delete, which destroys its postcards in diary's own transaction** (added 08/09/2026, CM-4), and — **added 08/09/2026 (TW-1)** — **the archive voiding a trip's pending invitations**. *Why it is an exception rather than an event, having briefly been one:* TW-1 broke the archive→invitation cycle by publishing `TripArchived` and reacting in invitation, and first wrote that reaction AFTER_COMMIT with its failure logged — which is the transport ADR-030 decision 3 asks for, and which **silently ended the act's atomicity**: the archive commits, the voiding then fails, and an archived trip goes on holding PENDING invitations, recruiting members into a workspace nobody can edit. That is the state the requirements' user story 4 exists to prevent, and it is the *same* trade this rule already refused for admission, where an accepted invitation with no member was judged the worse state. Caught at code review, not at build. The reaction is now `BEFORE_COMMIT` with `voidPendingInvitations` on `MANDATORY` propagation — so the cycle stays broken (membership names no invitation type; the coupling is an event) while the two writes remain one act, and **the propagation is what makes the fix hard to lose**: moving the phase back leaves no transaction to join, so the listener throws rather than half-succeeding. `ArchiveVoidsInvitationsAtomicallyTest` pins both halves. **Trigger for dissolving it:** the same FK-drop story as destruction — invitation rows hang off the workspace, so an asynchronous void has the same problem the diary delete does. *The reason matters more than the exception, because the obvious fix is wrong:* CM-4 planned to make it a `DiaryDeleted` AFTER_COMMIT event and reversed that at its grilling on measurement. The postcard→diary references are **live foreign keys** (`postcard.diary_id`, `postcard.diary_day_id`, `diary_day.diary_id`, the first declared NO ACTION deliberately), so **the asynchronous delete cannot even commit today** — Postgres refuses it — and making it an event would require dropping the key first. Measured against the readers, a failed reaction after that drop would not be invisible garbage but a **traveler-visible ghost**: the Home feed renders the orphan in full (every feed query selects from postcard alone with no diary join), tapping it 404s `DIARY_DAY_NOT_FOUND`, and the profile denies it exists. **So the principle: rule 5 exists so modules are not coupled by transaction in a way that blocks extraction, but the foreign key already couples these two at the schema level — the shared transaction adds no coupling the schema does not impose.** Decoupling the transaction before the schema would mean building a transactional outbox purely to restore a guarantee just destroyed. The genuine decoupling step is dropping the key, which is rule (6)'s work. **Trigger: the FK-drop story**, which is also where this arc's first event lands. **(6) Schema per data-owning module: recorded, not applied** — no named schema exists, and the measured `pg_dump` trap makes every inbound key a hazard the day one does; trigger the FK-drop story or the first extraction rehearsal. **(7) The boundary is enforced by the build**: the guards now, Spring Modulith's `verify()` once the god module is gone.
- **Alternatives rejected.** *Layer folders for every module regardless of size* — reproduces the flat god-module shape being escaped. *The `.internal.` marker* — one rule for the tree and Modulith's convention, but its failure (a package created outside `internal/`) is silent, where the allowlist's (a module with no guard) is caught by the meta-test. *A message broker* and *events for authorization reads* — ADR-035's triggers stand; an eventually-consistent membership check is a security hole. *Per-module Flyway beans* — Boot's condition silently disables the auto-configured Flyway.
- **Consequences.** CM-4 applies (1), (3) and (4) to the three content modules and converges their guards on the allowlist form; TW-1 applies all seven to trip; the two existing ws listeners are already the event shape; the seven per-module guards in the tree today keep their sabotage checks.
- **Invalidating condition.** A consumer whose lost reaction corrupts data → an outbox for that consumer, never for all. A second deployable process consuming events → ADR-035's broker question reopens. A layer folder in a layered module passing ten files → it folds.

### ADR-039 — The modular-monolith standard: adopted whole as the rule every module is held to, measured against the tree, three deferrals each carrying a trigger *(amends ADR-002's boundary rule and ADR-038's conventions; applies ADR-038's "schema per module — recorded, not applied"; gives ADR-038 rule 4's registry deferral a trigger; attaches the fork direction and the two read-surface modules to CM-5)*

- **Status.** Accepted · 09/09/2026 (founder, in conversation, after the standard was measured against the tree module by module: *"i'm pretty sure i want to adapt those standards right now when we talk about modules"*).
- **Context.** ADR-038 settled conventions at TW-1's grilling with the largest module on the table, and left several things recorded rather than applied or deferred with a trigger: schema per module, the event publication registry, Modulith's `verify()`. With TW-1 merged (2026-09-08) the tree is fifteen modules beside the old package, and CM-5 — the story that deletes that package and mints two read-surface modules — is next. The founder brought a written standard for a modular monolith and asked how the tree's modules should be coupled and decoupled under it. It was measured first (below); most of it was already true, three rules were not, and one rule would have been broken by CM-5's own text.
- **The standard, as adopted.** One clarification governs every clause: *through api* means each module's published Java `api` — interfaces, commands and queries, DTOs, events, exceptions — called in-process; never HTTP between modules in one deployable, which gives the latency and failure modes of microservices without the independence. **Structure.** Modules are cut by business capability, never by technical layer. Each has an `api` others depend on and internals nobody else touches. A tiny shared kernel holds true cross-cutting types (ids, the error model, security primitives); if it grows business logic it has become a coupling magnet. The root build owns versions, the formatter and static analysis, so every module gets the same tooling. **Boundaries, enforced not documented.** A test fails the build on cross-module internal access and on cyclic dependencies. Each module owns its data: its own migration folder, no cross-module JPA relationship, no cross-module foreign key; another module's data is reached through its api, never by joining its tables. The dependency direction is explicit and acyclic. **Communication.** Synchronous: inject the other module's `api` interface and return DTOs, never entities. Side effects and fan-out: domain events through a publication registry, so a failed reaction is recorded and replayed rather than lost; prefer an event when the caller does not need the result. A transaction stays inside one module; cross-module consistency is eventual, through events. **Testing and CI.** A module's tests boot that module with its dependencies stubbed. CI builds only what a change affects. **Smells rejected at review:** a fat `common`, a cross-module entity reference, `@Lazy` to break a cycle, one module reading another's tables, a "temporary" cross-module HTTP call.
- **Measured against the tree, 09/09/2026, main sources.** *Met:* in-process api only (the only HTTP clients are outbound, to Resend and Photon); no `@Lazy`; no entity crosses a line among the five guarded modules; fifteen modules cut by capability. *Met with one exception:* the dependency graph is acyclic except `identity ↔ ws` and `identity ↔ media`, and both cycles have one cause — the request principal (`CurrentTraveler`, `Traveler`) lives in `identity.web`, so the `ws` and `media` controllers import identity while identity uses their fanout and photo services. *Not met:* nothing checks for cycles; `common` is 54 files and `common.authz` alone is 14 — `Membership`, `Role`, `AuthorizationGuard`, `WriteFence`, the writability and editing-session ports, four trip exceptions — which is the trip's authorization model wearing the kernel's name; 55 migrations sit in one folder; foreign keys cross module lines throughout (into `traveler` from eleven tables, into `workspace` from seven, into `itinerary` from five, into `diary` and `diary_day` from postcard); five transactions write across a line (ADR-038 rule 5); the root pom owns versions through the Boot BOM, and no formatter or static analysis is configured. *The cycle CM-5 would have created:* its line says fork starts from the itinerary object's snapshot, which puts `trip.fork` on `itinerary.api` while `itinerary` already depends on `trip.api` — TW-1 moved fork into `trip` when its source was a trip's live plan, and the source change flips its direction.
- **Decision, as one piece.** **(1) The standard above is the rule every module is held to from this date**, and every clause below is how this tree satisfies it, or when it will. **(2) The dependency direction is declared by each module's guard allowlist, and a cycle rule joins the guards.** The allowlist is the explicit dependency list the standard asks for; a README restating it would rot where the guard fails, so the guard is the declaration. ArchUnit's slice cycle rule lands before CM-5 opens, because CM-5's fork move is the first cycle it would catch; the two existing cycles are broken first by moving the request principal into `common.security`. **(3) `trip` never depends on `itinerary`.** Fork's *act* belongs to the itinerary module (ADR-037: forking is an act on an Itinerary), calling a `TripApi.createFrom(snapshot)`; `trip` keeps only the provenance row. Attached to CM-5. **(4) Discover and Home are composition modules** — `discovery` and `feed` — owning no table and no SQL. The data-owning module fences, pages and counts in SQL and exposes that as one api call taking the viewer's follow set or hidden-author set as a parameter (postcard's `feedPageOf` is the precedent); the surface composes cards from several apis and owns the wire contract. A module wrapping one call would be a Middle Man and is not minted. Where a lower module needs an upper one's data it declares a port the upper implements — `DiaryContents` implemented by postcard, `TripEditingSession` and `MembershipResolver` implemented by trip are the pattern. Both modules are classified under the rule at birth (ADR-038's meta-test). Attached to CM-5. **(5) The kernel shrinks to what the standard means by one.** `common.authz` dissolves after CM-5: membership, role, the guard, the write fence and the trip ports into `trip.api`; the audience fence into `identity.api`; `PublicationState` dies with the flag. `common` keeps error, id, tx, config, storage, security. This touches the authorization guard, so it runs the stop-rule gate; it is a relocation with no semantic change. **(6) Schema per module is applied, in two halves.** The cheap half — a migration folder per module through `spring.flyway.locations`, one Flyway bean, global version numbers (Flyway records name and checksum, not path, so existing files move safely; ADR-038's rejection of per-module Flyway *beans* stands) — is pullable at any story. The expensive half — the foreign keys — is ranked by what they couple: the keys into `workspace`, `itinerary`, `diary` and `diary_day` are the ones behind four of ADR-038's five transaction exceptions and go first; the eleven keys into `traveler` couple nothing but referential integrity and wait for the extraction that would need them gone. **(7) The publication registry is the adopted mechanism for every reaction whose loss must be replayed**, and it arrives with Spring Modulith at CM-5, when `verify()` can pass — a scheduling choice, not a technical one: the registry does not need `verify()` to pass, and the eviction listener on the epic map's registry line is the argument for pulling it earlier. Until then ADR-038 rule 4's WARN is owed on the three listeners that lack one. The trigger that makes the registry mandatory rather than adopted is the first projection table — a feed or discovery index fed by events — because a lost event there is a card missing forever, the traveler-visible ghost ADR-038 already refused. **(8) Transactions inside one module is the rule, reached by a path.** ADR-038's five exceptions stand as recorded debt: the flag bridge dies at CM-5; destruction's five deletes, the diary delete and the archive voiding invitations dissolve with the FK drops in (6); admission stands, argued — an accepted invitation with no member was judged the worse state, and an eventually consistent admission creates it. **(9) `verify()` and per-module tests arrive together at CM-5**, when the old package is gone and the module model can be declared; until then a module's integration tests are scoped by package (`-Dit.test='com.largata.<module>.**.*IT'`). Modulith treats every nested package as internal by default, so at that point each module's `api` package is declared a named interface, or its types move to the module root — a CM-5 detail, recorded so it is not rediscovered. **(10) The seven modules owed a guard** — `chat`, `poll`, `invitation`, `join`, `health`, `report`, `verification` — had TW-1's merge as their trigger, which fired 2026-09-08; they are pullable now and each is small.
- **Three deferrals, each with a trigger, and why they are deferrals rather than refusals.** *One build module per business module, with a bootstrap module.* It buys compile-time enforcement where the guards enforce at test time, which is a real gap. For one deployable, one founder and several agents it is seventeen poms and no independence gained; **trigger: a second human contributor, or a build whose time path-gated CI can no longer hide.** Affected-only CI and CODEOWNERS per module ride the same trigger — a CODEOWNERS with one owner is a no-op today, and CLAUDE.md's path-ownership rule covers agents running in parallel. *Package-private by default.* Java package visibility cannot span the layer sub-packages ADR-038 chose, so the allowlist guard is the enforced thing; after CM-5, trip's internals drop `public` where the layout allows, since the legacy exemption is the only reason they carry it. *A formatter and static analysis in the root build.* Not configured, and the weakest of the three: the only real cost is the one commit that reformats the whole tree, which collides with any long branch in flight. **Trigger: a single formatting commit right after CM-5 merges**, when no long branch is open.
- **Alternatives rejected.** *Adopting the standard verbatim, deferrals included.* Seventeen Maven modules and package-private-across-layers would each cost a restructure of a tree that satisfies the intent by other means already measured. *Adopting it as guidance rather than rule.* A convention each story applies is what ADR-038 was, and CM-4 had to promote its own rule 1 to a standing property for the same reason: a rule nobody asserts is a reader's audit. *A `content` umbrella for the read surfaces.* Rejected at CM-1 for the objects and rejected here for the surfaces — Discover and Home compose different apis and grow different logic (tagging, promoted slots, engagement, the diary card). *The feed in `postcard` and discovery in `itinerary`.* The query lives with the table, but the composition does not; a content-object module carrying follow sets and author cards is the smell the standard names.
- **Consequences.** CM-5's epic-map line carries (3) and (4). Five epic-map lines carry (2), (5), (6), (10) and the deferrals. The registry line's trigger is amended per (7). CLAUDE.md's module rule and `04-architecture.md`'s boundary rule point here. `06b` §11 is unchanged: it measures the tree, and this ADR records what the tree will become.
- **Invalidating condition.** A second deployable process → the deferrals' triggers fire together and this ADR is re-read as a service-extraction plan. A module needing another's data faster than an api call allows → a projection in the reader, fed by events through the registry, never a join.
