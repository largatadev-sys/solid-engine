## Decisions

### ADR-001 — Offline posture: read-cache + queued writes now; offline-first as declared target
- **Status.** Accepted · 12/07/2026
- **Context.** Users are travelers — dead zones, airplane mode, foreign SIMs. Full offline-first means a local DB + sync engine + conflict resolution for collaborative data — a foundation-scale commitment.
- **Decision.** v1: itinerary, ledger, diary readable offline via a local cache; edits queue and sync on reconnect. Offline-first is the declared long-term target. Design obligation now: the mobile data layer sits behind a repository/local-cache abstraction from day one; no raw API calls in UI code.
- **Alternatives rejected.** Online-required — fails the core usage context. Offline-first now — months of sync/conflict engineering that validates nothing the alpha tests.
- **Consequences.** Read access survives connectivity loss cheaply; the abstraction is the graft point for the future sync engine. Queued writes accept server-side ordering.
- **Invalidating condition.** Post-validation data showing engagement loss in low-connectivity contexts, or conflict-rate pain → begin the offline-first migration on the prepared abstraction (a real migration; the abstraction makes it possible, not free).

### ADR-002 — Modular monolith on the aggregate boundaries; one PostgreSQL; object storage for media
- **Status.** Accepted · 12/07/2026
- **Context.** Many domain moving parts suggested microservices/multiple DBs. But: alpha 2–3k users (orders of magnitude inside one Postgres's headroom), one developer + agent, and the Workspace aggregate demands transactional consistency (INV-7/8) — splitting the ledger into a service turns a money ledger's invariants into a distributed-consistency problem.
- **Decision.** Modular monolith; modules = the domain aggregates; interaction by ID + service interface only; one PostgreSQL as the transactional home; S3-class object storage for media; the ledger as a bounded submodule with a designed promotion path.
- **Alternatives rejected.** Microservices — all cost, zero benefit at this scale; they solve team-scaling problems this team doesn't have. Multiple databases — breaks the transactional home for no load reason.
- **Consequences.** One deploy, one DB to operate, transactions where the money is. Any module extracts later along its existing interface — addition, not rewrite.
- **Invalidating condition.** A measured post-validation signal: sustained load approaching single-instance limits, or one module's deploy cadence diverging hard → extract that module. Never calendar-triggered.

### ADR-003 — Authorization: single chokepoint guard now; RLS as the post-validation second wall
- **Status.** Accepted · 12/07/2026
- **Context.** The Trip Workspace is the isolation boundary; a silent leak is the product's worst failure. Per-service checks fail by omission; row-level security is strong but the visibility logic (public/unlisted/published-state/diary-grants) is object-shaped and painful as row policies.
- **Decision.** One authorization guard resolves (user, workspace) → Membership before any workspace-scoped operation; service methods require the resolved Membership as a parameter — unbypassable by structure. RLS adopted later as defense-in-depth (purely additive beneath the guard).
- **Alternatives rejected.** Per-service checks — safety by vigilance. RLS-only now — cost and policy complexity without v1 benefit while the guard stands.
- **Consequences.** A forgotten check is a compile error, not a leak; one rule the agent can be held to mechanically.
- **Invalidating condition.** Any app-layer leak → RLS immediately. Otherwise the post-validation hardening phase adopts it on schedule.

### ADR-004 — Mobile: React Native + Expo
- **Status.** Accepted · 12/07/2026
- **Context.** Solo developer, first mobile app, both iOS and Android at launch (hard constraint), strongest recent skill React/Next.js.
- **Decision.** React Native + Expo (EAS builds, dev-build workflow); TypeScript throughout; the future web surface shares the React ecosystem.
- **Alternatives rejected.** Flutter — new language/ecosystem, zero transfer, no web sharing. Kotlin Multiplatform — shares logic, not UI: still two UIs. Two native codebases — infeasible solo.
- **Consequences.** One codebase, maximum skill transfer. Share-sheet capture requires a native extension → Expo dev builds, not plain Expo Go.
- **Invalidating condition.** A required native capability dev-builds cannot reach, or profiled framework-attributable performance pain in core flows.

### ADR-005 — Backend: Java + Spring Boot
- **Status.** Accepted · 12/07/2026
- **Context.** The developer's primary specialty; the domain needs a strong transactional story (INV-7/8) and a mature security layer for the guard.
- **Decision.** Spring Web · Spring Security (resource server + guard) · Spring Data/JPA + Flyway · @Transactional aggregate operations · @Async unfurler worker.
- **Alternatives rejected.** Node/TypeScript backend — one language appeal, but trades away the deepest expertise where correctness matters most. Anything new-to-learn — the learning budget is spent on mobile.
- **Consequences.** Fastest correct path on the backend; the new-skill risk is isolated to the client.
- **Invalidating condition.** Nothing foreseeable at this scale; revisit on team change.

### ADR-006 — Auth: Firebase Auth (managed identity); backend as OAuth2 resource server
- **Status.** Accepted · 12/07/2026
- **Context.** Google + Apple sign-in needed (Apple mandatory on iOS alongside any social login), email verification for invites, reset/refresh/revocation. Hand-rolling ≈ weeks of security-critical work that tests nothing.
- **Decision.** Firebase Auth owns credentials and sign-in; Spring validates its JWTs as a standard resource server; the domain keeps its own Traveler keyed by Firebase UID — the provider owns credentials, we own identity.
- **Alternatives rejected.** Hand-rolled JWT auth — undifferentiated security burden. Auth0/Cognito/Supabase — viable peers; Firebase wins on RN SDK maturity + free tier + smallest integration surface.
- **Consequences.** Sign-in is configuration; the UID-keyed indirection is the designed exit from the provider.
- **Invalidating condition.** Pricing/lock-in pain at scale, or a compliance need to own credentials first-party.

### ADR-007 — Unfurler: in-process async worker; build Tier 1+2; buy as fallback
- **Status.** Accepted · 12/07/2026
- **Context.** Items arrive as links; metadata must be fetched server-side. Tiers: 1 = Open Graph/Twitter-card/title; 2 = JSON-LD (schema.org); 3 = per-site parsers (fragile, deferred).
- **Decision.** An async worker inside the monolith; Tier 1+2 built in-house; results cached by URL; graceful degradation to bare link always; items enrich asynchronously. Commercial unfurl APIs recorded as the buy-fallback.
- **Alternatives rejected.** Separate unfurler service — deployment overhead without load justification. Buy-first — Tier 1+2 is small, and the spike may show it suffices.
- **Consequences.** Zero partnership dependencies for v1; the same item pipeline later accepts webview capture (v1.5) and provider APIs (future).
- **Invalidating condition.** The register #8 spike (or production) showing heavy bot-blocking / thin coverage on must-have sites → buy-fallback behind the same interface, or targeted Tier 3 parsers.

### ADR-008 — API versioning: path-versioned /v1, additive-only within a version
- **Status.** Accepted · 12/07/2026
- **Context.** Mobile clients cannot be force-updated; store review + user update lag means multiple app versions call the API concurrently for weeks.
- **Decision.** /v1 path prefix; strict additive-only evolution within it (new fields/endpoints only; clients tolerate unknown fields); /v2 only for a genuinely breaking reshape — expected never during alpha/beta.
- **Alternatives rejected.** Header versioning — invisible, easy to fumble in a mobile client. No versioning — no escape hatch for a true break.
- **Consequences.** Old app versions keep working; API evolution discipline is enforced at review.
- **Invalidating condition.** A domain-level reshape inexpressible additively → /v2 with a sunset window measured against real version-adoption telemetry.

### ADR-009 — Subscriptions: entitlement chokepoint at the register #14 split decision *(amended from "Epic 1")*; store billing (RevenueCat-class) at Epic 7
- **Status.** Accepted · 12/07/2026 · **amended 28/07/2026** (S1.8 grilling — the seam's ship moment moves from Epic 1 to register #14's decision)
- **Context.** The business model is subscription-based (two tiers: Free / Subscriber). Launch is free; charging during alpha would contaminate validation, and TestFlight subscriptions are sandbox-only. Apple/Google require their in-app purchase systems for digital subscriptions (15–30% platform cut).
- **Decision.** Build the seam now, the feature later: one entitlement service — can(traveler, capability) — ships in Epic 1 returning full access; every potentially-gated feature asks it. Epic 7 (post-validation, pre-beta) integrates store billing via a RevenueCat-class wrapper (products, purchase/restore, receipt validation, webhooks → entitlement state). Standing rule: the split gates capabilities, never a user's existing data.
- **Amendment (28/07/2026 — S1.8 parked at its grilling; owner call).** The "ships in Epic 1" clause is superseded. E1 reached S1.8 with register #14 undecided, and the owner refused mechanism-before-policy: a full-access seam has zero real callers, the shape S1.1's spec already rejected ("a seam with zero callers proves nothing"), and its acceptance criteria cannot be made falsifiable. **The seam now ships at register #14's decision moment** (unchanged: before Epic 7) — born wired to the first genuinely-gated capabilities, so it never exists without real callers and real policy. Until then: no entitlement code exists; the no-inline-tier-checks rule stands; and **every story spec from S1.9 on records a one-line candidate-capability note** — the acts that pass the **potentially-gated test** (a *capability*, not access to existing data · *grows the traveler's footprint* — creates entities or consumes a meterable resource · *not governance* — role-authority acts are membership semantics, not tier features). The retrofit sweep this ADR originally feared is answered by that accumulated map, not by early code. First two candidates, recorded at the grilling: `itinerary.create` (traveler-scoped) and `invitation.send` (workspace-scoped — the `context?` parameter's caller). **Added at S4.28 (22/08/2026):** `invitation.link` — issuing a trip's shareable join link. It passes the test on all three counts: it is a capability rather than a read of existing data, it grows the footprint (a link is the door through which unbounded strangers arrive), and it is not governance — *approving* a request is owner authority and stays out of the map, while *minting and sharing* the link is the metered act. Note the pair is deliberate: `invitation.send` meters the trip asking one named person, `invitation.link` meters the trip opening a door to anyone.
- **Alternatives rejected.** Billing at launch — contaminates validation and is sandbox-only anyway. No seam until Epic 7 — retrofitting gating across fifty stories *(amendment: mitigated by the candidate-capability map; the seam still precedes Epic 7)*. Stripe-only in-app — store rejection for digital subscriptions. *Added at the amendment:* shipping the seam bare in E1 — process theater satisfying this ADR's letter while abandoning its point; wiring two structurally-chosen test-load call sites in E1 — recommended at the grilling, declined by the owner as mechanism before policy.
- **Consequences.** Monetization becomes a two-way door: Epic 7 is pure addition behind an existing switch. Pricing must absorb the platform cut. *(Amendment: the switch itself now arrives with the split decision rather than years before it.)*
- **Invalidating condition.** A founder decision to charge during alpha (pulls Epic 7 into launch scope — revisit validation criteria with it), or a multi-tier model (the entitlement service grows from boolean to capability-set — the seam absorbs it). *Added at the amendment:* a pre-#14 story needing a real gate → that story ships the seam early, wired to its capability.

### ADR-010 — Platform sequencing & mobile build pipeline: Android-first; local builds, no EAS
- **Status.** Accepted · 13/07/2026 · partially supersedes ADR-004's build-workflow clause
- **Context.** Apple Developer overhead (US$99/yr + macOS toolchain) is real cost before validation; the RN/Expo single codebase makes sequencing a distribution decision, not architecture.
- **Decision.** Android first at launch; iOS activates once Android validates. Launch builds run locally (Expo prebuild + Gradle, signed AAB), uploaded manually to the Play Console; Play internal testing is the pre-release track. **EAS is the declared later adoption** — triggers: the iOS activation (local iOS builds need macOS the developer doesn't have; EAS is the recorded answer, no Mac purchase), or Android release cadence making manual builds a real cost.
- **Alternatives rejected.** Both platforms at launch — pays Apple's cost pre-validation. EAS — a paid cloud dependency the Android toolchain doesn't need.
- **Consequences.** The alpha cohort is Android-only (recruiting constraint in iOS-heavy markets, recorded). Sign in with Apple defers to the iOS phase.
- **Deferred decision at the iOS trigger.** Local iOS builds require macOS + Xcode — activating iOS means acquiring a Mac or reintroducing a cloud build service for iOS only.
- **Invalidating condition.** Validation showing the Android-only cohort is unrepresentative, or a moment requiring iOS presence → pull the activation forward and resolve the build path then.

### ADR-011 — The phased authorization guard: chokepoint in `common/authz`, membership lookup behind a resolver seam
- **Status.** Accepted · 16/07/2026 (S0.3 grilling) · extends ADR-003
- **Context.** ADR-003 fixed the pattern (guard resolves membership; service methods require the resolved `Membership`), but the first domain endpoint (S0.3) arrives before the Workspace exists — and the guard's future data owner (workspace) and first consumer (itinerary) would otherwise form a reference cycle.
- **Decision.** Guard + `Membership` value type live in `common/authz` with the permanent signature `requireMember(traveler, itineraryId) → Membership`; the lookup hides behind a one-method `MembershipResolver`. S0.3 ships an owner-based resolver; S1.1 replaces it with the workspace module's row-backed resolver and backfills workspaces for pre-E1 itineraries. The seam that must never be retrofitted is the signature and call-site discipline, not the storage. (`Membership` is not unforgeable — the guard defends against *forgetting*, not deliberate fabrication.)
- **Alternatives rejected.** Seeding the workspace module early — an unspecced module and an immediate cycle. Pulling S1.1's tables into S0.3 — re-litigates ratified scope. Guard calling `ItineraryService` — the swap lands inside the Full-rigor chokepoint, and `common` points at a module.
- **Consequences.** A forgotten check stays a compile error from the first domain endpoint; the S1.1 swap happened behind the seam without touching call sites.
- **Invalidating condition.** Workspace↔Itinerary ceasing to be 1:1, or a second aggregate needing guard semantics the itinerary-keyed signature can't express → widen additively, superseding this.

### ADR-012 — PaaS: Railway (one project, three environments, Singapore); custom domains as the exit hatch
- **Status.** Accepted · 16/07/2026 (S0.4 grilling)
- **Context.** Artifact 04 fixed the shape (PaaS + managed Postgres, three environments) but not the vendor. Solo operator, pre-validation cost sensitivity, Docker deploy, users/founders in Asia; operator already runs a structurally similar app on Railway.
- **Decision.** Railway: one project, `dev`/`preprod`/`prod` in Singapore, per-environment backend (Dockerfile) + own Postgres 18 (explicit image tag), branch-tracked deploys gated on green CI, platform probe = `GET /v1/health`. Custom domains from day one (`api[-env].largata.com`) so every baked URL is vendor-independent — leaving Railway is a DNS re-point.

- **Consequences.** Familiar operations compound daily; the custom-domain seam is ADR-008's constraint applied to infrastructure.
- **Invalidating condition.** Real production data outgrowing snapshot-grade recovery (beta scale, ledger live) → PITR bar at post-validation hardening; sustained reliability pain → migrate along the domain seam.

### ADR-013 — Plans are day-indexed: Day + Activity structure; dates stay itinerary metadata
- **Status.** Accepted · 23/07/2026 (S1.3 grilling, founder-confirmed)
- **Context.** The original Itinerary Item carried a calendar date/time, making "Day 3" a projection of dates. The 07/18 mock plans by ordinal days (duration at create, day titles, empty days); itinerary dates are optional since S0.3; forking wants relative days — date-grouping collapses for undated plans and has no home for a day title or an empty day.
- **Decision.** The Itinerary aggregate gains a **Day** child (contiguous ordinal, optional title); **Activities** belong to a Day with manual sort order as the authoritative ordering (optional time-of-day is display metadata, local, timezone-free). Dates remain optional itinerary metadata; Day N's calendar date is derived, never stored. No span↔day-count invariant in MVP (S1.7 revisits). Entity noun becomes **Activity** (was Itinerary Item); `type`/`source` defer as columns to their first reader (E6/E4).
- **Alternatives rejected.** Date-anchored items — break for undated itineraries, hold no day titles or empty days, copy meaningless dates on fork. Dropping dates — ADR-008 forbids it and register #10 wants them.
- **Consequences.** `/v1` speaks `days`/`activities` permanently within v1 — accepted knowingly, even for E6's future unfurled hotels/flights. Ordinal contiguity is the aggregate's consistency job.
- **Invalidating condition.** Real demand for calendar-anchored planning (cross-timezone flights, calendar sync) → an optional per-activity datetime added additively beside the day structure.

### ADR-014 — MVP concurrency: single-writer itinerary edit lock (supersedes S1.3's last-write-wins)
- **Status.** Accepted · 24/07/2026 (S1.4 grilling, founder-ruled) · **amended 31/07/2026** (trip-surfaces reconciliation — subject-typed leases; ships at S4.9) · partially supersedes ADR-001 (plan writes leave the offline queue); ADR-008 waived for the S1.3 write endpoints, knowingly
- **Context.** S1.3 shipped last-write-wins with attribution; AC 7 pinned the absence of any conflict surface. Founder ruling 2026-07-24 after challenge: silent overwrites are unacceptable for MVP; live editing is the declared future, this lock its stopgap.
- **Decision.** Whole-itinerary lease lock: one row (holder + expires_at), acquired on entering any plan-edit surface, TTL ~3 min auto-renewed while editing, released on save/cancel, expiry self-heals abandonment. No force-take (owner included). Server-enforced on every plan write (membership guard first, then lease); the client modal is a response to a failed acquire, never a broadcast (pull-based clients).
- **Amendment (31/07/2026 — trip-surfaces reconciliation, founder-ruled; ships at S4.9).** The lease becomes **subject-typed** — `header | day | activity` — same per-row semantics: the activity lease guards an activity's edits and deletion; the day lease guards the day's title and deletion (never its activities); the header lease guards the itinerary fields. Adds are unguarded (they commute); add/delete **day** is owner-only *interim* (revisit: validation gate; ADR-008 waiver renewed); delete-day 409s while a contained activity is leased by another member; **reorder is version-checked** (stale → 409, never silently overwritten); the lease gains an additive, pull-based read surface for the advisory "being edited by" indicator — never presence, and the modal stays the enforcement. Supersedes both the whole-itinerary scope and this ADR's per-item-locks rejection, answering the recorded "partial protection" objection structurally. Full text in `04-architecture.md`.
- **Alternatives rejected.** Keeping LWW — rejected by founder ruling on the merits. Per-item locks — more bookkeeping, partial protection. Live editing now — presence/sync infrastructure the alpha doesn't test.
- **Consequences.** Offline plan-editing disabled (read-only offline); shipped /v1 write endpoints gain a rejection case (additivity waived while clients are founders-only); S1.3's AC-7 IT deliberately replaced; editing serializes per itinerary.
- **Invalidating condition.** Validation-gate evidence that serialization hurts collaboration, or live editing arriving → the live-editing backlog line supersedes this wholesale.

### ADR-015 — Traveler handle (@username): a unique, changeable label; the id stays the identifier
- **Status.** Accepted · 30/07/2026 (S4.0 grilling, founder-ruled) · supersedes the 2026-07-17 "no handles in the MVP" ruling; closes the epic-map handle decision ahead of its pre-S4.3 pin
- **Context.** S0.2 ruled the display name non-unique and never an identifier; the 07-17 UX reconciliation kept handles out of the MVP, registered for pre-S4.3 (discovery cards are the first surface rendering one). The S4.0 wireframes reintroduced the field and the founder pulled the decision forward with the full onboarding flow.
- **Decision.** Traveler gains a handle: 3–20 chars `a–z 0–9 _`, stored lowercase, globally unique case-insensitively, required at onboarding (collision-free prefilled suggestion), freely changeable, released immediately, reserved-word blocklist. **The handle is a unique label, never a key** — routes, FKs, and future profile URLs stay id-keyed, which is what makes free change safe. Availability check is an additive endpoint. Existing accounts carry NULL until they complete the profile step — client-routed, never backend-enforced.
- **Alternatives rejected.** No handles until S4.3 — superseded by the full-onboarding pull. Immutable/tombstoned handles — protects against a takeover vector the id-keyed rule already eliminates.
- **Consequences.** Display name stays the non-unique human label; uniqueness semantics get a pinning test.
- **Invalidating condition.** Impersonation/abuse via handle churn → cooldown/tombstone added additively. Vanity URLs → redirect-on-change semantics at that story; the id-keyed rule stands.

### ADR-017 — Publish: a binary visibility flip with a live rule-scrubbed projection; the audience ladder
- **Status.** Accepted · 31/07/2026 (S4.1 grilling, founder-ruled) · resolves register #11 · re-rules S1.9's archive sight and S1.3's `notes` semantics (ADR-008 waivers renewed) · retires `completed` as a gate
- **Context.** Register #11 accumulated snapshot-vs-transition, publish-from-creation (proposed twice), est-vs-actual, and the 2026-07-29 safety constraint: a published itinerary must not reveal that its traveler is currently away from home — binding the whole projection.
- **Decision.** Publish flips a binary `private → published` visibility fact on the one itinerary, orthogonal to the dormant lifecycle; the public surface is a live projection scrubbed by rule (INV-2 amended), never a copy. No lifecycle gate; owner-only; symmetric unpublish (hidden-not-deleted; forks survive). The absence rule: no absolute dates, lifecycle state, or stamps ever cross — duration derives from day count. The audience ladder: archived = owner only · private = owner + collaborators · published = everyone; archive dominates publish, unarchive restores the prior audience. Unlisted deleted; `friends_only` reserved additively for the friend graph.
- **Alternatives rejected.** Snapshot-publish — kills the live-derived cost, mints a second identity, makes publish side-effectful. Two modes — double semantics, no consumer. A `completed` gate — resurrects removed UI, can't classify dateless trips. Date opt-in — a consent surface for a fact with no consumer.
- **Consequences.** Publish stays side-effect-free (S1.7's race exemption holds); post-publish edits are instantly public (reviews-vs-moving-target recorded for S4.5); members lose sight of archived trips; empty publishes accepted; the dormant lifecycle ships untouched.

- **Amendment — the mask extends to writes** *(13/08/2026, S4.23 grilling, founder-ruled)*. The audience ladder's archived rung binds every door, not only reads: a non-owner member's **write** to an archived trip answers the same not-found mask as their read, and on that trip the mask answers **before** any finer permission refusal — a mask with a louder door beside it is no mask. The owner's writes keep the honest archived refusal (the trip legitimately exists for them); self-leave stays open (S1.9's rule); acts closed by archive-time voiding (offer/invite acceptance) keep their existing answers. Supersedes the write fence's pre-ADR-017 member posture ("an archived trip tells a member it is frozen"), which encoded the sight rules this ADR ended. ADR-008 waiver renewed on the standing founders-own-clients ground.

### ADR-018 — Publication status is one three-valued fact, and publishing freezes the plan *(supersedes ADR-017's decisions 1, 2, 5 and 12)*
- **Status.** Accepted · 01/08/2026 (founder, on sight of the shipped S4.1 build; confirmed and clarified 03/08/2026) · **built** — supersedes ADR-017 decisions 1, 2, 5 and 12. ADR-008 waived on the record for the wire break, the third time in this story, on the standing ground that the installed clients are the founders. own.
- **Context.** S4.1 shipped ADR-017's model — binary `private ⇄ published`, a live projection, post-publish edits flowing straight to the public page. Looking at the running app, the founder re-drew it: *"public and private are both published, public being the default. draft will be the status when you are still working on the itinerary… you cannot edit a published itinerary."*
- **Decision.** One three-valued publication status replaces the binary visibility fact: **`draft`** (traveler + collaborators, **editable**) · **`private`** (published, traveler + collaborators, **frozen**) · **`public`** (published, every onboarded traveler, **frozen**, and the default on publish). Transitions: `draft --publish--> public|private`, `public ⇄ private` while published, and **`unpublish` returns the itinerary to `draft`**, which is the only way back to editing. The freeze covers **the plan only** — title, destinations, description, Standouts, best time, days, activities — while membership acts (invite, remove, ownership transfer, archive) keep working, mirroring the archive fence's existing "acts on the plan freeze, acts on the relationship do not".
- **What it reverses.** ADR-017 decision 1 (*"post-publish plan edits flow to the public page; no versioning, no freeze"*) — publishing is now a freeze. Decision 2's vocabulary — **`private` changes meaning**, from *not published* to *published, restricted*, and `published` as a wire value is replaced by `public`. Decision 5 — unpublish no longer returns to a private-but-unpublished state; it returns to draft. Decision 12's ladder re-derives on three values plus archived.
- **Consequences, including the ones to weigh before building.** *(a)* Fixing a typo on a public itinerary takes the page **down** — a stranger holding the link gets not-found, and stars/comments/reviews hide with it (decision 5's hidden-not-deleted) — until it is republished. *(b)* Conversely, ADR-017's recorded reviews-vs-moving-target worry for S4.5 **dissolves**: a review can only ever land on a plan that cannot change under it. *(c)* The derived Est. Total can no longer drift while published. *(d)* `friends_only` (reserved for the friend graph) now overlaps conceptually with the new `private` — the friend graph story must say what the third tier adds. *(e)* The Trips chips' accepted Draft/Private overlap **disappears**: three mutually exclusive values need no overlap rule. *(f)* This is a **wire break, not an additive change** — `private` changes meaning and `published` is replaced — so it needs the same ADR-008 waiver S4.1 has already renewed twice, defensible only while the installed clients are the founders' own.
- **Naming, resolved 01/08/2026.** Publication status ships as a **new field `status`** (`draft | private | public`); the dormant lifecycle keeps `state` and stays invisible, so the two "draft"s never meet. `visibility` retires with the wire break. *(Was recorded as the open question blocking a build.)*
- **Invalidating condition.** A traveler who needs to correct a live itinerary without taking it down → the draft-changes/publish-update flow ADR-017 rejected as versioning, reconsidered with a real reader.

### ADR-022 — The Trip Workspace model: one home surface, one exclusive Draft Workspace, and the lifecycle presented as a soft lock
- **Status.** Accepted · 08/08/2026 (S4.17 grilling, founder-ruled) · supersedes ADR-014's 31/07 subject-typed amendment for plan editing (restores the original whole-itinerary scope, reshaped as a session) · a presentation layer over ADR-019/020 (both untouched) · resolves the epic map's parked "three surfaces over one plan" question · **decision (3)'s saving semantics superseded by ADR-023 (10/08/2026)** — edits now buffer and Save Changes commits; the two surfaces and the exclusive session stand · **decision (2)'s soft lock superseded by ADR-027 (15/08/2026)** — Edit Itinerary now edits in place in every unpublished state, and the editor renames to Itinerary Workspace
- **Context.** Three surfaces grew over one plan — the workspace overview (`[id]/index`), the planner (`days/index`), and the read-only day view (`days/[dayId]`) — and the parked question asked which should win. The founder brought the workspace mock set (2026-08-08, two frames of the draft editor, a finalize sheet, a finalized viewer, add/edit activity, plus parked poll frames): a single home screen per trip and a single editing screen behind Edit Itinerary. Separately: live collaborative sync does not exist, so the subject-typed leases permit simultaneous editing that neither party can see happening.
- **Decision.** (1) **Two surfaces replace three.** The **Trip Workspace** (viewer) is every own unpublished trip's opening screen in every lifecycle state — read-only presentation, the lifecycle ladder as its CTA rail (Finalize in the editor · Start Trip · Complete Trip · Publish routing into the existing publish flow), a quiet one-step "Step back", and the shared tab row. The **Draft Workspace** (editor, behind **Edit Itinerary**) owns all plan editing via the day-by-day accordion. Published trips keep their published view; archived shows the viewer with the unarchive banner. (2) **The lifecycle presents as a soft lock.** Ready and beyond render read-only; Edit Itinerary on a Ready trip fires `reopen` and enters the editor in one act. The hard freeze remains `published`'s alone — the domain rule of ADR-019/020 is untouched; this is presentation. (3) **The Editing Session.** Edit Itinerary acquires an exclusive whole-itinerary hold (an additive lease subject); other members see "being edited by X" with Edit Itinerary disabled; **Save Changes** ends the session and returns to the viewer — it persists nothing, since every edit already saved per action; back-exit and the TTL self-heal abandonment.
- **Alternatives rejected.** Keeping the subject-typed leases for the workspace — built and server-enforced, but without live sync two members editing different parts is blind co-editing; the founder ruled the exclusive session honest ("live editing for collaborators is not implemented here"). Cutting Save Changes — rejected; the founder kept it as the session's explicit end. Stubbing Complete/Publish on the new viewer — rejected: both are shipped acts, and the surfaces that carried them are being retired, so stubbing would regress live features.
- **Consequences.** The planner, day-view and old-overview routes retire (their references migrate: S4.15's greyed CTA, publish-success's back link, the preview's published-state button). The workspace is single-writer while a session is held — an abandoned session blocks everyone until the TTL clears it, accepted knowingly. The activity form culls Description / Creator Tips / Photos / Move-to-day (wire fields stay additive; the orphaned-capability consequences live on the epic-map backlog). Drag-to-reorder un-parks (the arrows graduate; the version-checked PUT was built for this). Ongoing/completed badges and Step back ship as named deviations — those states have no mock frames.
- **Invalidating condition.** Live editing arriving (ADR-014's own condition) → sessions dissolve into presence and the exclusive hold goes; or validation-gate evidence that exclusivity blocks real collaboration → the subject-typed leases return from the shelf.

### ADR-023 — Plan edits buffer in the Editing Session; Save Changes commits via one version-checked bulk save *(supersedes ADR-022 decision 3's saving semantics; the surfaces and the session stand)*
- **Status.** Accepted · 10/08/2026 (S4.18 grilling, founder-ruled) · reverses ADR-022's *"Save Changes persists nothing"* on the founder's defect report from the running S4.17 build; ADR-014's lost-update settlement re-answered at the wider window buffering opens
- **Context.** ADR-022 kept per-action persistence and made Save Changes the session's end — a button whose label promises gating it does not do. The founder reordered activities, pressed back without saving, and found the change already persisted: leaving without pressing Save reads as discarding when it is not. Two fixes were weighed openly — relabel to `Done` (cheap, honest, keeps per-action crash-safety) or buffer for real — and the founder chose buffering. Also at decision time: the app holds no local persistence of any kind, and activity-photo upload is already dead UI (the S4.17 cull), so neither a crash-surviving draft nor a photo-staging exception had existing machinery to lean on.
- **Decision.** (1) **Edits stage; the server sees nothing until Save Changes.** The seven plan ops (append/rename/delete day, create/edit/delete activity, reorder) mutate a local draft of the plan — a value, not an op log — initialized when the session opens. The activity form stages into the same draft across its navigation. (2) **One transactional bulk save.** `PUT /v1/itineraries/{id}/plan` replaces the plan document wholesale, reconciled by id, holder-only, all-or-nothing; Save Changes = commit + release + return to the viewer. Back-exit confirms, then discards. (3) **The save is version-checked, never last-write-wins by default.** A `planVersion` bumped by every plan-document write — the bulk save and the still-live per-action endpoints old clients use — rides the request; a stale base refuses with a named code, and the refusal offers two explicit choices: discard-and-reload, or an overwrite that re-submits against the current version (explicit, attributed, race-safe — one endpoint semantic, no force flag). (4) **Crash loss is accepted.** Process death costs the buffer; the mitigation (a persisted draft) is parked with a trigger rather than built. (5) **History is derived by diff.** The server diffs committed vs staged plan at save and emits the same typed entries per-action capture wrote, attributed to the saver; staged-then-undone churn never becomes history.
- **Alternatives rejected.** Relabeling to `Done` — honest about the wrong thing: the founder wants the promise kept, not corrected. Last-write-wins — reopens the wound ADR-014 closed, in a wider window. A client-shipped op log for history — the server should derive history from state it can verify, not from a client's narration. Local draft persistence — the app's first storage layer plus a reconciliation model, smuggled into a labeling fix. Staging photos — the pending-media state machine ADR-021 already rejected, for a surface that currently has no UI.
- **Consequences.** Other members read the last-*saved* plan for the whole session — a longer stale window, accepted knowingly (the advisory "being edited by" already covers it). A crash loses a session's work where per-action saving lost nothing — accepted, parked mitigation. The per-drop stale-reorder retry machinery retires; its version check graduates to the whole plan. The per-action endpoints stay live under ADR-008 and bump `planVersion`, so old and new clients coexist honestly. S4.10 inherits diff-derived history — capture cannot be backfilled, so this granularity decision is permanent for entries written from here on.
- **Invalidating condition.** Live editing arriving (the condition ADR-014 and ADR-022 already share) → the buffer dissolves with the session into presence + sync. Real reports of crash-lost work → the persisted-draft line un-parks. Travelers repeatedly hitting the stale-save refusal → the exclusivity/TTL balance gets revisited before any merge UI does.

### ADR-024 — The Diary is a per-traveler postcard stream derived from activities *(the shared-album model retires; INV-2a and INV-5 amended)*
- **Status.** Accepted · 11/08/2026 (S3.1/S3.4 grilling, founder-ruled) · reverses the 00-brief's "Diary is a first-class object — the shared-album model" and canon's contributor-grant mechanics · register #13 re-pointed, not resolved
- **Context.** Canon defined Diary as a shared album: one author-owner, contributors joining by the owner's consent (INV-2a), entries accreting, published as a unit. The founder's 08/11 mock and his own definition described a different object — *"a personal post, like a postcard, derived from an activity of an itinerary; the owner of the diary is the traveler"* — with no contributor concept anywhere in it. The two could not both be the domain model, and the story that builds diaries (S3.1, re-cut from an S4.2 ask at this grilling) needed the answer first.
- **Decision.** (1) **Diary** = one traveler's collection for one trip; **Diary Entry** = one activity-derived post (a postcard: 1–5 photos + optional caption). (2) **Contributor grants are deleted** — INV-2a narrows to *a diary has exactly one author; only the author writes*. INV-5 becomes: every entry belongs to one traveler's diary for one itinerary and derives from at most one activity, whose title/day/time it **snapshots at post time** (provenance nullable — plan edits never rewrite a postcard). (3) "One itinerary → many diaries" survives as **one per traveler**. (4) **No diary table** — the Diary is a projection over entries (the Gallery/Highlight precedent); diary-level state arrives additively at its first reader (S4.2's publish). (5) **Author-only visibility** until the story that owns each widening: the profile is the ruled surface (register #13's standing answer), co-traveler and public exposure are deferred acts, and INV-2's absence rule is satisfied structurally in the meantime. (6) The shared-album *need* is partly re-homed: the **Photo Dump** (S3.4) is the member-shared pool; a dump photo selected into an entry is **copied**, so dump deletion never reaches a diary — and the consent question that stores up (another member's photo living on in my diary) is a recorded must-answer for S4.2 before any diary is visible beyond its author.
- **Alternatives rejected.** Keeping the shared album — nothing in the founder's product needs co-authored diaries (the group's shared thing is the dump; the diary is the *personal* perspective, and "independent lived perspectives on the same plan" gets stronger with one per traveler). A global profile stream with trip tags — makes Highlights a filter query and trip-grouping an afterthought; the per-trip collection keeps S4.2 a coherent projection. Live-linking entries to activities — an edit made for unrelated reasons silently destroys a traveler's memory (the append-only-ledger reasoning, applied to memories). Minting the diary table now — a row with no reader, the mechanism-before-reader shape this repo refuses by default.
- **Consequences.** S3.2 ("entries: text + geotag") dissolves — free-standing entries and the geotag park. S3.1 re-scopes to the capture story; S4.2 stays parked behind diary-publish and inherits the consent must-answer plus register #13. E3's line re-reads accordingly; the day-execution machine the mock drew around the capture links is backlogged separately. Media: a diary-entry photo kind with an author-only audience; entries own their bytes.
- **Invalidating condition.** A real demand for co-authored trip records → revisit as a *new* surface over the dump + entries, not by resurrecting grants. S4.2 finding diary-level publish needs state → the diary table arrives there, additively, as designed.

### ADR-025 — Postcards share individually to a public home feed *(per-entry opt-in; dump-implies-consent; independent of trip publish; the absence rule re-grounded on consent — INV-2a amended, register #13 re-pointed again)*
- **Status.** Accepted · 12/08/2026 (S4.22 grilling, founder-ruled; decision 2 reversed by the founder at spec review the same day, on the record) · discharges S3.1 decision 6's dump-photo consent must-answer for the *public* widening · supersedes the parked S4.2 shape ("published diaries on published itineraries") as the publicness primitive — S4.2 keeps Highlights, re-pointed onto this mechanism.
- **Context.** The Home tab has been a dead stub since S4.13, and diary entries have no visibility state at all — author-only structurally (ADR-024), with every widening reserved for the story that owns it. Canon's parked trajectory for diary publicness was diary-level publish gated on the published trip (S4.2 / register #13) — but publish requires `completed` (ADR-019/020), so a feed built on that shape could never show a trip being lived, and the founder's home-feed mock is unambiguous that it must ("Day 3 · 2h ago"). Separately, S3.1 recorded a must-answer before any diary is visible beyond its author: a postcard can contain photos *other members* dumped into the trip's shared pool.
- **Decision.** (1) **The share is per-entry**: a diary entry gains a `shared` state plus its instant — the author's sole act (INV-2a), default private, symmetric (unshare hides on next fetch, never tombstones; delete removes). (2) **Dump-implies-consent**: contributing a photo to the trip's Photo Dump consents to co-travelers using it in their postcards, shared ones included — the dump exists so members build their diaries from it, and the entry's copy belongs to the entry's author outright. The share reads nothing about a photo's origin: no provenance, no refusal, no consent machinery. The dump surface itself stays member-only. *(First ruled the opposite — own-photos-only — at the grilling; the founder reversed at spec review with the t1/t2 public-share case stated explicitly, both costs on the table: tightening later retro-blocks shipped postcards, and a contributor's control ends at the copy, leaving report/moderation as their only recourse.)* (3) **Independent of trip publish and lifecycle**: sharing is legal wherever the entry is (entries already require `ongoing`/`completed`); the trip's three axes are read, never moved. The card exposes the author, trip name, snapshot day label + activity title, caption, photos, and time-since-shared — never roster, absolute dates, lifecycle, or plan content; the link to the published itinerary activates only once it exists. (4) **Audience = any signed-in traveler**, by the S4.1 guard-bypass scrubbed-projection pattern; the diary-entry media audience widens to any authenticated traveler *for shared entries only*. Unauthenticated web stays backlogged. (5) **The feed is a global firehose ordered by shared-time** (retro-shares surface at the top); the friend graph, when it ships, narrows `public` per its standing backlog line. (6) **The absence rule is re-grounded, not excepted**: INV-2 forbids the *plan's projection* from revealing absence because that exposure is involuntary; a shared postcard is the author's own deliberate broadcast, and it identifies no one but its consenting author — no public surface carries the roster. Recency is therefore legal on the shared postcard and stays forbidden on the published itinerary.
- **Alternatives rejected.** Diary-level publish on published trips (the parked S4.2 shape) as the primitive — coarser consent than the act warrants, and structurally post-trip-only: a feed whose newest item is a finished trip has no pulse. Own-photos-only — the grilling's first answer, reversed at spec review: it makes the dump's core loop (build your diary from the pool) second-class the moment a diary is shared, and it demands origin provenance the copy path never kept (verified at spec time: the copy stamps the author, and legacy rows are indeterminate). Per-photo contributor consent — machinery before any evidence of need. A follow-scoped feed — assumes a graph that is deliberately post-validation; at current scale the firehose *is* the product. Requiring the trip published for the link's sake — inverts the dependency: the line un-tints until publish and self-heals.
- **Consequences.** The Home stub becomes the feed and Home becomes the landing route (Trips one tab over; Discover stays greyed for S4.3). S4.2 re-points: per-entry sharing is the primitive, diary-level publish becomes optional sugar over it, Highlights consumes shared entries; its inherited consent must-answer is discharged by decision 2's implied consent. Two backlog lines mint: the unpublished-trip teaser projection (a scrubbed landing for feed links before publish) and moderation/report — this is the app's first strangers-see-strangers surface *and* the dump contributor's only recourse after the copy, so the line is pulled forward on first incident. The Photo Dump surface owes one info line at its next touch (dumped photos may appear in co-travelers' shared postcards), keeping the implied consent honest at the point of contribution. Engagement chrome (likes/comments/save/search/bell) ships as S4.21-pattern stubs behind the one kill-switch; their real backends are separate stories. The feed's follow-flavoured empty-state copy deviates from the mock until the graph exists.
- **Invalidating condition.** The friend graph shipping → the feed narrows with `public` (backlog §106) and the terminal-card copy reverts toward the mock. A contributor complaint about a dumped photo's public life or any moderation incident → the report line pulls immediately; revisiting the consent model itself takes a new ADR and a migration story, because tightening retro-blocks postcards already shared — the cost decision 2 accepted. S4.3's discovery feed arriving → the browse role may re-home there; the postcard feed stays the recency surface.
- **AMENDED 13/08/2026, at S4.22's close, before the merge — decision 1 is reversed: there is no per-entry opt-in. Posting a diary entry publishes it.** *(Founder: "all diaries entries, if public are automatically in the homefeed. they default to public. revert that share button to what it was before, it was supposed to be a share diary entry you can send to someone… i dont know if there is already mechanism for private and public diaries but as far as i know it is not yet implemented, only for trips.")* **What changes:** `shared_at` is stamped at birth by the entity's constructor, so no caller can post an entry that is not public; the share/unshare endpoints, the request's `shareToFeed` field, the composer toggle and the preview's globe control are all **deleted**, cut deliberately *before* the merge because ADR-008 freezes /v1 the moment this ships and an endpoint re-added later could never be removed. `PostcardPreview`'s Share reverts to the send-this-to-someone stub it was on `dev` — which is what the founder's "revert that share button" names. **V30 backfills every pre-existing row from `created_at`**, not `now()`: a row left NULL would be permanently invisible with no UI able to surface it, and stamping the migration's clock would file last month's trip at the top of the feed claiming a moment that never happened. That backfill is irreversible and was taken on the standing ground that the installed base is the founders' own. **What survives unchanged:** decision 2 (dump-implies-consent) — the pinned IT still guards it; decisions 3, 4 and 5 entirely; and **decision 6's re-grounding of the absence rule, whose load-bearing clause holds with one word swapped** — the deliberate act is now *posting* rather than *sharing*, and a postcard still identifies no one but its author, so recency stays legal here and forbidden on the published itinerary. **What is parked rather than deleted:** the column keeps its nullability, because the friend graph — or any later per-entry control — re-enters through it. **The cost, stated:** a traveler's only retraction is now delete. There is no "post but keep this one back", and the composer says so plainly before the first postcard rather than after.
- **AMENDED AGAIN 13/08/2026 — archiving a trip takes its postcards off the feed with it, which restores the bulk retraction the reversal removed.** *(Founder ruling, on being shown that 117 shared postcards on archived trips were still public.)* **What was wrong:** the feed was half archive-aware — `navigableTripOf` already withheld the *link* for an archived trip while the *card itself* stayed on Home, so the product had two answers to one question. That is an inconsistency rather than a principle, and it was found only because a seeder's re-runs archived their previous trips and the postcards accumulated in plain sight. **What changes:** the projection excludes any entry whose trip is archived, so the card leaves the feed and the trip's public diary answers **404** — one filter in `PostcardFeedService.project`, so the feed and the per-trip diary cannot disagree. The lookup is **batched** (`WorkspaceService.archivedAmong`) rather than asked per entry, and the query stays on the workspace module's own service, never a join into its tables (ADR-002). **Why this and not the other direction:** decision 1's reversal deleted unshare, leaving delete — per-entry and permanent — as the only way out. Archive is the gesture a traveler already reaches for to put a whole trip away, it is **reversible** (unarchive returns the postcards, pinned by a test), and the link half already behaved this way. **The counter-argument, on the record:** archive is a *workspace* concern and a postcard is the author's deliberate broadcast, so one could equally have made the link stop being archive-aware. That reading was heard and declined — a bulk, reversible retraction is worth more to a traveler than the purity of the module boundary, especially with no trip-delete endpoint anywhere in the API. **Consequence to know:** a feed page may now return fewer cards than its limit, because the filter runs after the page is read. Pagination is unaffected — the cursor is taken from the last row *read*, not the last card *kept*.

### ADR-026 — The verification harness drives through Playwright *(the hand-rolled CDP layer retires; the API smokes fold in; web walks become specs)*
- **Status.** Accepted · 14/08/2026 (H1 grilling, founder-ruled) · reverses the epic-map port line's recorded scope ("smoke-*.js stays as it is"), chosen with that decision on the table · spec: `docs/plans/H1-playwright-port/spec.md`
- **Context.** The web rung's harness was never a decision: eleven `drive-*` scripts speak raw CDP over a WebSocket because S0.6's first driver did ("real headless Chrome, no new dependency") and every later story copied the shape. The costs are on the record — 2,145 lines across four drivers re-implementing the same plumbing, most of S4.21's closing debugging being the harness lying rather than the app breaking, and, measured at S4.3's gate, 15–25 minutes of serial browser time against ~30 seconds of API smokes: no parallelism (one shared Chrome profile, structurally), hand-guessed sleeps, and a runner whose progress could only be probed by greping for a live process — which once killed the run it was watching. Three walks rotted and were retired, their requirements captured in the flow inventory; the founder-reported problem is now wall-clock, and the trigger ("the next story adding a seventh walk, or the next gate abandoned for time") fired the day it was sharpened.
- **Decision.** (1) The harness is **one `@playwright/test` suite** (TypeScript, Chromium): the full runner — workers, auto-waiting locators, fixtures, reporters, traces — not Playwright-as-library, which would rebuild the runner by hand. (2) **Two projects**: `api` (request-context, no browser — the API smokes fold in, a founder reversal of the recorded keep-as-is scope) and `web` (phone viewport, `hasTouch` — the product is mobile web). (3) **The CDP/`ws` layer deletes entirely**, the diagnostic CLI re-engined on the Playwright library with its command-line contract intact; no new CDP script after this lands. (4) **Parallel-safety is contractual**: per-module static identity allocation from the verified pool (exclusive tags only for traveler-state mutators), and every spec seeds its own trip through the API — the per-trip Editing Session makes self-seeding sufficient isolation. (5) **Two-lane target** preserved: Metro while iterating, the preview container for the gate, one `baseURL` switch. (6) **Exit code and runner output are the only progress interface**; traces retained on failure. (7) **Vocabulary**: the web rung speaks Playwright — its tests are *specs*; "walk" survives only on the device rung. (8) **The gate keeps three rungs** — suite, backend ITs, emulator walk.
- **Alternatives rejected.** Repairing the CDP walks — rewriting the same files twice, the argument that settled the retirement. Playwright-as-library inside the old script shape — keeps the hand-rolled runner, the actual defect. Keeping the API smokes as standalone Node scripts — the previously recorded choice; reversed for one runner, one report, one vocabulary (the smokes' assertions port as-is, so the coverage cost is nil). Desktop viewport — tests a frame no traveler holds; the founder's erratic-carousel bug survived a green 40/40 walk precisely because headless Chrome's pointer is always a mouse. Per-worker identity allocation — the founder's per-module map is static, self-documenting (a screenshot names its module), and lifts the worker cap.
- **Consequences.** `ws` leaves; `@playwright/test` enters as a dev-dependency with per-machine browser binaries (one-time `npx playwright install chromium` per workstation). The orchestrator script dies; `npm run smoke` runs the suite. The retired walks' dark flows — the lifecycle ladder and the publish act, currently watched by nothing — are rebuilt from the inventory before green coverage is ported, so the port ships more coverage than the walks had when healthy. CLAUDE.md's recipes and the glossary update; historical records are not rewritten. Wall-clock is re-measured at close against the 15–25 minute baseline.

### ADR-019 — Lifecycle, discovery and visibility are three independent axes *(supersedes ADR-018's single-column shape; reinstates the `completed` gate ADR-017 retired)*
- **Status.** Accepted · 03/08/2026 (founder, two days after ADR-018, on the same running build) · ADR-008 waived on the record for the wire break, the fourth time in this story, on the standing ground that the installed clients are the founders' own.
- **Context.** ADR-018 fused two questions into one mutually-exclusive value: *is it in the feed?* and *who may read it?* The founder re-drew the model as three separate facts — *"an itinerary has 3 states, draft, active, complete… 2 states for the discovery feed, published and unpublished… 2 states with regards to the social feed. public and private."* Under that reading `status` cannot hold them: an itinerary is simultaneously somewhere in its life, in or out of the feed, and open or restricted.
- **Decision.** Three orthogonal axes on the one itinerary. **Lifecycle** `state` — `draft → active → complete`, traveler-driven (no date derivation), forward with a **one-step undo**; this is V12's dormant enum reactivated, not a new concept. **Discovery** `published` — boolean; governs the feed **and the freeze**. **Visibility** `visibility` — `public | private`; governs who may read, independent of the feed. Publishing **requires `complete`** and defaults to `public`; unpublish thaws and frees the lifecycle. While published the lifecycle is **pinned** — to move it, unpublish first.
- **What it reverses.** *ADR-018's shape, not its reasoning*: the naming argument (two unrelated "draft"s must not share a column) is **upheld and is why this works** — `state` keeps lifecycle, the other two axes take their own columns, and `status` retires after two days. **ADR-017 decision 1's lifecycle position reverses**: the epic map recorded *"publish gates on nothing; `completed` is retired as a gate"* — it is reinstated, and the "can't classify dateless trips" objection dissolves because the transition is a button, not a date. ADR-018's `private`/`public` stop being *publication* values and become *visibility* values, orthogonal to the feed.
- **Why the gate is the load-bearing choice.** It prunes 6 combinations to 5 and removes the frozen-draft: a plan can only freeze once the trip is over. That re-grounds the freeze — ADR-018 justified it as *"nobody reads a trip that changes under them"*; here it is *"a completed trip is a record of what happened"*, which is a rule a traveler can infer from one line of UI rather than being taught.
- **Consequences, including the ones to weigh.** *(a)* **Published + private is legal**: an entry in the feed that only the owner and collaborators may open — the feed must filter per-viewer, and a traveler who publishes privately gets a frozen plan with no public page. Accepted knowingly as the price of orthogonality. *(b)* **Publishing is now two steps** — mark complete, then publish — where ADR-017/018 allowed it from creation; the preview CTA must explain the precondition rather than merely hiding. *(c)* The lifecycle UI removed at the E1 promotion gate (epic map: *"the mobile surface comes out"*) **comes back**, which is why the endpoints were kept dormant rather than deleted — that call now pays. *(d)* `friends_only` re-collides: with visibility already split out, the friend graph narrows `public` rather than adding a tier. *(e)* Every existing row needs a lifecycle value; none has ever been completed, so all land on `draft` — meaning **every currently-published itinerary migrates to a state that could not have published it**, tolerated as a one-off since the installed base is the founders'.
- **Invalidating condition.** Travelers publishing plans *before* travelling (a use the gate forbids) → the gate loosens to `active`, or retires again with the freeze re-anchored. Dates becoming mandatory → lifecycle derivation reconsidered, its objection having been about dateless trips.

### ADR-020 — The lifecycle is four states: `draft → upcoming → ongoing → completed` *(amends ADR-019's ladder; upholds its axes, gate and freeze)*
- **Status.** Accepted · 04/08/2026 (founder, at the create-itinerary-flow grilling against the final Figma frames) · ADR-008 waived on the record for the `active → ongoing` wire rename, the fifth time in this story family, on the standing ground that the installed clients are the founders' own.
- **Context.** ADR-019's three-state ladder fused two facts into `active`: *planning is finished* and *the trip is being lived*. The creation flow's final frames needed a terminal act, and the only honest one — "I am done planning" — had no state to land on: `draft` denies it, `active` overclaims it, and `completed` asserts a trip that never happened (the exact falsehood V20's migration refused to write). The founder re-drew the ladder with the missing rung: *"draft (planning) → upcoming (planning finished) → ongoing (currently doing the trip) → completed (trip completed)."*
- **Decision.** Four lifecycle states on the one `state` axis: **`draft`** (planning) → **`upcoming`** (planning finished, trip not started — the creation flow's terminal CTA, **"Finish Planning"**, lands here) → **`ongoing`** (the trip is being lived; renames ADR-019's `active`) → **`completed`** (the trip happened). **Every transition is the traveler's tap** — dates never flip state; a date-holding trip may *nudge*, never act. **One-step undo runs down the whole ladder** (`completed → ongoing`, `ongoing → upcoming`, `upcoming → draft` — the last is "reopen planning"); two-step jumps stay refused. **The publish gate stays at `completed`** and **the freeze stays solely on `published`** — no lifecycle state ever locks the plan: `upcoming` stays editable (or "Finish Planning" becomes a trap travelers learn to avoid) and unpublished `completed` stays editable (completion is when the record gets corrected; the freeze's ground is *readers*, and readers arrive at publish). Birth is not a transition: creation bears `draft`; a `completed`-at-birth door ("Add a Past Trip") is parked, unbuilt, pending its argument.
- **Alternatives rejected.** Naming the terminal CTA "Complete Itinerary" — puts one word on two facts (done-planning vs trip-happened), the exact collision ADR-018's upheld naming argument forbids. Date-derived transitions — dateless trips stall forever (the objection that killed derivation twice), and an auto-flipped `completed` turns the publish gate's grounding assertion into an automation. Freezing at `upcoming` or `completed` — locks plans with no readers and re-mints the frozen-not-yet-happened plan ADR-019 removed.
- **Consequences.** *(a)* `upcoming` is a new wire value and `active → ongoing` is a rename — one waiver covers both. *(b)* Existing rows: `draft`/`completed` keep their values; any `active` row becomes `ongoing` (none exist beyond seeds). *(c)* The Trips surface renders the lifecycle as four sections (Ongoing · Upcoming · Draft · Completed, empty hidden), superseding S4.11's chips; S4.11 decision 7's published/private row badges are **deferred, not deleted** (epic-map backlog). *(d)* The publish-success chrome re-homes from creation's end to the publish act, where its every line is true. *(e)* `WriteFence` ships unchanged.
- **Invalidating condition.** Travelers not tapping — trips rotting at `upcoming`/`ongoing` while the feed starves → revisit the nudge's strength before revisiting derivation. The parked past-trip door winning its argument → birth-state parameter (`draft | completed`), which this ADR already shaped for.

### ADR-028 — The trip's own facts: ONE destination, ONE Trip Currency, merge-patch on the update endpoint, owner-only details editing *(the second ADR-008 waiver; carries three /v1 semantics changes at once)*

Dates are named a **workspace-private invariant** — no public or published surface ever carries them; duration is the public fact (already true, now pinned by name rather than by accident). E5 inherits a trip that already knows its currency, with no FX anywhere.

What is switched off is decision 7 (facts line), decision 8 (cog) and the date half of decision 9. **The parking is a flag, not a revert** — the components stay imported and rendered behind a runtime `false`, so `tsc` and Jest still cover them and unparking is one boolean each. **One consequence worth naming, because it is the reason merge-patch was worth building:** with the date fields hidden the client OMITS `startDate`/`endDate` rather than sending null, since null means *clear* under decision 4b — a hidden field must not be able to destroy the value behind it. ### ADR-030 — WebSockets enter the stack as generic topic infrastructure *(partially reverses the pull-based-only posture of ADR-014's family; extends ADR-008's additivity to socket payloads; push notifications remain a separate, unmade decision)*
- **Status.** Accepted · 20/08/2026 (founder — the transport ruling at the S4.10 chat grilling, grill-with-docs, three rounds; infrastructure-first sequencing ruled in the same session: WS-1 builds before its first consumer)
- **Context.** Every read surface to date is deliberately pull-based ("no sockets, no push, no broadcast" — the lease indicator, polls, invitations). In-trip chat (S4.10) is the first surface where live delivery is the expected UX, and its plausible successors (poll activity, presence, live editing's eventual sync) all want the same pipe. The alternative — polling the chat read while the tab is focused — was recommended and considered; the founder ruled sockets, built once, generically.
- **Decision.** One WebSocket layer inside the existing backend and app — no new deployable infrastructure. **(1) Auth:** a single-use ~30s ticket (`POST /v1/ws-ticket`), redeemed-and-burned at the `/ws` upgrade — never a bearer token in a URL (P3); browser WS cannot send headers, and a burned ticket in an access log is worthless. **(2) Subscriptions are authorization acts:** topic names (`itinerary:{id}:{channel}`) are parsed, the Membership resolves through the guard, non-members get the masked refusal, and membership hard-delete evicts the member's subscriptions AFTER_COMMIT — the S1.5 lease-release posture on the socket. **(3) Fan-out rides domain events**, `@TransactionalEventListener(AFTER_COMMIT)`, IDs only (ADR-002): a broadcast can never precede its commit; delivery is **at-most-once by design** because **(4) the database is the source of truth and the socket is a latency optimization** — every consumer must be able to re-read its state over REST after a reconnect (the catch-up convention); UUIDv7 event ids give finer grain when a consumer wants it. **(5) The envelope** `{topic, type, eventId, at, payload}` **evolves additively only** (ADR-008 extended — installed apps hold sockets against new servers for weeks) and **clients silently ignore unknown event types** — the rule that lets the server grow topics without stranding old apps. **(6) Hygiene:** server ping 30s / close after 2 missed; bounded send queues — slow consumers are closed, never buffered unboundedly. **(7) Origin posture mirrors CORS:** dev-profile allowlist bean, absent Origin admitted (native), prod refuses browser origins, invariant-tested. **(8) In-process fan-out behind an interface** — the broker seam is named and deliberately unbuilt.
- **Alternatives rejected.** Polling (`refetchInterval` while focused) — adequate for chat at alpha scale and architecturally consistent, but rebuilt-per-surface and a dead end for presence; the founder chose the pipe once. STOMP/SockJS — subscription routing for one channel shape doesn't earn a protocol layer. Bearer-in-query auth — P3. Sticky first-frame auth — kept as the recorded fallback if the edge mangles query strings (the WS-1 spike decides on evidence). A broker now — infrastructure for a scale that doesn't exist; the interface is the graft point.
- **Consequences.** The first stateful component in the stack: the harness gains socket assertions that must name their failure mode (connected-and-dead looks connected), the emulator and preview rungs gain `ws://` derivations of the one API base URL, and Railway's edge behavior becomes load-bearing (proven by WS-1's spike before anything is built on it). Chat (S4.10) ships as one table + two REST endpoints + one topic row. **What this ADR does not decide:** push notifications (a closed app still hears nothing — a separate decision with its own moment); presence/typing/live editing (ADR-014/022's invalidating condition does **not** fire because a transport shipped); horizontal scale-out (the broker seam's own ADR, on its day).
- **Invalidating condition.** The backend scaling past one instance → the in-process fan-out is replaced behind its interface (broker ADR). Live editing genuinely arriving (ADR-014/022's condition) → presence and sync design on top of this layer, not beside it. The spike or the device rung contradicting the hygiene defaults → the numbers move, the structure doesn't.

### ADR-031 — CI answers for the suites; the machine answers for the eye *(extends ADR-026's harness posture to where suites RUN, not what they assert; changes no coverage; supersedes CLAUDE.md's "whole stack, once, before proposing a promotion")*

- **Status.** Accepted · 21/08/2026 (founder — grilled at H2, grill-with-docs, five rounds, 22 questions) · discharges the founder's per-ticket full-suite complaint
- **Context.** `implement` runs per ticket and its line 11 demanded *"the full test suite once at the end"*, so a six-ticket story paid six full passes — and the verify-and-modify loop after it had no skill at all, so agents defaulted to running everything. A full local pass measured **~30 minutes**. Meanwhile `.github/workflows/ci.yml` had been running `mvn -B verify` (214 unit + 882 ITs), the typecheck, the Jest suite and a clean-checkout compose on **every push, every branch**, in **2m46s** — five times faster than the same suite locally on a runner with *no more cores*, because the gap is Docker Desktop's WSL2 boundary and the Windows-only workarounds it forces, not CPU. Cost: ~6 billed minutes per push against a 2,000-minute allowance. Nothing could read it: an agent memory asserted `gh` was deliberately absent, so `dev` sat red for **13 consecutive pushes** on one order-dependent fixture collision before anyone looked.
- **Decision.** Three tiers, by what a suite *needs to exist* and whether it can go red without the code being wrong. **Cheap** (no prerequisites, near-zero startup, a red is always yours — Jest, `tsc`, backend unit) and **medium** (starts its own containers, can lie environmentally — the backend ITs) run **in CI on every push**, path-filtered behind an always-runs aggregator; per-push rather than per-gate because it localises a break to the commit that caused it. **Expensive** (needs a system someone stood up, can lie loudly — Playwright) runs at the **merge gate**: a `pull_request` to `dev`, required, with its own compose stack and the preview container built in-job. Local work is Tier 1 only — incremental `tsc`, `jest --changedSince`, and looking at the change. `dev` gets required PR + required check, administrators included. **`preprod` and `main` get required checks and NO required PR**, because GitHub's PR merge has no true fast-forward and requiring one would mint a different SHA, destroying the `git rev-parse main preprod` property the pipeline exists for.
- **Alternatives rejected.** *Scoping the backend locally by module* — H2's own first draft, and the centrepiece until CI's 2m46s was measured; it takes ~14 minutes to ~5, not to ~1, because most of a scoped run is startup. Survives only as a one-line debugging convenience. *An end-of-day full local sweep* (the founder's opening proposal) — right in spirit, but once CI owns the suites there is nothing left in it but the device walk. *Nightly Playwright* — an unattended red at 3am that nobody triages is precisely the lying-suite problem. *Trusting CI by discipline rather than protection* — thirteen red pushes is the evidence against. *Admin bypass on `dev`* — recreates the gap being closed.
- **Consequences.** Nothing automated runs on the founder's machine; their time goes to the device walk, motion fidelity and the defect classes no suite reaches (the avatar blind spot was found by chatting with a real person). A red becomes unmissable at the moment it matters because the merge button refuses — **email is explicitly not a signal here, the founder does not read it**. Direct commits to `dev` end, enforcing CLAUDE.md:39 rather than inventing a rule. Feedback moves from foreground blocking to a wait at the merge, which is already a pause point since promotions are propose-first. A workflow file can now read the pool credentials, so **workflow edits become sensitive**. The `@Tag("migration")` exclusions and the per-module scope table are cut, their justification having moved.
- **Invalidating condition.** CI going unread again — the named failure mode, and why readability blocks H2 rather than trailing it. A second workstation or contributor whose pushes contend for the pool. The Playwright job's minutes becoming a line item, which is also the re-worded trigger on the parked P8 duplication line. CI ever pointing at deployed dev instead of its own stack, which inverts the no-contention argument entirely.

### ADR-032 — The invite link + join request model *(extends S1.2's invitation model with the second consent direction; takes the ADR-008 waiver family's ground for the publish-freeze semantics changes; the anonymous teaser is the deliberate exception to the everything-authenticated posture)*

- **Status.** Accepted · 22/08/2026 (founder — grilled at S4.28, grill-with-docs, four rounds + a design-prompt cycle; design baseline = the Travelers Spec s2 canvas, contracts C1–C7/M1–M7 normative)
- **Context.** Invitations reached only people the inviter could name — an email address (S1.2) or an exact @handle (S4.9) — and only the owner could issue them, from a door buried in the plan editor. Nothing could bring in someone not yet on Largata except dictating their email, and the founder's ask was a Discord-style shareable link — with the explicit constraint that holding the link must **not** mean entry, because links get forwarded.
- **Decision.** **(1) Two consent directions, named in the domain model:** an **Invitation** is the trip asking the traveler (the traveler consents by accepting — no owner action); a **Join Request** is the traveler asking the trip (the owner consents by approving). **(2) Approval creates membership immediately** — the request was the requester's consent, so there is no third handshake; a request can only exist for a signed-in, onboarded, email-verified account, so approval never admits a half-built identity. Decline is silent and retryable; membership arriving by either path supersedes the other's pending rows. **(3) One live link per trip**: an opaque unguessable token (≥128-bit), minted lazily, reused forever — no expiry, no regeneration (reset parked with a spam-report trigger); the link is dead while the trip is archived or published, computed at read time. **(4) The token-gated teaser answers anonymously** — title, destination, dates, traveler count, cover; never roster or plan — the first anonymous product endpoint, deliberate: the landing is the conversion moment for exactly the not-yet-onboarded person the feature targets. Two capability-scoped cover reads exist because the audience fence correctly refuses both audiences (the token and the invitation are themselves the authorization). **(5) Policy: any member invites by handle, revokes pending invitations, and shares the link** — the additive widening S1.2's grilling recorded in advance; **removal stays owner-only** (the mock's any-member-removal was rejected: an approve-then-purge griefing surface); the Requests queue and ownership offers stay owner-only. **(6) Publish freezes the people, not just the plan:** invitation issuance/revocation/acceptance, removal, join-request creation/approval, and all ownership-offer operations refuse on a published trip — "publishing is already a completed trip"; pending rows go inert and hidden, resurfacing on unpublish; **leave always works**; completed-but-unpublished keeps everything open (post-trip adds are the photo-dump use case). **(7) Link joiners onboard in full** — the pending token persists through sign-up/onboarding and app restarts and returns them to the landing; no trimmed path (rejected, not parked), no guest accounts (parked: they are an entitlement tier, which is ADR-009's parked seam, and handle forfeiture needs the scheduler this codebase deliberately lacks).
- **Alternatives rejected.** *Approval minting an inbox postcard the requester must still accept* — a third tap on a person who already asked, and a join that silently never completes if the card goes unnoticed. *Any-member removal (the s1 mock)* — subtractive authority with a griefing surface confirms can't fence. *Link expiry / regeneration now* — approval already gates membership, so a leaked link is queue noise, not entry; Discord-style rotation is real machinery for a problem with no evidence yet. *A blind sign-in wall instead of the teaser* — wastes the one moment the feature exists for. *Guest accounts* — see (7). *Network fuzzy search in the add sheet* — no search infra exists and the founder ruled it waits for the network itself; v1 is exact-handle plus the link.
- **Consequences.** Three shipped-/v1 semantics changes ride this ADR's waiver (the founders-only-clients ground of S4.23/S4.25): members' invite calls stop 403ing, membership/offer mutations start refusing on published trips, and invitation accept refuses on published trips. The app gains its first pre-auth screen and the auth gate learns to admit one segment unauthenticated. The share URL is composed server-side per environment, shaped so Android App Links can adopt the same URLs later. The analytics this story emits (teaser views, requests, outcomes) are what make the guest-accounts trigger measurable. The members screen and the editor's invite door are deleted; the Travelers tab becomes the single membership surface, ownership transfer included.
- **Invalidating condition.** Link-request spam actually reported → the parked reset-link line pulls. Invite-link conversion visibly dying at the sign-up wall → the guest-accounts line pulls (as its own grilled story, plugging into the landing's signed-out state — the mechanics here don't move). Public profiles landing → the suggestions/multi-select v2 annex activates in the add sheet. A real notification system arriving → approval/decline get their notification moments; nothing structural changes.
