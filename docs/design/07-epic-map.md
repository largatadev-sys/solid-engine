# 07 · Epic Map — Largata  `[MVP-THIN — launch epics named; near-term stories detailed]`

**Architect's question:** *What is the whole territory, and what is the smallest slice of it that tests the idea?*

**The epic map is durable — the living backlog, not a design-time snapshot.** Anything raised over the life of the product — an improvement, an issue, a deferred idea, a new feature — has one home: the backlog here. Raising something *means* capturing it in this map; it waits as a placeholder and is elaborated into stories only when picked up. Created during design, **maintained forever after** — it does not stop being the backlog when the MVP ships.

_Status: **proposed — pending founder ratification.** Launch scope = Epics 0–6 (founder decision: the ledger is **in** launch — the hypothesis is "plan + costs + record"; costs stay). Stories are elaborated **just-in-time**: Epic 0's are agent-ready now; later epics carry story lists at slice level, elaborated when pulled. Only the next few stories are ever in flux — by design._

## Epic 0 — Walking Skeleton  *(stories agent-ready now)*

> **S0.1 — Repo, environments, and the standing rules**
> **Context anchor.** Epic 0 · no domain yet · establishes the patterns everything follows: Artifact 04 (deployment, containerization scope), 06a/06b.
> **Vertical slice.** Monorepo per the 04 layout decision (`backend/` + `mobile/` as root-level peers; docs and bridge files at root) · full-stack local Docker (Spring + Postgres + storage emulator) · Spring skeleton with `common` (logging filter, exception handler, error envelope) · Expo app skeleton with the repository/cache layer stub and one typed `apiClient` · CI (build + test) · `.gitignore` for all secret files **before the first commit** (the structural guarantee) + a staged-diff secret/PII scan before every commit (the soft backstop) · CLAUDE.md and BUILD_STATUS seeded · `GET /v1/health` returning through the whole stack.
> **ACs (=tests).** `docker compose up` yields a working stack from clean checkout · health endpoint returns 200 with the standard envelope conventions · a thrown `DomainException` produces the Artifact 05 error envelope with a traceId that appears in exactly one log line · CI red on test failure · a planted fake secret is blocked from commit.
> **Scope boundary.** No domain entities, no auth, no deployment to PaaS yet.

> **S0.2 — Auth end-to-end**
> **Context anchor.** Epic 0 · identity module · ADR-006, Artifact 03 (context propagation).
> **Opens with (carried from S0.1, 2026-07-15).** Install Android Studio + an AVD — the dev-build needs the toolchain regardless, so this is a prerequisite, not extra work. First act: close S0.1 ticket 05's two open device ACs (the health screen on a device, and its typed error state). This also tests the `10.0.2.2` host alias, the one assumption S0.1 could not reach. **Note:** Expo Go on the emulator may hit the same SDK 57 store lag that blocked both phones — if so, the dev-build closes those ACs instead, and is the better test anyway.
> **Vertical slice.** Firebase sign-in on mobile (Google + email; Apple sign-in activates with the iOS phase — ADR-010) → backend validates the JWT as OAuth2 resource server → first authenticated call provisions the domain `Traveler` (keyed by Firebase UID) → `GET /v1/me` returns it.
> **ACs.** Sign-in on the Android dev-build · request without token → 401 in the standard envelope · first `/me` call creates the Traveler exactly once (idempotent) · `userId` appears in request-scoped logs via the filter, never set by leaf code.
> **Scope boundary.** No profile editing, no account deletion (its own story later), no workspace anything.

> **S0.3 — Create and view an Itinerary (the first domain slice, guard included)**
> **Context anchor.** Epic 0 · itinerary module · Artifact 02 (Itinerary aggregate, `draft` state), Artifact 03 (the guard exists from the first domain endpoint — not retrofitted).
> **Vertical slice.** `POST /v1/itineraries` (title, destination, dates → `draft`) · `GET /v1/itineraries/{id}` · `GET /v1/itineraries` (mine, cursor-paginated) · mobile screens: create + list + view, reads through the repository/cache layer.
> **ACs.** Creator can create/list/view · **another authenticated user → 404 on my private itinerary** (the guard's first proof) · visitor (no token) → 401 · created itinerary is `draft` with `private` visibility · list uses the one pagination shape.
> **Scope boundary.** No items, no workspace, no publish, no fork. The guard resolves ownership only (membership arrives with E1).

> **Scope boundary.** No Apple sign-in (iOS activation) · no native flow changes (button visuals only, per the grilling amendment) · no backend changes · no One Tap · this does not make the preview a supported *deployment* — the service stays interim, still deleted when the real web surface or TestFlight arrives (teardown list now includes the OAuth origins).

- **S4.18 · Buffered plan editing — nothing saves until Save Changes** — *(founder ruling, 2026-08-09, on the running S4.17 build: "nothing is saved up until save changes is pressed")*. **Reverses ADR-022 / S4.17 decision 4's per-action saving**, on a concrete report: the founder reordered activities, pressed back without Save, and found the change already persisted. **The defect is a broken promise, not a missing capability** — a button labelled *Save Changes* that only ends the session tells the traveler their edits are unsaved when they are not. So the schema **assumes** `published ⇒ published_at IS NOT NULL` and nothing enforces it. `DiscoveryService.browse` ends `InstantCursor.encode(last.publishedAt(), last.id())`, and `encode` does `at.toString() + …` — an **NPE** that escapes as a 500 through the catch-all. ### Architecture review 2026-07-29 — five deepening candidates, parked

*One review, run against `dev` after S1.9 (131 Java files / 9,160 L; 74 TS files / 7,502 L). Its sixth candidate — the comment policy — was decided and shipped the same day (off-epic ledger, 2026-07-29); these five were not. Vocabulary is the deep-module one (module · interface · depth · seam · leverage · locality). **Each is parked with its own trigger, not scheduled** — they are recorded so the next architecture pass inherits the evidence rather than re-deriving it, which is the whole reason this section exists.*

- **The archive fence and the edit lease have no structural guarantee — only the guard does** — *(raised at the architecture review, 2026-07-29; the review's own top architectural pick)* `AuthorizationGuard` is genuinely **deep**: 13 lines of implementation buying a compile-time property across ~39 service signatures, because `Membership` is a type only the guard can produce, so an unguarded handler **cannot call** a workspace-scoped method. That property was never replicated for the other two gates. `WriteFence.requireWritable` is hand-written at **9 call sites** and `EditLeaseService.requireHeldBy` at **9 more**, both enforced by convention and tests rather than by any signature — and `WriteFence.java:19-23` says so outright: *"A future write endpoint can still forget to call this — no signature forces it, unlike the guard's `Membership` parameter."* The consequence is that *"can this traveler edit this itinerary right now?"* takes **24 files across 5 packages** to answer, and the three gates live in three different layers with three different mechanisms (controller/type-enforced · service/convention · service/convention-with-two-carve-outs). The shape of the fix is already proven twice in-tree: `EditLeaseService.java:263-268` folds the fence into `requireHeldBy` so it covers all nine plan writes at the seam they must structurally pass — the correct instinct, applied once and never generalised. **Candidate shape:** a second capability type (`WriteAccess`) that only the guard mints, demanded by plan-write methods the way `Membership` is today. **Trigger:** the next story that adds a plan-write endpoint, or any story that touches `common/authz` — whichever comes first; both are **stop rules**, so it starts with an owner decision, not an agent's. **Do not pull it as tidy-up:** it is the highest-consequence candidate (a forgotten fence is a write landing on an archived trip, silently) and it is Full-rigor territory, so it deserves a grilling and a story, not a drive-by.
- **`WorkspaceService` is a 16-method shallow façade over a 5-column table** — *(raised at the architecture review, 2026-07-29)* 16 public methods, **145 code lines**, of which seven (`stateOf`, `isArchived`, `isMember`, `roleOf`, `ownerOf`, `workspaceIdOf`, `membersOf`) are pure repository pass-throughs. Its interface is nearly as complex as its implementation — the textbook shallow module. Two concrete symptoms, both verified: (1) **three answers to one question** — a missing workspace makes `stateOf` return `Optional.empty()`, `isArchived` return `false`, and `RowBackedTripWritability.isFrozen` **throw a 500**; each choice is individually defended in javadoc and nothing names them as one decision made three times. (2) **the seam leaks the key it exists to hide** — `workspaceIdOf` is public with **8 external call sites** across `invitation` and `membership`, both of which also store `workspace_id` as a column, so two modules above the seam are keyed on `workspace`'s private identifier and every read pays an id-translation hop to undo it. `RowBackedMembershipResolver.java:47-49` claims the opposite in a comment (*"keeps the workspace id — this module's private business — from leaking above the seam"*), which the call graph contradicts. **Trigger:** the next story that adds a workspace-scoped question, or E5's ledger work, which will otherwise add a ninth pass-through.
- **The offer/accept lifecycle is implemented twice, and a third instance is coming** — *(raised at the architecture review, 2026-07-29)* `invitation/Invitation` + `InvitationStatus` (S1.2) and `membership/OwnershipOffer` + `OwnershipOfferStatus` (S1.6) share **13 of 15 structural elements**: UUIDv7 id, non-updatable `workspace_id`, `@Enumerated(STRING) status`, `resolved_at`, the four terminal transitions (`accept`/`decline`/`revoke`/`voidBySystem`) with byte-identical bodies, a partial unique index on PENDING, and a 404-before-403 rejection ladder. ### S4.28 travelers tab 2026-08-23 — a parked hardening line

- **Rate limiting: the backend has NONE, on any endpoint — and a miss-throttle is NOT a substitute for token entropy.** Parked while shortening the invite token, where it was proposed as the thing that would make an 8-character (48-bit) token safe. **It would not have, and the reason is worth keeping because the design looks obviously correct until you write it down.** A bucket that consumes on a *failed* lookup and answers `429` when exhausted hands the attacker a free oracle: once the bucket is empty every miss returns `429` instantly, at no cost, so they enumerate at full speed and watch for the one response that *isn't* a `429`. The limiter contributes exactly nothing. Closing the oracle means refusing **all** lookups when throttled — valid tokens included — which converts a cheap guessing script into a global outage of every invite link in the product. Per-IP buckets dodge the outage and are defeated by header rotation unless Railway's trusted-proxy chain is configured correctly, which is its own piece of work. **The ruling that followed: take the entropy instead (ADR-032 amended to ≥64 bits, 11 characters) and let the limiter be ordinary hardening rather than load-bearing security.** It is still worth having — a public, unauthenticated endpoint with no ceiling is a genuine gap — but nothing should depend on it. **Trigger: the first abuse report, or any story that puts a costlier act behind an unauthenticated route.**

### S4.35 ticket 01 2026-08-25 — the async dispatcher parked, its premise measured and not reproduced

- **The WS fan-out's synchronous drain is PARKED, and the scheduler pool shipped in its place** *(owner call, 2026-08-25, on the implementer's recommendation — narrowing S4.35's own decision 8, which had ruled the dispatcher into the story)*. The ticket named two live defects: `Session.send` draining on the committing thread, so one dead connection stalls another traveler's write; and `synchronized(socket)` letting a stalled drain block the heartbeat that exists to detect it. **Neither reproduced on any rung available to us, and the numbers are recorded so nobody re-derives them.** Broadcasting 8KB frames straight through `EventFanout` to one genuinely non-reading socket: the session was dropped at **broadcast #278, ~2.1MB in flight**, by the *existing* `SEND_QUEUE_LIMIT` overflow close, **worst single broadcast 57ms**. Through the REST path, a third traveler's POST issued while four threads flooded the deaf socket took **191–497ms**. Under continuous flood, `pingEverySession()` timed twenty times came back **worst 0ms**. The bounded queue already absorbs the stall before a socket write blocks anyone — which is *why* the defect could not be provoked, not evidence that the source reading was wrong.
  - **What shipped instead is the half that is a code fact rather than a measurement:** there was **no `TaskScheduler` bean and no `spring.task` configuration anywhere in the tree**, so Boot's single-threaded default carried both `pingEverySession` and `sweepExpiredTickets` — one stalled task delaying the other, independent of socket behaviour. That is provable by a test that fails without the fix, so it was built test-first and landed.
  - **Why parking rather than shipping it anyway.** The dispatcher would have landed with **no test that fails without it and none that catches it regressing**, as an untested concurrency change to the transport every later S4.35 ticket fans out across. A subtle error in the executor's shutdown or its interaction with `writing`/`overflowed` surfaces as dropped or duplicated frames under load, first visible on the founder's phone. Shipping it would not have made it more proven, only more code.
  - **The honest limit of the probes, stated so this can be attacked rather than trusted.** They ran on **Windows loopback with TCP autotuning at `Normal`**, which grows the receive window aggressively; Railway's edge, a mobile network and a genuinely wedged handset are all different. Tomcat's default blocking send timeout (20s) is unconfigured, so a real stall surfaces as a 20-second hang, not a permanent one. What is proven is that **this rung cannot produce a slow consumer** — the same thing S4.35's decision 9 predicted about load numbers taken against a Testcontainers box, arriving one layer earlier than expected. The source reading in the spec's Problem Statement remains correct as source reading.
  - **The harness is committed and must not be mistaken for a proof.** `SlowConsumerIsolationIT` **passes against the unfixed synchronous dispatcher**, and says so in its own assertion message. `DeafWsSocket` (`src/test/java/com/largata/support/`) completes the `/ws` upgrade over a raw socket and never calls `read()` — **the JDK `HttpClient` cannot express "stopped reading"**, because declining `request(1)` stops listener delivery but not TCP reads, so the first fixture drained happily into its own buffers and passed while proving nothing. ### S4.35 review round 2 2026-08-25 — four parked findings on the topic grammar and the ledger

*Raised by the two-axis review after S4.35's events landed. All judgement calls — the two genuine defects the same review found were fixed in the story (ticket 08's round-2 note).*

### S4.35 live walk 2026-08-25 — the reconnect is correct but its worst case is a 30s stale window, and no test can see it

- **An unfocused tab can sit on stale data for up to 30 seconds after the server returns, and nothing on screen says so** *(founder observation, 2026-08-25, during the S4.35 live walk: "the restart did not take effect right away… when I changed the focus window, that's when it refreshed")*. **The behaviour is correct and was verified as such**, not assumed: `scheduleReconnect()` retries on a plain `setTimeout` regardless of focus, so the socket *does* come back on its own; `reconnectIfDead()` (wired to `AppState`/window focus) additionally **short-circuits the wait** by resetting `attempt = 0` and reconnecting immediately. So focus is an accelerator, not the mechanism. What the founder actually caught is the **backoff's tail**: `delayForAttempt` is `1s, 2s, 4s, 8s, 16s → capped 30s` with jitter, so a server outage long enough to burn five attempts leaves the next retry up to 30 seconds out. The walk's outage was ~56s (a cold `docker compose restart`, harsher than a real container swap), which is why the tail was visible at all.
  - **Why no existing test catches it, and this is the part worth keeping.** The Playwright reconnect spec kills the socket while the page is active — and a Playwright page is *always* focused, so it cannot distinguish *"reconnected on its own"* from *"reconnected because focused"*. It proves resubscription happens; it is blind to which path got there. **A test that would catch it has to blur the page (or drive an unfocused context) and assert the socket returns anyway** — i.e. assert the accelerator is not load-bearing. Same family as this repo's standing rule that a check whose two outcomes are indistinguishable is not a check.
  - **The options, none taken yet because this is a founder call.** Cap the backoff lower for a foreground app (30s is a background-tab number); or reset `attempt` on any successful `/v1` response, since a live REST call proves the network is back; or surface the state — a quiet "reconnecting…" the way the pull control surfaces a fetch. The third interacts with the motion line below and with S4.34's spinner rule (nothing here may bind to `isRefetching`).
  - **Trigger: the next story touching the socket lifecycle, or the first report of stale data after a deploy.** Related: the device rung, still unrun, is where the `AppState` half of this gets exercised at all.

### S4.35 live walk 2026-08-25 — a live card that changes silently is a signal nobody catches

- **A field that updates underneath the traveler needs a MOTION, not a substitution** *(founder observation, 2026-08-25, watching the S4.35 walk live: "we should put some text motions for this so the signal is easily captured" · "put a motion for that when the text is changing, just to make the cards responsive and interactive")*.   - **Scope, so it is not confused with a spinner.** This is not "show that we are loading" — the whole design point of absorbing a payload is that there is no fetch to spin about. It is the opposite: the value has *already* changed and the motion is the receipt. The candidates are a brief highlight/fade on the changed text, a cross-fade between old and new value, or the entrance the advisory row could have instead of appearing fully-formed. **The advisory and the subline are different cases** — one is a row appearing and disappearing (enter/exit), the other is a string being replaced in place (value transition), and they may not want the same treatment.
  - **Two constraints from this repo, both learned the hard way.** Any motion must be **platform-forked or platform-safe**: `nativeEvent.timestamp` is unpopulated on react-native-web (S4.22) and reanimated's native init kills any Jest suite that imports a screen (S4.17), so the testable seam is a pure module and the render is device/browser-verified. It is also a design question before it is an implementation one — the founder should see options rather than receive one. **Trigger: the next story that touches the Trips card's chrome, or a founder pull — whichever comes first.** Related and deliberately separate: the four retap surfaces line above already wants that card's shared components collapsed, and doing both at once is cheaper than either alone.
