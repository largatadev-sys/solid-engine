**Final gate (2026-08-11), after three more founder passes and a second code review.** The passes: the editor **stages every change until "Save to Diary"** (photos included — picking one used to POST it and tapping a bin used to DELETE it and its bytes, so a traveler tidying an entry was making irreversible changes while still deciding); a save now lands on the **same confirmation the create does**, worded for an edit; and a **photo swap on a full entry** is no longer refused.

**That last one was mine, and it is the sharpest lesson in the story.** Making the editor stage meant applying the staged edits as a *sequence* of calls, and I ordered every addition before every removal — protecting the floor (never reach zero mid-save) and breaking the ceiling in the same stroke. The founder hit it immediately: delete one photo from a full entry, add another, *"A diary entry holds 5 photos."* **Neither fixed order works**, because the server enforces both fences one call at a time — adds-first breaks a swap at 5, removals-first breaks a swap at 1. So the order is **computed rather than chosen**: `saveSteps()` interleaves against a running count, adding while there is room and removing while more than one remains, so the entry never leaves the 1..5 window at any intermediate step. Sabotage-verified by deleting the room check, which fails the cap test immediately.
