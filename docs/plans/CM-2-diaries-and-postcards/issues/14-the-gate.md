- *2026-09-07, a real bug the review found and this branch fixes:* **adding a day before a diary’s start produced two days both numbered Day 1.** `addDay` widened the diary and then numbered the new day against the moved start, while every existing day kept a number derived from the old one — and `diary_day` uniques only `(diary_id, date)`, so nothing refused the collision. Proven on the live stack before the fix (`07-05=Day1`, `07-03=Day1`, and the two returned out of order) and closed by shifting the dated days’ ordinals by the same delta, which preserves the gaps the ordinal rule exists for. `extendingTheRangeBackwardsRenumbersTheDaysAlreadyThere` pins it and is sabotage-checked. **Left alone deliberately:** editing a diary’s dates through `PATCH /v1/diaries/{id}` still leaves existing ordinals frozen, so the numbers no longer track an edited range. That produces no collision, it is what V53’s header intended (“a day keeps its number if the diary’s start ever moves”), and reconciling it with `spec.md:60`’s derived-from-the-start rule needs a founder ruling and a new refusal for a date edit that would strand a day — backlogged, not smuggled into a bug fix.
