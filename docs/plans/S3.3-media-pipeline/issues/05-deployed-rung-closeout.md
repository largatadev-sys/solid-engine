**2 · A REAL WEB BUG, found by driving the browser and not by any test — the S1.3 lesson repeating exactly.** `<Image>` on react-native-web **ignores `source.headers`**. The avatar uploaded successfully and then rendered as a broken image, because RNW issued a bare anonymous GET against a media endpoint that requires a bearer token. Every layer said green: Jest resolves the `.native` fork, the ITs never touch a browser, and the screen *rendered*. The tell was one line in the driver's request list — `ANON GET /v1/media/…` among `bearer` everything else. Fixed by platform-forking the resolver: native passes headers through, web fetches the bytes with auth via `apiClient.fetchBlob` and hands `<Image>` an object URL. Re-driven after the fix: **every media request now reads `bearer`.** Both halves are in CLAUDE.md's Gotchas.

**3 · Driving a web file picker took five attempts, and four plausible ones fail silently.** The picker creates a hidden input, clicks it, and removes it on settle; headless Chrome opens no chooser, so `cancel` fires immediately and the element is gone before CDP can reach it — `DOM.setFileInputFiles` then attaches to nothing and **reports success**. Rejected in order: querySelector-by-nodeId, resolve-by-objectId, `Page.setInterceptFileChooserDialog`, hooking `appendChild`. What works is planting the file *before* the click (patch `HTMLInputElement.prototype.click`, adopt a pre-seeded `DataTransfer`, dispatch `change`). `drive-preview.js` gains `--upload label=path`; the bytes come off disk, so the real handler → repository → multipart path runs.

**Bug 1 — `FormData` on RN 0.86.** The decade-old `{uri, name, type}` idiom now throws **`Unsupported FormDataPart implementation`**, and the obvious fallback (`(await fetch(uri)).blob()`) throws **`Creating blobs from 'ArrayBuffer' … are not supported`**. Fixed with `expo-file-system`'s `File`, which `implements Blob`. **The error message actively misled**: our catch mapped it to *"Could not reach the server"*, sending the investigation to connectivity and the `10.0.2.2` tunnel for a failure that never touched the network. One temporary `console.warn` of the raw cause ended it.

**Bug 2 — `<Image>` drops `source.headers` on native too.** Ticket 05 comment 2 recorded this as a *web* bug and fixed only the web fork; the device proved the native fork carried the identical false assumption. The avatar uploaded, the media GET reached the backend, and the backend logged `Security rejection: code=UNAUTHENTICATED` — a bare anonymous request. Fixed with `File.downloadFileAsync(url, dest, {headers})`. **Both fixes are now pinned by tests that assert auth is attached on each platform**, and both traps are CLAUDE.md gotchas.

**5 · The code review found a real defect the whole story had missed: EXIF orientation was never honoured.** Decision 5 and AC 5 both say a rotated phone photo must render upright, and ticket 02 checked the box — but `grep -i orientation` over the backend returned **zero hits**. The cause is subtle and worth recording: `ImageIngest` decoded to a `BufferedImage` first and handed *that* to Thumbnailator, and by then the EXIF tag is gone — pixels carry no orientation. So the library was in the tree for exactly one reason (honouring orientation, per its own dependency comment) and was being used in the one way that cannot. **The strip then made it permanent**, since the tag is discarded with everything else. Fixed by rotating from the *bytes* (`Thumbnails.of(InputStream).useExifOrientation(true)`) before decoding, and **sabotage-verified**: flipping the flag to `false` fails `aSidewaysPhonePhotoComesOutUpright` with a real EXIF `Orientation=6` fixture.

**10 · The founder iterated the avatar crop into ONE shared cropper, and the web-only version came out.** Sequence of founder calls, each on sight of the running build: crop should be circular → the web got a `react-easy-crop` modal (verified by the founder) → *"can't we do the same for the mobile?"* → **one shared component on both platforms, zero new gesture dependencies**. `CircularCropper.tsx` is a single file — RN `Modal` + `PanResponder`, both of which react-native-web ships — over a pure geometry module (`cropGeometry.ts`, 19 unit tests). **12 · The founder asked what happens to a pro-camera photo, and the honest answer produced the auto-downscale.** Probed live before answering: an 11 MB upload gets the named domain refusal (`400 PHOTO_TOO_LARGE`, *"the limit is 10 MB"* — the 10→12 MB gap between domain and servlet caps working as designed), while a 50 MB upload gets a **connection reset** — Tomcat kills the stream before buffering, correct protection with an unhelpfully generic client message, and no server-side fix can exist because no response survives the abort. Since a modern phone in a pro/48MP mode really does produce 20 MB+ files, warnings were the wrong tool: **the client now downscales before upload** — longest edge 2048 (mirroring ingest's `DISPLAY_MAX_EDGE`, beyond which the server discards pixels anyway), JPEG 0.92, both platforms, both shapes: free picks route through `downscaleForUpload` (canvas on web, `expo-image-manipulator` on native), and the circle path's crop output is capped the same way (previously uncapped — a zoomed-out crop of a huge photo could itself exceed 10 MB *after* a successful-looking crop). Pure maths in `cropGeometry.downscaleTarget`, unit-tested; no-op for images already within bounds, so small photos are never re-encoded.

**Verified with a 29.2 MB / 24-megapixel generated noise JPEG — a file that cannot pass the servlet cap unshrunk, so upload success is itself the proof.** Native: picker → shared cropper → confirm; the manipulator's cache output is **2.9 MB (2048²)** where an uncapped 4000² crop would be ~12 MB, and the stored row reads 2048×2048. Web, in the rebuilt container: the same 30,606,197-byte file planted → modal → confirm → `bearer POST /v1/me/avatar` → the new media id fetched and rendered, zero console errors. Residuals, stated honestly: the two `downscaleForUpload` *call sites* (cover, activity photos) are covered by tsc and the unit-tested maths but not by a live walk — the plumbing they share with the crop path is what the walks exercised; RAW files remain a named `NOT_AN_IMAGE` refusal (ImageIO cannot decode them, and "try a JPEG or PNG" is the right advice); HEIC on web fails at browser decode with the read-error message (Android decodes HEIF natively, and the manipulator's JPEG re-encode actually *improves* server compatibility there). Two tooling notes: `drive-preview.js --upload` now plants file bytes as **chunked base64** — the old one-shot JSON byte-array became a ~110 MB V8 source string on a 29 MB file and hung headless Chrome for ten minutes; and the emulator's photo-picker grid kept reflowing under blind taps because **every `screencap` written to `/sdcard` root is media-scanned into the gallery** — 185 stray screenshots deleted, captures now go to `/data/local/tmp`.

**13 · The founder asked whether each preview surface can define its size — the answer is the variant ladder, and auditing it found one wrong rung.** Per-surface *exact* sizes would mean a resize-per-request service; the two stored variants (display ≤2048, thumb ≤400) plus render-time scaling are the MVP-right mechanism, and each surface simply fetches its rung. The audit: activity-strip tiles and published gallery tiles already fetched `/thumb`; full-width covers correctly fetch display; but **all three small-avatar surfaces (`Avatar`, `AvatarStack`, the published byline) fetched the full 2048² display into 96px-and-smaller circles** — a ~16 MB decoded bitmap where ~400 KB serves. `thumbOf` in the media contract now derives the thumb URL, guarded by `isOurMedia` so an external Google-import avatar URL is never suffixed with a path that is our contract, not the web's — pinned by unit tests. Verified at the shipping layer on both platforms: the native media cache shows a `…_thumb` file after the Profile tab renders, and the driven preview's request list reads `bearer GET /v1/media/…/thumb`.

**14 · The founder's three profile-photo reports were one bug wearing three costumes: the photo committed on pick while everything else on the form commits on Save.** Reported after a real walk: a picked photo "stays" after backing out without saving · replacing shows no preview · changing without saving "removes" the actual photo (replace had already deleted the old blob server-side — nothing left to restore). All three dissolve under one model change: **the pick is staged locally and commits with the form.** `StagedAvatar` holds the cropped pick (or a removal intent); the circle previews `avatarPreviewOf(staged, currentUrl)` — the staged photo's local uri renders directly through the existing `Avatar` (a non-`/v1/media/` uri passes `mediaSourceFor` untouched), so the preview is instant and fetch-free, which is also what fixes "no preview". Save/Continue uploads the staged photo (or DELETEs on staged removal) before the field save, with photo failures surfaced via `messageForPhotoFailure` and the button busy through the whole commit; leaving the screen discards the stage by construction (component state). Helper unit-tested (4 cases). **Verified stepwise on the emulator**: staged gradient previews instantly with the photo row count unchanged → back-without-save restores the server photo → Save lands the row (07:44:33) and the Profile tab renders the new avatar. **On web**: pick → Use photo produced **zero** `POST /v1/me/avatar` in the driven request list — the stage holding. The commit path is the same shared screen on both platforms; native carries its live proof.

**Two rig traps from this walk, both now in CLAUDE.md**: the emulator app cold-starts into the *last visited route* (expo-router restores it), so a blind tap-chain that assumes the tab root can land on any screen — one chain opened *"Delete Day 1 and everything in it?"* and only the screenshot-before-tap discipline kept the next tap off DELETE; and every `screencap` written under `/sdcard` is media-scanned into the photo picker's grid, shifting the tiles between the look and the tap — three identical misfires, 185 stray screenshots cleaned, captures moved to `/data/local/tmp`.

**Two side-findings, both recorded rather than half-fixed here.** The first emulator confirm looked like a silent failure and was the *emulator itself* rebooting mid-walk (machine instability, twice today) — no app crash existed in any buffer; re-walked clean. And `useMediaSource` turned out to be one-shot: a transient fetch failure (cold-start token race) left a grey avatar for two minutes until a remount retried — everything underneath was healthy. That retry gap is now an epic-map backlog line with its trigger, not a quiet TODO.
