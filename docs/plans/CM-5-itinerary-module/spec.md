# CM-5 — The itinerary module: publication takes the itinerary name, the readers move onto the object, the old package is decommissioned

**Status:** Drafted 2026-09-09 — grilled that day (grill-with-docs, four rounds; the record is `grilling.md` beside this file, and every decision below cites it); awaiting the owner's review and `/to-tickets`; **builds after two small PRs land ahead of it** (the cycle rule with the request-principal move, and the seven owed boundary guards — both ADR-039 lines, both pullable now), last in the content-remodel arc · **Epic:** none (the content-remodel arc, after TW-1) · **Depends on:** TW-1 (merged 2026-09-08), ADR-039 (2026-09-09) · **Branch:** `feature/CM-5-itinerary-module`, cut from `dev` after the two small PRs merge; **two PRs from one branch** — the first is squash-merged and walked on `dev` before the second is opened (round 1 Q7).
**Grilled:** 2026-09-09, four rounds, with the tree as it stood after TW-1 and ADR-039 (record: `grilling.md`). Where the record and this spec differ, the record wins.
**ADR:** none minted. **ADR-037** is amended with this spec's docs (the freeze stays, the audience is ADR-034's, the eight diary routes are a dated exception to the sunset, no backfill); **ADR-039** decision 5 is amended (`PublicationState` survives); **ADR-034** is applied to the object read, which CM-1 had built against it.

**Freshness note:** every surface this story rebuilds is public and stays **focus-fresh pull**, per S4.35's ruling that a public feed's audience is every online traveler: the Itinerary page, Discover, Home, the profile. ## Problem Statement

Two worlds answer one question. The trip's `published` flag is what Discover, the Home feed, the profile showcase, the published page, the join card and the workspace fence all read; the itinerary object CM-1 minted is what publishing is *supposed* to create, and it is dark — the client still calls the old flag-flip, the object read has no caller, and the two acts wear one verb. The old package holds the readers: 40 files, 17 live beans, 22 mappings on seven roots, 39 integration tests, reaching into the trip module through a counted exemption that exists only so they can be deleted rather than rewritten. Three of what the readers' rebuild needs are wrong or missing today: the object's plan is one `TEXT` blob nothing can filter; the object read fences by the owner's Profile Visibility, which ADR-034 says never governs an Itinerary; and the fork move ADR-039 attached here would, done as TW-1 left it, put `trip` on `itinerary.api` and create the first cycle in the graph. Meanwhile `publication` cannot take the name the founder gave it because the old package holds it.

## Solution

Make the Itinerary the thing every public surface reads. The itinerary module owns the object, its publish, unpublish, preview and fork acts, its widened page read, a by-trip read, and the columns Discover filters on; it answers "does this trip have a live Itinerary" through the port the workspace fence already consults, so the freeze stays and the flag stops being written. Three composition modules — `discovery`, `feed`, `profile` — rebuild the readers over the new modules' apis with no table of their own and no path changed. The client moves its publish, unpublish, fork and page reads onto the itinerary module and keys the public page by the object id. Then, in a second PR after the first is walked on `dev`: the old package goes, its diary half relocating into `postcard` as legacy adapters under unchanged paths; `publication` is renamed `itinerary`; `/v1/itineraries/**` sunsets but for those eight routes; the guards that named the old package dissolve; Spring Modulith's `verify()` turns on. No backfill: a trip published by the old flag and never republished reads as unpublished, and unfrozen, from the day the readers move.

## User Stories

1. As a trip owner, I want publishing to create an Itinerary with its own address and to fence my workspace exactly as it does today, so that what strangers read is the plan I published and my co-travelers cannot edit it out from under them.
2. As a trip owner, I want unpublishing to take the Itinerary down and give the workspace back, and republishing to bring the same address back with the plan as it now is, so that a link I shared once is never dead for good.
3. As any signed-in traveler, I want to read any published Itinerary, private profile or not, so that "published" means what the word says.
4. As a traveler on Discover, I want the cards, the count, the trending destinations and the recommendations to show Itineraries, so that what I find is what the owner published.
5. As a traveler on Home, I want a postcard's trip link to open the Itinerary, so that the feed and the page agree.
6. As a traveler forking, I want my new trip made from the Itinerary I am reading, so that the copy is what I saw and not a plan its owner has since changed.
7. As a trip owner whose trip was published before this story, I want to be told nothing broke when it reads as unpublished, and to republish in one tap, so that the cutover costs me one act and no data.
8. As a traveler holding an old share link, I want it to keep opening the page for a while, so that the identity change is invisible to me.
9. As the founder, I want the readers rebuilt and walked on `dev` while the old ones still answer, and the deletion to be a separate revertable unit, so that the only running environment never carries both risks at once.
10. As the next agent, I want the old package gone, `publication` named `itinerary`, every guard that named the old world dissolved, the graph acyclic by rule and Modulith's `verify()` green, so that the strangler is finished and not merely quiet.

## Implementation Decisions

**The rulings, from the grilling record.** The freeze stays whole (round 1 Q1 b). The trip record keeps `published` and `publishedAt` and gains a nullable `itineraryId`, all read through a port (Q2). The object id is the public identity (Q3). No backfill and no read-fallback (Q4 c); the flag columns stop being written and stay in place (round 2 Q8). Discover filters on denormalized columns (Q5). The old diary half relocates into `postcard` (Q6). Two PRs (Q7). A `profile` composition module (Q8). Photos stay in media (Q9). Nothing renames in the schema (Q10). The glossary says the record is untouched and the workspace fenced (round 2 Q1). Fork acts on the object; old fork rows are left (Q2). Legacy links resolve by trip then rewrite (Q3). The page read widens additively and the snapshot gains the pin and photo ids (Q4). Archive hides the page (Q6). Republish refreshes `publishedAt` (Q7). The Itinerary's audience is every signed-in traveler, ADR-034 as ruled; CM-1's visibility fence on the object read is a contradiction and comes off (round 3). Signed-in only; the anonymous page is a line (round 4).

**"Published" means a live Itinerary exists.** `PublicationState.isPublished(tripId)` is re-implemented by the itinerary module: true when an unretired object exists for the trip. `WriteFence`, `ChatService`, `InvitationService` and `JoinService` keep consulting it unchanged, so plan edits, membership changes, joining and chat are fenced exactly as today, and retiring or hard-deleting the object is what unfreezes the trip. A second read on the same port — the live object's id and `publishedAt` — feeds the trip record's three fields. The port stays in `common.authz` until the kernel dissolution ADR-039 scheduled after this story; `trip` never imports `itinerary` (ADR-039 decision 3), and the cycle rule that lands ahead of this story is the proof.

**The itinerary module.** `com.largata.publication` is renamed `com.largata.itinerary` in the second PR, once the old package is gone; until then it works under its working name. It owns: the object and its table; `POST /v1/trips/{id}/publish` and `…/unpublish` as CM-3 left them (the editing-session guard, the tolerant unpublish); `GET /v1/trips/{id}/preview`, moved from the old package and answering the page's shape; `GET /v1/publications/{id}`, widened additively with `creator`, `forkCount`, `forkedFrom`, `estimatedCost`, `pin` and typed `days[]` beside the raw `plan`; `GET /v1/trips/{tripId}/itinerary`, the by-trip read that legacy links and the owner's "view published" use; `POST /v1/publications/{id}/fork`, which builds a Trip from the snapshot through a `TripApi.createFrom(snapshot, forker)` port and writes `fork_relationship` with the object id as source; `DELETE /v1/publications/{id}` as CM-1 built it. **Audience, everywhere in this module: every signed-in traveler** (ADR-034 decision 2), masked `404 PUBLICATION_NOT_FOUND` for non-owners while the trip is archived (round 2 Q6, today's posture), `404` when retired or absent. The `AuthoredContentAudience` call in the object read is removed. **The table gains** `title`, `destination`, `duration_days` and `cover_image_url`, written at mint and refresh, indexed for Discover's filters, and **the snapshot gains** the pin and per-activity photo ids at mint; the five objects already on `dev` predate both and render without them until republished. Republish refreshes the snapshot, the columns and `publishedAt` under the same id. `TripEditingSession` and `PlanApi` stay the module's only way into the trip.

**Three composition modules, no table, no SQL, paths unchanged.** Each is classified under ADR-038's rule at birth with an allowlist guard, and each composes at least three apis, which is what makes it a module rather than a Middle Man (ADR-039 decision 4). *`discovery`* owns `/v1/discovery/*`: browse and count over `ItineraryApi.browse(filters, hiddenOwners, archivedTrips, cursor)` and `count(…)`, the two answered by one SQL predicate so the count agrees with the list (epic-map line 193 is the bug this rule closes); trending destinations and recommended over the same api; suggestions over itinerary titles and destinations; people over identity's search. The archived set comes from `MembershipApi.isArchived`'s bulk form and the hidden-owner set from identity, both passed *into* the query, never post-filtered. *`feed`* owns `/v1/feed/postcards` and `…/trips/{tripId}/by/{authorId}`: `PostcardApi.feedPage(authorIds, cursor)` as today's adapter already does, author cards from identity, the `following` scope from identity's follow set, hidden private authors excluded in the query, and the card's trip link resolved to the **object id** through `PublicationApi.objectIdsByTrip`. *`profile`* owns `/v1/travelers/{handle}`, `…/published`, `…/followers`, `…/following`, `/v1/me/profile/stats` and `/v1/me/profile/published`: the header and follow lists from identity, `publishedCount` and `destinationCount` and the showcase from the itinerary module's owner-scoped reads, cards carrying the object id. Per-object lists stay where they are (`/v1/travelers/{handle}/diaries` in `diary`). `DiscoveryFilters`, the cursor grammar and the response records move with their surface and keep their shapes.

**The old diary half relocates into `postcard`.** `DiaryService`, `DiaryEntry` and its repository, `DiaryEntryPhotoAudience`, `DiaryExceptions`, the entry request and response records, `DiaryController`, `MyDiaryController`, `PublicProfileController`'s `/diary/trips` route and the feed's `/trips/{id}/by/{author}` route are already adapters over `postcard.api.LegacyEntries`; they move under `postcard/adapter/` as a legacy controller set with every path and shape unchanged, and `LegacyEntries` folds back inside the module that owned it. `PhotoSubject.DIARY_ENTRY` and the `diary_entry` table stay. The five client screens that call these paths are untouched. Their cutover and the adapters' deletion are the epic-map line minted from this grilling, with CM-2's original trigger.

**The cutover, and what `dev` looks like the next morning.** No migration touches the flag. The morning the first PR lands, every trip published by the old act and never republished has no object: its page answers `404`, it leaves Discover, its owner's workspace shows it unpublished and **editable again**, and one tap on Publish mints its Itinerary from the plan as it is. On `dev` that is roughly 290 trips including the seeded demo set, and Discover shows the handful of real objects until `seed-travelers.js` and `seed-trip.js` run through the new route. The story says this in its PR description rather than letting the founder discover it as a regression.

**The client.** `publishTrip` and `unpublishTrip` move onto the itinerary module's routes and the two mutations refetch rather than write the response into the trip's cache — CM-3's commit `0861f564` is the shape to copy back, including the `tripGrammar.test.ts` assertions. `fetchPublished` moves to `GET /v1/publications/{id}`, and the page screen, on a `404`, tries `GET /v1/trips/{id}/itinerary` and rewrites its own URL to the object id (round 2 Q3). `forkTrip` moves to `POST /v1/publications/{id}/fork`. The workspace's "Published" badge, settings items and row tap target keep reading `itinerary.published`; the row, the share link and "view published" navigate by `itinerary.itineraryId`. Discovery cards and feed trip links carry the object id and navigate as before. The client learns nothing new about diaries. The 45 old-root occurrences in the Playwright suites, the seed helper and the scripts that name `publish`, `unpublish`, `fork`, `audience` and `finish-planning` move to the new routes or are deleted with the retired acts; the 13 that name diary entries stay. `itineraryKeys` and the hook names are **not** renamed here (an owed ruling, below).

**Media.** Photos referenced by a live Itinerary stay workspace media under `TripMediaAudience`, which consults the port instead of the flag: readable by every signed-in traveler while the Itinerary is live and the trip not archived, exactly today's rule. Destruction leaving a page's photos dangling is accepted and recorded; copying into the Itinerary's custody is the evolution, with destruction's screen as its trigger.

**The second PR: deletion, rename, sunset.** In order, each a ticket: the new modules' integration tests exist and are green (written in the first PR); the old package's 32 non-diary files and their 39 tests are deleted, `RowBackedPublicationState` with them; `publication` is renamed `itinerary` and its guard, `PublicationContractIT` and `ItineraryObjectSteppingIT` follow; `/v1/itineraries/**` sunsets — every controller's dual class-level mapping collapses to `/v1/trips`, `TripLifecycleController`'s five old-root acts die, `/v1/published-itineraries/**` goes, `TripGrammarTwinIT` and the equivalence test retire having done their job, and the refusal code on the new root flips to `TRIP_NOT_FOUND` as ADR-037 decision 4 planned (the client has handled both since CM-3); the guards dissolve — `TripModuleBoundaryTest`'s legacy exemption, `NewWorldBoundaryTest`'s two-type content-half exemption and its old-world regex, `ModuleGuardMetaTest`'s `BEING_DISMANTLED` list — and trip's internals drop `public` where the layout allows; Spring Modulith arrives with `verify()` green, each module's `api` package declared a named interface (ADR-039 decision 9); the client's `TRIP_NOT_FOUND` flip is proven by the four guard files' tests. **The old root's sunset has one dated exception:** the eight diary-entry routes, now served from `postcard`.

**Events: none new.** The badge refetches; the fence reads the port synchronously. The first content event still waits for the FK-drop story.

**Docs.** This spec's PR amends the glossary, ADR-037, ADR-039, the object contracts and the epic map (see the record's last section). The gate annotates the epic-map line built, updates the BUILD_STATUS row, and records the measured counts.

## Testing Decisions

A good test here asserts **what a path answers, what rows exist afterward, and who may read** — never a module's internals. Seven seams, the first written before anything is deleted.

1. **The new modules' contract tests, before the old ones die** *(the story's proof; prior art: CM-1's contract classes, `DiscoveryFiltersIT`, `PublicationContractIT`)* — the page read widened; the by-trip read; fork from the snapshot with provenance by object id; Discover's browse, count, trending, recommended, suggestions and people over objects, with **the count agreeing with the list under every filter and every fence**; the feed's scopes and its trip link by object id; the profile's counts and showcase; the legacy diary adapters answering byte-identical from `postcard`. The gate diffs the assertion lines these carry over from the 39 they replace, TW-1's script reused.
2. **ADR-034 on the object, the test CM-1 lacked** — a stranger reads a private owner's Itinerary, its photos and its fork; the same stranger is refused that owner's postcards. A test that fails on the tree as it stands today.
3. **The port** *(prior art: `WriteFence`'s tests, `PublicationContractIT`)* — publish fences edits, membership and joining; unpublish, hard delete and a retired object unfreeze; the trip record's three fields follow the object; a trip flagged by the old act and without an object reads unpublished and editable.
4. **The migration-free cutover, stepped** — on a database holding old-flag trips, the readers answer none of them and the fence admits edits to them; no `UPDATE` runs.
5. **The guards, in final form** — the legacy exemption gone and its absence asserted; the content-half exemption gone; the dismantled list empty and the meta-test green with `discovery`, `feed`, `profile` and `itinerary` under the rule; the cycle rule green; `verify()` green; `TripRawSqlWaiverTest` unchanged.
6. **Playwright, both lanes** — the publish and unpublish walks on the new routes, the page by object id, the legacy link rewriting, Discover and Home over objects, the fork walk; the 45 old-root occurrences migrated and `npx playwright test --list`'s total read, never the tick.
7. **The `dev` walk, by hand, between the two PRs**, with `t1 = owner, t2 = stranger, t3 = private owner, t4 = member`: t1 publishes and the workspace fences; t2 reads the page, finds it on Discover and Home, forks it; t3's Itinerary is readable by t2; t1 archives and t2 loses it; t1 unpublishes, edits, republishes and the same link resurrects at the top of Discover; an old-flag trip of t1's shows unpublished and editable, then one tap publishes it. Read against a backend whose log lines name the itinerary module.

The connection ceiling stands: every new integration test reuses the shared context signature.

## Out of Scope

A backfill of any kind · the five old Trip Diary screens' cutover and the adapters' and `diary_entry`'s deletion (their own line) · an Itinerary page that opens signed-out (its own line) · the FK drops, the schema story and any table or column rename or drop · the kernel dissolution (after this story, ADR-039) · renaming the client's hooks and keys (owed ruling 2) · copying media into the Itinerary's custody · a destruction screen · a broker, a formatter, the build-module split (ADR-039's deferrals) · any change to what a Diary or Postcard is.

## Further Notes

- **Measured before this was written:** the old package is 40 files (8 the diary half), 17 live beans, 22 mappings on 7 roots, 39 integration tests; two trip files reach into it, counted; 45 old-root occurrences in `e2e/` and `scripts/` name the five retiring acts and 13 name diary entries; five client screens call the diary paths; the local stack held 28 published trips and 0 objects on 2026-09-09, `dev` 295 against 5 at CM-3; the object read's visibility fence is one line, `PublicationController:55`.
- **What this story deletes, stated so it can be objected to:** the old package minus its diary half; the flag writes and `RowBackedPublicationState`; `TripLifecycleController`'s five old-root acts; the old root and the projection root; the twin and equivalence tests; three guard exemptions. Nothing in the database is touched.
- **The two acts under one verb, closed:** after the first PR the client calls one publish, the itinerary module's, and the old flag-flip has no caller; after the second it has no route. The CM-3 lesson — diff the implementations, not the paths — is why seam 3 exists.
- **Why no backfill is the founder's call and not the agent's:** the recommendation was a migration; the ruling was that owners republish. It costs `dev` its demo set for a morning and buys a story with no data migration, no stepping test of one, and no second truth about what "published" meant before.
