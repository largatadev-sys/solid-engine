# 03 — The fence: `TRIP_ARCHIVED`, one checker, enumerated

**What to build:** an archived trip refuses every act on itself — and keeps exactly one door open: anyone may still leave. Demoable at the API: archive a trip, walk every mutating endpoint, watch each refuse with the same envelope — then leave as a member and watch that one succeed.

1. **One checker, sibling of the guard** (spec decisions 3 + 11): a single method taking the guard-resolved `Membership`, passing on a live trip, throwing the conflict subtype carrying **`TRIP_ARCHIVED`** on an archived one. Never inside the guard — the guard answers *who you are*, this answers *what's allowed now* (widening the guard's contract is stop-rule territory and was explicitly declined). Never scattered per-service `if`s (Artifact 03's default-by-omission) and never AOP (no precedent in this codebase; S0.2's invisible-interception history).
2. **The call sites — acts on the trip freeze** (spec decision 4): itinerary field edit (`PATCH`) · day create/patch/delete · activity create/patch/delete/move/reorder · edit-lease acquire/renew (release stays callable — releasing a lease that cannot exist is harmless and refusing it would be a dead end) · lifecycle `POST /start` and `/complete` · invitation **send** and **revoke** · ownership-offer **create** and **revoke** · **removing another member**.
3. **The exemption is a rule, not a special case:** self-removal (leave) passes the fence — *acts on your own membership survive archive* (founder ruling). On the members DELETE endpoint the fence therefore applies only when caller ≠ target. `OWNER_CANNOT_LEAVE` is unchanged — the owner still cannot leave, archived or not (INV-4; the recorded path out is unarchive → transfer).
4. **Four doors are already fenced structurally, in code they don't touch:** invitation accept/decline and offer accept/decline act on a `PENDING` row, and archive voided every pending row transactionally (ticket 02) — `VOIDED` is terminal, so the existing status checks refuse. No new check lands in those handlers; the enumeration IT covers them anyway, proving the *outcome* rather than trusting the reasoning.
5. **The enumeration IT** (spec AC 4 — the fence's real guarantee): one test class walking **every mutating endpoint** against an archived trip, asserting `TRIP_ARCHIVED` (or the structural refusal for the four voided doors) — **with the positive control: self-removal succeeds**. Two outcomes by construction, so the test can distinguish "correctly refused" from "endpoint doesn't exist" (the indistinguishable-outcomes rule). This test is also the tripwire for the future: a new mutating endpoint added without the checker fails it. Guard-assertion bodies must pass validation (S1.5's comment 5: `@Valid` runs before the controller body — an invalid body answers 400 through a path that never consulted the fence).
6. **No eviction, proven:** archive leaves every membership row intact; after unarchive the same roster works the trip again (spec AC 5).
7. **Ladder order holds:** the fence check runs after authority — a non-member probing an archived trip still gets the guard's 404, a non-owner member attempting an owner act still gets 403; `TRIP_ARCHIVED` is only ever told to someone entitled to act at all. Asserted in the enumeration IT for at least one endpoint per family.

**Blocked by:** 02 — archive and unarchive end-to-end on the API *(the enumeration IT archives through the real endpoint, never planted state)*.

## Comments

**2026-07-28 — done. 5 ITs enumerating 18 mutating endpoints; full suite 301, 0 failures.**

1. **The fence lives in `common/authz` behind a resolver seam — ADR-011's pattern, reused wholesale.** `WriteFence` needs the workspace's state but must be reachable from every module; a direct call would point `common` at a module and close the cycle the guard's seam was invented to prevent. So: `TripWritability` (one method, in `common`) + `RowBackedTripWritability` (in `workspace`), exactly mirroring `MembershipResolver`/`RowBackedMembershipResolver`.
2. **`requireWritable` takes a resolved `Membership`, not an itinerary id — and that is what makes the ordering structural.** You cannot call the fence without having passed the guard, so a non-member can never receive `TRIP_ARCHIVED` in place of their 404.
3. **Nine plan writes are fenced at one seam, not nine call sites.** Every plan-write method's first line already is `editLease.requireHeldBy(member)` — that call *is* the enforcement hook — so the fence check went there, before the lock check. Order matters: on an archived trip nobody holds a lease (archive released it) and nobody may acquire one, so a lock-first order would answer *"«nobody» is editing"* to a question whose real answer is *"this trip is frozen"*. The non-plan writes (lifecycle, invite, revoke, offer, offer-revoke, remove-other) carry explicit calls.
4. **The four accept/decline doors needed no code, as ticket §4 predicted — verified rather than assumed.** They all begin by loading a `PENDING` row, and archive voided every pending row transactionally, so they refuse via the existing not-found path. The IT asserts the *outcome* (`OFFER_NOT_FOUND`, 404) rather than trusting the reasoning. Note the assertion was written expecting 409 and corrected to 404 — the code was right and the test was wrong.
5. **Sabotage run and reverted.** Short-circuiting `requireWritable` to a no-op failed `everyActOnAnArchivedTripIsRefused` with `expected:<TRIP_ARCHIVED> but was:<EDIT_LOCKED>` — a *useful* failure shape: it shows the two gates are genuinely layered rather than one masking the other. The fixture deliberately has the owner hold the lease before archiving, which is what makes a disabled fence produce a visibly different code instead of a 200.
6. **The enumeration IT nearly fell into S1.5's comment-5 trap, in its own first draft.** `PATCH /v1/itineraries/{id}` requires `title` *and* `destinations`; a partial body answers 400 from `@Valid` during argument resolution — before the controller, therefore before the fence — so those probes would have passed while proving nothing. The full body now lives in a named constant with the reasoning attached.
7. **`MembershipService.archive`/`unarchive` are deliberately unfenced** — they are the way in and out. Archive checks `isArchived` for its own 409; unarchive requires it.
